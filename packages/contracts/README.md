# contracts

`openapi.yaml` is **generated** by `tools/contracts.py` and never edited by hand. It combines two sources:

- the route registrations in `services/api` (every path, method and listener), and
- `bodies.json`, the hand-written request and response descriptions (ADR 0032). Keys of `operations` are `"METHOD /path"`; `schemas` become `components.schemas`.

Every operation also carries `x-vesqira-permission` (ADR 0050): for the owner listener it is the `authz.<Permission>` named in the route's `s.route(...)` declaration (names read from `services/api/internal/authz/permissions.go`), and for the review, reader and publisher routes a capability name assigned by path prefix in `tools/contracts.py`. It is written, never edited.

`make docs` fails when the file is out of date, when `bodies.json` names a route that does not exist or a schema it does not define, or when the web client (`apps/web/src/api`) calls a route that does not exist. It also enforces a ratchet: `undescribed.txt` lists the operations that still have no described bodies (one `METHOD /path` per line, sorted).
A route missing from bodies.json and from that list fails the check (describe it), and so does a listed route that is now described (`tools/contracts.py` trims the file; it never adds to it).

Status: bodies are described for `GET /api/datasets`, `GET /api/datasets/{id}`, `GET /api/datasets/{id}/view` and the plane frame (`GET /api/datasets/{id}/plane`: content type, query parameters and the JSON header; the binary payload is documented in prose), and so is the overlay geometry frame (`POST /api/datasets/{id}/overlay-geometry`, the same framing). `GET /api/capabilities` and every `/api/figures*` and `/api/boards*` operation (request bodies, JSON replies and the two PNG routes) are described too, and so are the two `/api/notifications` operations the text editor (`GET`/`PUT /api/files/text`, 409 conflict body) and the terminal (`POST /api/terminal/sessions`; the WebSocket at `GET /api/terminal` is described in prose). The review surface is described end to end: the reviewer API (`/review-api/{token}` and its preview, comments and outcome routes) and the author's snapshot routes (comments, reply, revoke, resolve). The point-catalog routes (`POST /api/catalogs` and `/api/datasets/{id}/catalog/*`) are described too, and `Dataset.kind` (`fits` or `catalog`) says which header a dataset carries (ADR 0044), and the host storage and run folder sizes routes (`/api/hosts/{id}/storage`, `/storage/refresh`, `/folders`, `/folders/size`; ADR 0045). The relative-orientation analysis (`POST /api/analysis/relative-orientation`, its summary, and the CSV table at `GET /api/datasets/{id}/relative-orientation.csv`) is described (ADR 0047). The transfer queue routes (`/api/transfers` and `/api/transfers/{id}/cancel|retry|resolve|remove|register`; ADR 0051) are described too. The dataset locations routes (`/api/datasets/{id}/locations` and its delete and fingerprint routes), `GET /api/datasets/newer`, `Dataset.locations` and `Figure.identity` are described too (ADR 0053). The rerun check (`GET /api/jobs/{id}/rerun-check`) and the run controls (`PUT /api/runs/{id}/controls`, with the optional `controls` of `RunSummary`) are described too (ADR 0054). The linked-views route (`POST /api/datasets/{id}/link`: the sky transform over a region and the channel correspondence between two maps; ADR 0042) is described too. The mask routes (`/api/datasets/{id}/masks`, `/api/masks/{id}/delete` and `/plane`), `Mask`, and the `tier` and `mappingVersion` of every declaration (ADR 0055) are described too, and so are the region spectrum frame and the region histogram (`GET /api/datasets/{id}/spectrum` and `/region-histogram`, with the `mask` parameter). The dataset locations routes (`/api/datasets/{id}/locations` and its delete and fingerprint routes), `GET /api/datasets/newer`, `Dataset.locations` and `Figure.identity` are described too (ADR 0053), and so are the redraw check (`GET /api/figures/{id}/redraw-check`), `Scene.render`, `ChannelGrid.render` and `redrawnFrom` (ADR 0042). The exploration history routes (`GET /api/history`, `GET /api/history/{id}`, `POST /api/history`; ADR 0057) are described too. All other operations are routes only. The offline routes (`/api/offline*`; ADR 0059) and the `offline` mark on a plane or view served from a copy are described too. The saved views of the runs table (`/api/run-views`; ADR 0062) are described too.

## Types for the web client

`apps/web/src/api/schema.d.ts` is generated from `openapi.yaml` with `openapi-typescript`. It lives in its own npm project here (not in `apps/web`) because the generator needs the TypeScript 5 compiler API, which TypeScript 7 does not provide.

- `cd apps/web && npm run gen:api` regenerates it; `npm run check:api` fails if it is stale (part of `make web`).
- `catalog.ts`, `planes.ts`, `boards.ts` (including the review types) and `metrics.ts` re-export their types from it; add new described shapes there rather than writing them twice.

## Go side

`services/api/internal/server/contract_test.go` (and `internal/review/contract_test.go` for the reviewer listener) decodes real handler responses (real worker, generated fixtures) and validates them against `openapi.yaml` with kin-openapi. When a handler and the spec disagree, the spec is what describes the wire; change it to match the handler, not the other way round, unless the wire format is meant to change.
