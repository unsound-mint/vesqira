# ADR 0044: Host storage, run folder sizes, and what a finished job used

Status: **proposed; implemented, awaiting owner review.** Decided by the implementing agent under the owner's delegation of ADR decisions (roadmap Stage S). No real cluster tool (`beegfs-ctl`, `lfs`, `quota`, `sacct` with a real accounting database) was run: see Validation. The new UI has not had a design review.

## Context
The owner's own HPC work hit the 400 GiB home quota and a run stalled writing its output; runs were cancelled and resubmitted by hand with other core counts; ROHSA runs were killed for memory when submitted with the default; run folders of 23 to 88 GB piled up with no view of where the space went; requests were sized by guessing. Slurm already knows how much each job used (`sacct`), and the host knows its quota and free space, but Vesqira showed neither.

## Decision
- **Storage of a host, on demand and cached.** `GET /api/hosts/{id}/storage` returns the last look if it is younger than 10 minutes, otherwise makes one; `POST .../storage/refresh` makes one now. A failed look is reused for 1 minute, and a refresh inside 15 seconds of the last look returns the cached one, so the button and an open screen cannot hammer a shared login node. One look is one `ssh` call (`Manager.Storage`): every tool that exists runs once with a 20 s `timeout` and `head -c 16384`, and the sections are cut at a line starting with a random marker (remote output cannot forge a boundary). The first tool whose output **parses** is the answer, in the owner's order: `beegfs-ctl --getquota --uid $(id -u)`, `lfs quota -u $USER <root>` (per declared root, at most 8), `quota -s -w`. A tool that prints something unreadable is skipped, not repaired. When none parses the answer is "this site's quota tool is not available" and the free space of each root from `df -P -k` is still shown, labelled as the file system's, not the user's allowance. The response keeps the tool's name and command, each line as printed (`raw`), and bytes (powers of 1024, which is what the tools print); soft and hard limits are `null` when the tool says there is none. Nothing runs with `sudo`; nothing writes.
- **Where it is shown.** `HostStorage` (a collapsed section under each host in the Hosts panel and at the foot of a job) asks nothing until it is opened; then it asks once, again every 10 minutes while open (the server decides whether that is a new look), and on Refresh. A quota line at 90 % of its hard limit says so in words, not only by colour.
- **Run folder sizes.** `GET /api/hosts/{id}/folders` lists, with no host call, the output folders of the host's jobs and the run folders found by scanning opened projects on it, with the sizes measured so far (`null` for unmeasured, never 0), largest first. `POST .../folders/size {path}` runs `du -sk -- <path>` (read-only; `timeout 80` on the host, 90 s on the connection; one at a time per host; the path must be a clean absolute folder inside one of the host's roots and is passed as one quoted argument). `du` exit status is kept: unreadable entries make the size a lower bound (`partial`, shown as "at least"), a timeout shows no size. The screen has a per-folder button and "Measure all", which measures sequentially and carries on after a failure. Sizes are held in memory only. There is no delete: removing files on a host stays out of scope (ADR 0041: archive and delete are catalog actions and never touch a host).
- **What a finished job used.** The status commands (the watcher's batched call and the Refresh button's, now one format) ask `sacct` for `JobID,State,ExitCode,Elapsed,Start,End,Timelimit,ReqMem,ReqTRES,AllocCPUS,TotalCPU,MaxRSS,NNodes` and drop `-X`, because `MaxRSS` exists on steps (`12.batch`, `12.0`) only; still one `squeue` and one `sacct` per host. `ParseBatchStatus` groups the rows per job; state and exit parsing read the job's own row as before. `ParseUsage` builds `Usage`: peak memory is the largest `MaxRSS` of any step (a per-task maximum, not a sum), requested memory is the `mem=` of `ReqTRES` (a total) else `ReqMem` with its `c` (per CPU) and `n` (per node) multiplied out, and every value sacct did not report is `null`, not 0 (a bare `MaxRSS` is KiB; all-zero `MaxRSS` is "not recorded"). It is stored once, as JSON in `jobs.usage` (schema 9), by the caller that sees the end (`SetUsage` only touches an ended job), so a later look cannot overwrite it. Jobs ended before this change have none and show none.
- **CPU efficiency and the unaccounted case.** `TotalCPU / (Elapsed x AllocCPUS)`. If that is under 0.5 % over at least 60 s, the work almost certainly runs in a process Slurm does not account (the ROHSA case), so `cpuNotAccounted` is set, no percentage is stored, and the screen says "CPU time not accounted by Slurm for this job" and why. A job under a minute at 0 CPU is a measured 0. If the job row's `TotalCPU` is 0 but its steps' sum is not, the steps' sum is used. Efficiency above 100 % is shown as it is.
- **Words.** The job shows "Used 79.0 GiB of 140.0 GiB requested; ran 6 h 12 min of a 3 d limit; CPU efficiency 43 %." (GiB, because Slurm's `G` is 1024^3). A job or any step in `OUT_OF_MEMORY` is explained as stopped for exceeding its memory, with the note that its peak understates the real need; `TIMEOUT` as stopped at its time limit, with the elapsed time as a floor and the output possibly incomplete. Neither says anything about whether the result is valid.
- **Suggestions, never applied.** `Usage.suggest` (computed by `SuggestRequest`): memory = peak x 1.3 rounded up to a whole GiB (to 256 MiB steps under 1 GiB); time = elapsed x 1.5 rounded up to a minute, capped at the partition limit when one is given. For a job killed for memory the larger of 1.3 x peak and 1.5 x the request. Time is suggested only for `COMPLETED` or `TIMEOUT` (a job stopped early says nothing about how long the work takes; for `TIMEOUT` the basis says it is a floor), memory only for those and OOM; a cancelled or failed job gets none. "Run again with…" (`rerun` now returns `lastJob {id, name, usage}`) and the new-job form (the newest measured job of the same kind on the same host) show a `SizingHint`: the measured peak and elapsed time next to what the form currently asks for, a warning when the request is below what that job reached, and "Suggested from job N's measured use" with one button for memory and one for time. Clicking is the only way a value is applied; preparing the job without clicking sends the form as it was.
- **Contracts.** The four routes are described in `packages/contracts/bodies.json` (ADR 0032) and checked against real handler responses by a Go contract test; `apps/web/src/api/schema.d.ts` is regenerated. `Job.usage` and the rerun's `lastJob` are in the hand-written web types, not yet in the spec (the job routes are not described yet).
- **Access.** All four routes are on the owner's loopback handler only (`localOnly` refuses a non-loopback Host and a cross-site request); the reviewer's handler has none of them (tested).

## Alternatives
- **Poll storage on a timer from the server**: touches the login node when nobody is looking, and a VPN that is down would be retried forever. Rejected; it is on demand with a cache.
- **A second `sacct` call for steps**: two calls per host per interval. Rejected; one call without `-X`.
- **Sum of `MaxRSS` over steps**: wrong for sequential steps (they do not coexist) and for tasks of one step. The maximum is a lower bound on the peak of the job and is labelled as the largest peak of any single step.
- **Parse every quota tool's output in the shell** (`awk`): the parsers need tests with garbage, oversize and unusual layouts; they are Go functions with fixtures instead.
- **Apply the suggestion by default**: a measurement from one run is not a policy and may come from a job that died; the owner decides. Rejected.
- **Cap the time suggestion by asking Slurm for the partition's limit**: needs a `sinfo` call and partition semantics (QOS limits, defaults) Vesqira does not model. Deferred: the cap exists in `SuggestRequest(partitionMaxSec)` and the hint tells the person to check the partition's maximum.

## Consequences
- Schema 9: `jobs.usage` (JSON text, `''` for none). An older build refuses a version 9 catalog (ADR 0020). `schema_v9.sql` is the snapshot; the main branch's latest was 8 when this was written, so renumber if another slice took 9.
- The status commands changed shape (no `-X`, more columns, steps present). A site that disables job accounting returns no `sacct` rows: usage stays absent and the state still comes from `squeue`. A site whose `sacct` rejects one of the column names answers with an error on stderr (discarded) and an empty list, which the watcher reads as "not listed": **this has to be checked on the real cluster** (see Validation).
- A `du` on a very large directory tree can take as long as the file system needs; the 80 s limit means such a folder shows "did not finish", not a partial number.

## Validation
Go: parsers for `beegfs-ctl` (one and two pools, unlimited, 0 Byte), `lfs quota` (kbytes, 0 = none, wrapped file system name, over-quota star), `quota -s -w` (human sizes, empty grace column) and `df -P -k` (names with spaces), against garbage, 1 MiB of one letter, NUL bytes, negative and absurd numbers, "not enabled" messages; `du` output with unreadable entries and with timeout status; the generated shell is read-only, quotes roots, times and bounds every tool, and keeps the order; section forging; a stand-in `ssh` with fake tools (junk from the first tool does not stop the next; no tool at all; unreachable host); `du` over the stand-in `ssh` for a real folder, a partial one (unreadable subfolder), paths outside the roots, with shell syntax and with quotes; the server cache (reuse inside 10 minutes, Refresh spacing, expiry, error kept with the last good look and not retried at once), run folder listing with no host call and measuring sorted largest first, cross-site and non-loopback refusal; contract responses against the spec; sacct parsing (K/M/G/bare MaxRSS, several steps, ReqMem per CPU and per node, `ReqTRES`, unreported values absent not zero, `TotalCPU` zero with long and short elapsed, steps' sum, `OUT_OF_MEMORY` on a step or the job, `TIMEOUT`, `CANCELLED by 1000`); the suggestion math, caps and withheld cases; usage recorded by the watcher and by Refresh, recorded once, none for a running job, in the job JSON and the rerun's `lastJob`; migration 8 to 9; the reviewer's handler has none of the routes. Web: the sentences (including the 79/140 GiB example, unaccounted CPU, OOM, TIMEOUT, unreported values), request parsing, the hint next to the requested values, applying only on click in both the rerun form and the new-job form (and the form sent unchanged when not clicked), no hint without usage, nothing asked of a host until a section is opened, the 10-minute re-ask and its stop on close, Refresh, the not-available note, sequential measuring that survives a failure, no delete control.
**Not verified:** any of the real tools on a real cluster (`beegfs-ctl` on the owner's BeeGFS, `lfs quota` on Lustre, `quota` against a real quota file system other than this machine's own `quota` command, which parsed correctly here), the real `sacct` column set and `MaxRSS` units on the owner's Slurm version (the ROHSA child-process case in particular), `du` timing on a real 88 GB run folder, and a design review of the new sections.

## Rollback / Migration
Revert the web section and the four routes; `UsageFields` back to the six old columns with `-X` restores the old status calls. `jobs.usage` can stay: nothing reads it then. Restoring a pre-9 backup (made automatically before the migration) removes it.
