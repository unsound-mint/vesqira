# ADR 0030: Projects open as folders; discovery by good practice

Status: **accepted** (owner direction and approved mock, 2026-11-05). Backend implemented in the same change; the screens are not built yet.

## Context
Importing runs and files one by one does not match how a researcher works: they have a folder on this computer or a cluster, and want Vesqira to work in it the way an editor opens a repository (`docs/product/shape.md` section 3, Stage W of the roadmap). Today a folder becomes readable only through `vesqira add-root`, and every run is imported by hand. Projects in the wild are tidy in different ways (VGT's `validation_output/<name>/run_metadata.toml`, `results/<time>_<sha>/provenance.json`, or no convention at all), and some hold things that must never be opened (a blinding key). The app must find what it can without per-project adapters, never guess what a researcher did not say, and never widen what is readable beyond the folder they opened.

## Decision
- **A project is a folder** on this computer or on a registered host. Opening it adds the canonical folder as a readable source root (on a host: as one of that host's roots, which restarts the host's worker with the new root). Existing roots keep working. `/`, the home folder itself, an ancestor of home, and `.ssh`/`.gnupg` are refused ("pick a project folder, not the whole disk/home"). On a host the worker reports its own home for the same check.
- **`.vesqira/project.toml`** inside the folder holds the researcher's layout (`[layout]` lists `data`, `runs`, `configs`, `jobs`, `skip`; `[[runs.manual]]` marks), `[hosts.<alias>] repo`, and their answers (`[[answers]]`, `declared_by = "you"`, dated). It is proposed (text shown, nothing written), written only on an explicit request, edited by appending validated blocks so comments survive, never `git add`ed, and re-read at every scan. Vesqira does not touch `.gitignore`; the health list suggests ignoring `.vesqira/`. What discovery found is never written into it as a declaration: found and declared values stay apart, and each run field carries its status (`declared` by a run record, `inferred` from a folder name, `you`).
- **Discovery by good practice only.** The scanner (`internal/discover`) sees the folder through a three-call interface (`ReadDir`, `Stat`, `ReadFile` of at most 256 KiB), so the same code runs on a local folder and, through the host worker, on a remote one. Rules: skip `.git .venv venv node_modules __pycache__ .cache .tox .mypy_cache .ipynb_checkpoints` and the project's `skip` globs; list archives as skipped with their total size and never open them; never list, stat or read a name matching `*DO_NOT_OPEN*` or a folder `blind*key*` (decided from the name before any call). A **run** is a folder with a run record (`run_metadata.toml`, `provenance.json`, `run.json`, `params.yaml|json` with `metrics.json`, MLflow `meta.yaml`); the record file is stored with the run. `<UTC time>_<short sha>` folder names give start time and commit as `inferred` only. Files in a run folder belong to the run; a run in a run is its own run and the outer one gets a note. **Data** is a file in a self-describing format: FITS is registered as a dataset (header read by the worker); TIFF, OME-TIFF, CZI, ND, ND2, HDF5, Zarr are listed with "no viewer yet". A `data/raw|interim|processed|external` layout marks a role (raw and external are read-only inputs), never units or meaning. Configs are `*.toml|yaml|yml|json` under `configs/` or `config*/` and top-level `config*.toml`; job templates are `*.slurm|sbatch|pbs`, and `*.sh` whose first 4 KiB contain `#SBATCH`, under `hpc/ slurm/ jobs/ scripts/`. Anything else the researcher marks by hand once. Runs are found before the data they own.
- **Links.** A symbolic link is never followed. One that resolves outside the project is reported as "points outside the project", a dangling one as dangling, one inside as an inside link (not counted again). Content reads resolve the real path and refuse anything outside the folder.
- **Rescan** on open and on request, comparing size and modification time; no file watching, no hashing. A scan stops after 200 000 entries or 20 s of walking and says `truncated`; registering FITS headers continues as a cancellable background step with progress. Only VGT runs are imported as Vesqira runs (the existing importer, same dedupe key: the canonical run folder, so a run imported by hand is the same run); other record kinds stay project entries because only VGT has a parser. `params.yaml` and `meta.yaml` count as run records but their settings are not read (no YAML reader in the tree; adding a dependency is its own decision).
- **Needs your input**: FITS without `BUNIT` (grouped by folder), orientation maps proposed by a run import but not confirmed, result-like folders without a run record, no version control, and an unknown repository folder on a host that has past jobs. Each carries its source and the allowed answers; "leave unknown" is an answer. Answers are stored in the catalog and written to `project.toml` only when the file exists or the request says so. Confirming an orientation map goes through the existing declaration (`catalog.SetInterpretation`, declared by the user). **A declared unit for a FITS file without `BUNIT` is recorded but not applied to the dataset**: the only dataset declaration that exists is the axial-orientation one, which accepts `deg` or `rad`; a general unit overlay changes what the viewer may show as declared and needs its own decision.
- **Projects on a host** are walked by the host's worker (`walk`, in pages, with the scanner's skip rules and never-read patterns sent with each request, so the host does not stat what must not be read); the project file there is read but not written (writing on a host is an external write that needs its own authorization), so answers for such a project stay in the catalog and say so. The worker's new `canon` request is the one answer given outside the roots (it only says where a folder really is, whether it is a folder, and the account's home), because opening a folder is what adds it to them; it is reachable only through the owner routes. Registering FITS headers runs one file at a time on a single lane shared by all projects, with progress and cancel.
- **Security.** Project routes are owner routes: registered on the loopback listener only (never the review listener), behind the same Host, `Sec-Fetch-Site` and JSON-content-type guards as every owner route. Paths are canonicalised before use; the project file is written through a temporary file and a rename after refusing a symlinked `.vesqira` or target; `git` is run (locally only) with `core.fsmonitor` off, no optional locks, a timeout and capped output, outside the project's hooks; remotely the commit is read from `.git/HEAD` and the dirty count is "unknown".

## Alternatives
- Keep `add-root` and manual imports: no discovery, the setup stays outside the app.
- Per-project adapters (a VGT adapter, a Snakemake adapter): grows without bound and guesses; rejected by the owner.
- Watch the folder: needs inotify on the local machine and nothing equivalent on a host; rescan on open and on request is predictable and cheap.
- Hash every file to detect change: the cost scales with data size; size and mtime are enough to say "changed" and are not claimed to prove identity.
- Put discovered values into `project.toml`: turns guesses into declarations.

## Consequences
- Opening a folder makes everything inside it readable by the API (the same as an `add-root`), so the folder choice is the authorization; the refusals above stop the broad mistakes.
- A host may now carry more than eight roots (limit raised to 32) and its worker restarts when a project is opened.
- `catalog.List` is called per request for hints today; the runs list now reads one name and size index instead (a bench case keeps it so).
- The scan cache (`project_entries`) can be large for a big folder; it is replaced on every scan and can be deleted without loss (answers are kept separately).

## Validation
Table tests on fixture trees in three styles (VGT-like, timestamp and sha runs, untidy), a counting filesystem proving the blinding key is never listed, statted or read, symlink and nesting cases, budgets with an injected clock, the project file round trip, store and API tests (owner routes only, cross-site refusal, review listener has no project routes), Python tests for the host worker's walk (same rules, paging, budgets, roots), and a request-count test for the runs list.

## Rollback / Migration
New tables only (`projects`, `project_entries`, `project_answers`), created idempotently; no existing table changes and the catalog version is not bumped, so an older program ignores them. To roll back, delete the three tables. Roots added to hosts remain until removed in the host form. `.vesqira/project.toml` files stay in the researchers' folders; they are inert to older programs.
