# ADR 0008: Plane transport, persistent worker and coordinate readouts

- Status: accepted under delegated merge, 2026-11-04; owner review pending
- Date: 2026-11-04

## Context
The plane viewer must show one spectral plane at a time from cubes that can be several gigabytes, scrub channels interactively, and read coordinates that match a trusted WCS implementation. ADR 0007 started Python once per request (0.2 s warm, several seconds on a loaded machine), which is unusable for scrubbing.

## Decision
- **Persistent worker.** `services/scientific-worker/plane_worker.py` runs as one long-lived process per API (`worker.Persistent`). Requests are serialized (one scientific task at a time), one JSON line in, one JSON header line out, then `nbytes` of raw payload. The API bounds the header line (64 KiB) and payload (64 MiB). A timeout (30 s), a crash, a bad length or an unparsable reply kills the process group and the next request starts a clean worker. A client that goes away while queued leaves without disturbing the worker; one whose request is already running does not trigger a kill, because planes are small and a cold restart costs more than the read.
- **Read only the requested plane.** The worker finds the x, y and channel axes from the WCS (`wcs.lng`, `lat`, `spec`), never by assuming axis 3, uses `HDU.section` for a selective read, and refuses cubes that have a second axis of length above 1. Degenerate axes (for example STOKES of length 1) are indexed at 0. BSCALE/BZERO are applied in float64, `BLANK` becomes NaN, and the plane is sent as little-endian float32. A 64-bit source loses precision and the header says `source_bitpix`.
- **Transport.** `GET /api/datasets/{id}/plane?channel=N` (0-based) returns `application/vnd.vesqira.plane`: uint32 little-endian header length, a JSON header (dtype, width, height, row 0 meaning, channel, `nan_meaning`, finite-only statistics, spectral value and unit, `flagged`), then the pixels. `GET .../view` returns the axis roles, spectral and sky facts and channel flags. `GET .../coord?x=&y=&channel=` returns the astropy WCS readout. The client names a dataset id and indices only; the API resolves the stored path again against the source roots on every request, and answers 409 when size or mtime differ from the registration.
- **Cache.** The API keeps a byte-bounded LRU of worker replies (default 256 MiB), keyed by dataset id, size, mtime, operation and indices, so a changed file cannot serve stale pixels.
- **Missing data is not zero.** NaN, BLANK and non-finite values mean "no value". Statistics use finite values only. The viewer draws them in a pattern distinct from every colormap entry and says so in text.
- **Spectral axis.** Velocity is shown for VRAD/VOPT/VELO. A FREQ or WAVE axis is shown in its own unit and its velocity is `unresolved`, because FITS headers do not declare the velocity convention. A spectral axis missing CRVAL, CRPIX or a step is `unresolved` as a whole: wcslib would default them to 0/0/1, which would invent coordinates, so the worker checks the header first. Units are `declared` when CUNIT exists and `inferred` (the FITS standard default for the CTYPE) when it does not.
- **Legacy and inferred values.** A legacy AIPS spectral type (`VELO-LSR`, `-HEL`, `-OBS`) is shown under its own name with velocity `unresolved`: astropy would translate it to optical/LSRK from an absent VELREF, and Vesqira does not adopt that guess. A celestial frame is `declared` from RADESYS (RA/Dec axes only) or the CTYPE (Galactic, ecliptic), `inferred` (FK5/FK4) from EQUINOX alone, else `unresolved`. If wcslib rejects the spectral axis, the celestial axes are kept and the spectral axis is `unresolved`.
- **Precision.** Planes are float32. A finite source value too large for float32 is counted (`overflow_count`) and named in the legend instead of being called missing; BITPIX 32/64/-64 files are labelled as shown in float32.
- **Flags.** Per-channel flags exist only if the file has a `FLAGS` 1-D extension whose length equals the channel count. That is a provider convention and a fixture convention, not part of the FITS standard. Without it the viewer says "No channel flags declared"; it never says a channel is valid. Flagged channels keep their data.
- **Coordinates.** Sky and spectral readouts come from astropy/wcslib in the worker. The wire uses 0-based pixel and channel indices; the interface shows 1-based FITS pixel numbers.

## Alternatives
A worker pool (more memory, no measured need); FITS reading in Go (a second FITS/WCS implementation to trust); sending the whole cube or tiles (violates the bandwidth rule); JSON or base64 pixels (3x the bytes and slower to decode); shared memory or a Unix socket between API and worker (more moving parts than pipes at this size).

## Consequences
Planes up to 16.7 M pixels are supported. One slow read blocks the others up to the timeout. The worker keeps four parsed headers; a replaced file is detected by size and nanosecond mtime (the catalog now stores nanoseconds, so delete a catalog made by an earlier build). The worker refuses a path that is not its own real path, which narrows but does not remove the window between the API's authorization and the open; closing it needs a descriptor handed to the worker. Worker errors for unreadable files are one fixed message, so paths never reach the browser. Cross-site requests are refused for every method. Reviewer access (#14) must not reuse these endpoints without the scoped-publication checks planned there.

## Validation
Worker tests (real subprocess, generated fixtures): plane equals a full astropy load including NaN; 4D cube with degenerate STOKES before FREQ resolves axis 4; BSCALE/BZERO/BLANK against a float64 oracle with a real 0.0 kept distinct from BLANK; coordinates against the independent TAN formulas; missing spectral reference stays unresolved; missing celestial WCS falls back to pixels; flags absent is not "unflagged"; bad indices fail in a controlled way and the worker survives; truncated data is an error; a changed file is re-read; one plane of a 4.8 GB sparse cube stays under 800 MiB peak RSS. Go tests: protocol, timeout kill and restart, crash, oversized length, queued cancellation, authorization on every request, 409 on a changed file, cache eviction, and an end-to-end run through HTTP with the real worker.

Measured on one machine against a real 3 GB, 2174 x 2174 x 159 float32 cube on local disk (plane 19 MB): layout 0.23 s cold, first plane 0.10 s, next planes 0.05 to 0.07 s, coordinate readout 6 ms, worker peak RSS 165 MB. Against a synthetic sparse cube (2000 x 2000 x 300 float32 sparse cube, 16 MB plane, not representative of disk-bound reads): first plane including worker start 0.50 s, next plane 0.07 s, repeat from the API cache 0.006 s, coordinate readout 0.001 s.

## Rollback / Migration
Remove the three routes and the `Persistent` worker; ADR 0007's per-request header worker is unchanged. No stored data changes.
