# ADR 0048: Parameter sweeps

Status: **proposed; implemented, awaiting owner review.** Decided by the implementing agent under the owner's delegation of ADR decisions (roadmap Stage L and Stage 4; Q128, Q222). Real Slurm is not verified (see Validation). The new screens (sweep form, submit dialog, grid with plot) have had no approved mock and no design review.

## Context
The owner's work is sweeps: ROHSA over N (8, 12, 16, 20, 24) and lambda (3, 10, 30), VGT over block size dn and ker, each run scored afterwards and the runs compared side by side. On the cluster, concurrent jobs that share a source folder broke runs (the ROHSA script rebuilds in the shared source tree), so a sweep must be able to run one job at a time. Until now every variation was a hand-made "Run again with..." draft, and a metric could not be set against a parameter.

## Decision
- **A sweep is a base, a grid and the drafts the grid expands to.** The base is a VGT job that kept its settings (or the run that job produced). The grid is one to three config settings, each an explicit list of values typed as text and never reparsed; the cartesian product is at most 64 jobs, the first parameter changes slowest. Each combination is rendered by `buildVGT`, the code `createJob` uses (now one helper), so a sweep's draft is an ordinary draft: its script is the text submitted, it can be read and edited, it has a note ("Sweep name: N = 12") and `parent_run_id` of the base run. Swept keys go only through `SetConfigValues`' whitelist (`dn`, `ker`, `noise`, ...; never `output_dir` or `input_file`); values may contain letters, digits and `. _ + -` only. All drafts are rendered and validated before any is stored, and stored in one transaction. Creating a sweep submits nothing (tested: no `sbatch` call).
- **Tables (schema 13).** `sweeps` (name, host, base job and run, parameters as JSON, state, detail, concurrency, stop-on-failure, board) and `sweep_jobs` (job id unique, grid position, values, the script hash approved). `jobs` and `board_items` are unchanged. State means what the owner authorised, not how jobs ended: `draft`, `running`, `stopped`, `finished` (every submittable job was submitted). The DDL is one constant shared by the store and the migration.
- **Submitting is one explicit act, after reading.** `GET /api/sweeps/{id}/review` returns every script, its line difference from the base (each differing line marked as a swept setting, the output folder, the job name, or `other`, which is never expected and is flagged), the requested resources in total and per job, and, when the base job has ADR 0045 usage, an estimate that says it is a guide. `POST .../submit` must quote `sweepHash` (over the job ids and script hashes shown), a concurrency limit 1 to 16 (default 1, sequential) and an optional stop-on-failure. The hash of each script shown is stored; the scheduler submits a draft only while its script still has that hash, otherwise it is *held* and shown as such.
- **The scheduler** submits through `submitDraft`, extracted from `submitJob` and shared with it, so the hash check, `BeginSubmit` (one winner per job) and the never-retry-after-an-unconfirmed-answer rule are the same code. One mutex serialises scheduler runs and cancel; the sweep's state is read again under it before each submission (`BeginSubmit` protects a job, the lock protects the limit). In flight means `submitting`, `submitted` or `running`: an unconfirmed `submitting` job holds a slot and is never resubmitted or skipped, and is listed in the sweep's `waitingOn`. It runs on four triggers: the approval, the winning end-state transition in `applyJobStatus` (so the ADR 0043 watcher and the Refresh button both drive it), a resolved `submitting` job, and every watcher pass (no host call unless something is to be submitted), so a restart loses nothing. Slurm's `MaxActive` limit (429) means wait for the next trigger. A failed job frees its slot and nothing is retried; with stop-on-failure chosen at approval the sweep stops and says why. Cancel stops scheduling (drafts stay drafts); optionally it also asks Slurm to cancel queued and running jobs. A stopped or finished sweep with drafts left may be approved again.
- **Runs.** Jobs are VGT drafts with automatic import on (ADR 0043), so each finished job becomes a run through the existing path; the sweep reaches it through `sweep_jobs.job_id` and `jobs.run_id`.
- **The grid.** `GET /api/sweeps/{id}/grid?metric=&x=` returns one row per job in parameter order with the metrics the run declared (the run metric model: unit, uncertainty; null is "not recorded", never zero; a job without a run has none), the metric keys with their units, and the plot series for a metric against one parameter, one line per combination of the other parameters. A metric the runs declared in different units is not drawn (reason returned); different definitions are reported as a note. Numeric parameter values sit on a numeric axis, others are categories in list order. Nothing is labelled best (AGENTS.md invariant 9). The web table is sortable; the plot's lines differ by dash and marker as well as hue, are labelled directly and in a legend, and break at a missing value.
- **The board.** `POST /api/sweeps/{id}/board` makes one board ("Sweep: name") with a job panel per job in parameter order (once per sweep; 409 with the board id after that). The label "N = 12, λ = 10" is **not** stored in a board note: notes are frozen into reviewer snapshots. `boardView` fills an owner-only `label` and `sweepId` on the job's `JobInfo` from the sweep; a snapshot freezes only a job's name and state (tested). The board shows the sweep's grid above the panels.
- **Scope.** VGT jobs and ROHSA jobs that kept their settings sweep (note below for ROHSA). Custom scripts, and a ROHSA job drafted before settings were kept, have no editable settings and are refused with that reason.
- **Note: sweeping ROHSA.** The sweep builder is shared: the base job's template picks the key whitelist (`CheckSetting` or `CheckROHSASetting`), the renderer (`buildVGT` or `buildROHSA`) and the draft's template; everything else (grid, drafts in one transaction, review, scheduler, `submitDraft`) is the same code. Swept keys are the ROHSA whitelist of ADR 0046, plus the tied `lambda`; `output_dir` and `input` are refused. The review's expected differing lines for a ROHSA sweep are the swept keys' config lines (the tied key is three), the output folder and the job name, and nothing else. **One job at a time is the default and is the server's:** approval without a `concurrency` means 1 (an explicit 0 is refused), the review carries `defaultConcurrency` and, for ROHSA, a `concurrencyNote` that the form shows with the limit and as a warning when the owner raises it. The reason is the owner's: jobs share one source folder, a job rebuilds the binary there when a source is newer, and a rebuild replaces the binary while another job may be starting it (the template's lock keeps two builds apart, not a build from a start); large fits also ask for 100G or more each. Every draft requests what the base job did, and a parameter such as N crosses a row of the owner's sizing table, so the review shows the table's suggestion for each draft next to what it requests (`sizing` per job, ADR 0046) and warns above the list when a draft asks for less memory. ROHSA drafts import their fit by themselves when they complete, from the host (ADR 0046, remote fits; ADR 0043), so a ROHSA sweep's grid shows each imported run's declared `fit_metrics` and links the row to its run, as for VGT; a job whose fit was not found has a row with no run and the reason in its notification. The pipeline's own memory preflight (`memory_gb`, 96 in the owner's 2048 configs) can refuse a larger N whatever the job requests; `memory_gb` is now an editable (and so sweepable) ROHSA setting (ADR 0046, Limits).
- **Routes** are on the owner listener only (`/api/sweeps...`); the review listener has none (tested). Bodies are described in `packages/contracts`.

## Alternatives
- **Free-form substitution into a script template** for ROHSA and custom scripts: puts text from the UI into a script. Rejected; typed whitelisted settings instead.
- **Submit all at once and let Slurm queue**, or Slurm job arrays or dependencies: the race in a shared source folder is not Slurm's to know, and a dependency chain would stop at the first failure. Rejected; Vesqira submits the next job when the previous one ends, as the owner chose.
- **Label in the item note**: leaks into snapshots. Rejected.
- **A new board item kind for the table and plot**: needs a rebuild of `board_items` and a reviewer-safe frozen form. Deferred; the grid is shown above the panels on the sweep's board and on the sweep page.
- **A "best run" column or sort preset**: AGENTS.md invariant 9. Rejected.

## Consequences
- Schema 13. An older build refuses a version 13 catalog (ADR 0020). `testdata/schema_v13.sql` is the snapshot.
- Pinning a job panel (ADR 0043) replaces it with a figure and drops the job link, so the parameter label of that panel is no longer shown on the board; the grid above still lists the job.
- A sweep waits while any of its jobs is `submitting`; the owner resolves it (Check on the host). A job Slurm stopped listing stays `submitted`, holds its slot and is announced as unknown (ADR 0043); the sweep does not guess.
- The estimate multiplies the base job's elapsed time; a parameter such as N can change time and memory a lot, so it is labelled a guide.

## Validation
Go (stand-in ssh, sbatch, squeue, sacct, scancel): grid expansion in parameter order, the 64 cap, 1 to 3 parameters, refusals (bad value, key, name, ROHSA base, both or no base) leaving nothing stored; drafts created with nothing submitted; preview counts and estimate; limit 1 submits one job and the next only when it ends, repeated triggers submit nothing more, every job reaches Slurm once with its own id; limit 2 keeps two in flight; cancel stops the rest and leaves drafts, optionally cancels running jobs, and approving again continues; a failure does not block the others and nothing is retried, stop-on-failure stops; an unconfirmed submission holds its slot, is shown and is never resubmitted; approval refuses a stale hash and an edited draft is held; finished jobs become runs and feed the grid rows, metrics and plot (gap not zero, no "best"); the board's order, labels and one-per-sweep rule, and a snapshot with no label or parameter; the differing lines of each draft are exactly the swept settings, the output folder and the job name; response bodies against the spec; the review listener has no sweep route; migration 12 to 13. Web (vitest): the form (count before create, count dropped on change, at most three parameters), the submit dialog (differing lines with reasons, total request, default 1, hash sent, invalid limit refused, unexpected-line warning), the grid (declared values, sorting, a line per other parameter, gaps, mixed units explained, no "best") and the board labels. ROHSA sweep (Go, stand-in host): four drafts from N x tied lambda in parameter order with each draft's embedded config carrying its values, no unexpected differing line, per-draft sizing 100G for N = 4 and 140G for N = 8 on a 2048 crop, the concurrency default and its reason in the review, approval without a limit running exactly one job, a second approval refused, the next job going when the first ended, `concurrency` 0 refused, and refusals (`output_dir`, `input`, a VGT key on a ROHSA base and the reverse, a bad value, an old base) leaving nothing stored; the review, the approval without a limit and the sizing route against the spec. Web: the form's ROHSA keys with the tied lambda and no `output_dir` or `input`, the submit dialog's default of 1, its reason, the warning when raised and the per-draft table line. **Not verified:** a real Slurm (`sbatch` queue behaviour, `squeue` after purge), a ROHSA sweep on the real cluster or with the owner's real configs, a design review or an approved mock of the new screens, browser walk-through beyond tests.

## Rollback / Migration
Leave `Sweeps` unset in `main` to drop the routes, scheduler and labels; drafts already made stay ordinary jobs. The two tables can stay unread. Restoring the backup made before the migration removes them.
