# ADR 0068: Tool profiles: pipelines as declared data, not built-in cases

- Status: proposed, awaiting owner review; implemented so far: slice 0 (template drift), slice 1 (relative-orientation presets, the CNM cut by its physics), slice 2 (orientation conventions), slice 3 (run detection and generic output roles), slice 4 (the decomposition record) and slice 5 (run templates)
- Date: 2026-11-13
- Related: ADR 0014 and 0018 (VGT products and header cards), 0042 (declared angle frame and quantity), 0046 (ROHSA runs and Gaussian components), 0047 (relative orientation), 0054 (strict rerun pins the commit), 0058 (import rules), 0067 (Planck maps declared without a pipeline)

## Context
Vesqira supports VGT and ROHSA by name: hard-coded header cards, run-record files, folder layouts, config keys, job templates and analysis defaults. The owner's direction (2026-11-13): Vesqira gives astronomers tools, not one group's pipeline. It must stay compatible with the open-source versions of the tools it knows, and other tools should plug in without changes to Vesqira's code. The point is to make routine work (registering outputs, aligning maps, comparing orientations, reviewing fits) quick and low effort for anyone, whichever code produced the data.

An audit of the code against the public repositories (2026-11-13) found:
- **VGT.** The only public implementation found is ISM-NU/VGT.jl (MIT). `PSIFRAME`, `PSIANGLE`, `VGTPROD`, the `VGT*`/`INB*` cards and `run_metadata.toml` are its conventions. They are public and documented, but they are one repository's choice, not a field standard. The fork Vesqira was first built against is private.
- **ROHSA.** Upstream (antoinemarchal/ROHSA) writes only the `.dat` rows (`# i, j, A, mean, sigma`, i and j 0-based, mean 1-based in channels, sigma in channels, no units) and its namelist. Vesqira's reader matches it. The run trace TOMLs, `parameters_n<N>.txt`, the `rohsa/<label>/{maps,cubes}` tree and the crop FITS come from the group's wrapper ISM-NU/ROHSA-LMC. What ADR 0046 calls "the pipeline" is mostly ROHSA-LMC.
- **Drift.** The VGT job form offered `noise_mode = separable_shrinkage`, which VGT.jl has rejected since 0.1.0, and could not set `angle_frame` or `output_bin`. The ROHSA form called its repository field "VGT folder on the host", although the entry point `rohsa/cli/preprocess.jl` is in ROHSA-LMC. Both are fixed in slice 0.
- **Owner-script defaults in user-visible text.** The relative-orientation defaults (P/σ_P ≥ 3, 2000 bootstraps, 1° floor, 10 arcmin disk) and line citations of `vgt_phase_vs_stars.py` and `star_vgt_scale_analysis.py` appear in results that other researchers cannot open. The 2.03 km/s CNM width cut is a built-in default.
- **Inventions.** Vesqira reads a `[metrics]` table that VGT.jl never writes. It falls back to "pixel frame, radians, field orientation" when a VGT product has no `PSIFRAME`, which states as known a convention nobody declared.
- **Already general.** The orientation declaration (`catalog.Interpretation`), import rules (ADR 0058), unit and WCS corrections, masks, relative-orientation statistics, point catalogs and the generic run records (`provenance.json`, `run.json`, `params`/`metrics.json`, MLflow) need no VGT or ROHSA. A Planck map already enters this way (ADR 0067).

## Decision
A tool Vesqira knows is described by a **profile**: a versioned data file that Vesqira's own code interprets. VGT.jl, ROHSA (the `.dat`) and ROHSA-LMC (runs and products) become the first three profiles, shipped in the repository. A researcher can add one for another tool in a project's `.vesqira/profiles/`, at the trust level of an import rule. Everything a profile supplies is labelled as declared by `profile:<name>@<version>`, never as verified.

A profile never runs code on the Vesqira server or the desktop. Rendering a job script, reading files and validating values stay in Go and in the worker, using the existing validators. This keeps AGENTS.md's rule against untrusted in-process plugins in v0.1.

### What a profile can declare
1. **Detection and output roles.** How to recognise a run of the tool by content (a file plus a key inside it, not by name alone), and which outputs fill which generic role. Roles: orientation map, reliability, support, component table, component maps, model cube, residual cube, crop. Contracts and the UI name roles, and the tool's name is only a label. The `vgt_*` and `rohsa_fit` roles and the `vgtHeader` field generalise with a compatibility note.
2. **Orientation conventions.** A table from header cards to the fields of the orientation declaration: quantity, axial or vector statistics, unit, zero direction, sense, and frame (pixel, or a named sky frame). Today's `PSIFRAME` handling becomes the VGT.jl entry in that table. A product the profile cannot place gets "unresolved", never an assumed default.
3. **Decompositions.** A format-neutral record of per-pixel components: amplitude (in the grid's unit), centre (unit, index base, spectral frame), width (sigma, FWHM or dispersion, and unit), the component order, and the source. The source can be a text table such as ROHSA's `.dat`, or one FITS map per parameter, as GaussPy+ and scousepy produce. The components panel, the sigma-v diagram, the width-class maps and the crop linking read this record, not ROHSA. The 1-based mean becomes a field of the ROHSA profile. The derived quantities (Doppler temperature, a CNM cut) stay optional, labelled and outside the contract.
4. **Run templates.** The repository URL and a pinned commit (strict rerun already checks it, ADR 0054), the entry command, any preparation lines shown to the researcher, the editable config keys with types and ranges (replacing `configKeys` and `rohsaKeys`), a progress pattern, resource defaults and the environment probes. The rendered script stays exactly what is submitted, and is shown before submission.
5. **Analysis presets.** Named sets of defaults with a plain description, for example "LMC star comparison (VGT phase scripts)" holding today's relative-orientation defaults and the 2.03 km/s cut. The neutral default for everyone is stated in the result. Results stop citing file paths and line numbers the reader cannot open.

### Order of work
Each slice is shippable alone, and the order follows how much routine friction it removes for a researcher who does not use VGT or ROHSA:
0. Fix the template drift (VGT.jl config keys, the ROHSA-LMC label). Small; in progress with this ADR.
1. Analysis presets (item 5). Small to medium. **Implemented** (see below).
2. Orientation-convention profile (item 2), the "unresolved" fallback, and one copy of the card table (`fits_header.py` and `analysis.py` each have one). Medium. **Implemented 2026-11-13**, see "Slice 2" below.
3. Detection and output roles (item 1). Large; contract renames get a compatibility period. **Implemented 2026-11-13**, see "Slice 3" below.
4. Decomposition record (item 3) with a ROHSA profile and a FITS-maps source. Large. **Implemented 2026-11-13**, see "Slice 4" below.
5. Run templates as data (item 4). Medium to large. **Implemented 2026-11-13**, see "Slice 5" below.

### Slice 1: what was done and what was not
- Done: relative-orientation presets (`relorient_presets.json`, `standard` and `lmc-star-comparison`, one reason per value), `preset` on the request and in the result and derived record, a route that lists them, a form that fills its fields from the chosen preset, and results that no longer cite script files or line numbers (ADR 0047 amendment).
- Done: the ROHSA CNM cut is shown as a Doppler temperature bound (T_D below 500 K gives σ below 2.03 km/s) and can be set as T_D or as σ. The starting width stays 2.03 km/s.
- Constant check: T_D = m_H σ² / k_B worked from m_H = 1.6735e-27 kg and k_B = 1.380649e-23 J/K is 121.2 K per (km/s)²; the code and every shipped result use 121.1 (0.1% lower; the proton mass gives 121.15). Vesqira now uses 121.2 (same as T = 21.86 ΔV²_FWHM). T_D is computed per reply and never stored, so only the displayed T_D moves, by 0.1%. At 500 K the width is 2.0311 km/s, still 2.03 to two decimals, so the default cut, classifications and class maps are unchanged. ROHSA-LMC's own `DOPPLER_TEMPERATURE_FACTOR` (src/rohsa.jl:2) is still 121.1.
- Not done, by design: presets are not yet a profile file a researcher can add under `.vesqira/profiles/`; the file is shipped with the worker. The ROHSA class-map default edge and the Gaussian review still take the width cut from the components browser. The `vgt_*` role names and the VGT/ROHSA header and run code are untouched (slices 2 to 5).
- One deviation from the sketch above: the preset file sits flat in the worker folder (`relorient_presets.json`) because `DEPLOY` accepts plain file names only.

## Alternatives
- **Keep built-in cases and add more tools the same way.** Every new tool would need a Vesqira release, and each one adds name checks to core code, which AGENTS.md forbids.
- **Executable plugins (Python or Go loaded at run time).** These are the most flexible, but they need a trust and isolation model that v0.1 does not have. Data profiles cover reading formats and rendering templates, which is what tools need from Vesqira.
- **A GitHub connector that reads a tool's repository and infers its formats.** Inference from code is unreliable, and wrong conventions are exactly the silent errors the scientific invariants forbid. A connector can later fetch a profile a tool's authors publish, and fetch the pinned commit for a template.
- **Generalise only the UI wording.** This is cheap, but a non-VGT tool would still not be readable.

## Consequences
- The VGT- and ROHSA-specific code moves behind three profiles, and the core gains roles, a decomposition reader and a convention table. The existing behaviour for VGT.jl and ROHSA-LMC users must stay identical, and their fixtures are the regression gate.
- Contracts change names (roles, `vgtHeader`, the `rohsa_runs` table to a general decompositions table). Old names are read for one release, the migration keeps every recorded run, and provenance records which profile version interpreted a file.
- A researcher-written profile is a declaration, like an import rule. A wrong profile gives wrong labels, not wrong data on disk, and the label says who declared it.

## Validation
- For VGT.jl and ROHSA-LMC, the current fixtures give the same results before and after each slice.
- At least one tool that is neither VGT nor ROHSA goes through each slice, with a fixture generated to its documented format: a HOG-style orientation map with its own cards for slice 2, and a FITS-maps decomposition for slice 4.
- A product without a declared convention shows "unresolved" in every place that showed the old default.

## Rollback/Migration
Each slice is separate. Until slice 3, profiles only add declarations and change no stored data. Slice 3 includes a schema migration that keeps old rows readable and records the profile used (slice 4 needs none: its record lives in the JSON of `rohsa_runs.info`), and each can be reverted by restoring the previous reader, because the files on disk are never changed.

## Slice 2: orientation conventions (implemented 2026-11-13)
- **The table.** `services/scientific-worker/orientation_profiles.json` (shipped through `DEPLOY`, so it reaches remote hosts and the RPM with the worker) holds one entry per tool: a name and version, the cards that detect it, the cards it writes to describe its own product, and for each of frame, quantity and unit the card and the values it places (a frame value also names the zero direction and the sense). The only entry is VGT.jl, from `vgt_product_header` and `ANGLE_FRAMES` of ISM-NU/VGT.jl at commit af0a794: `PSIFRAME` (`PIXEL`, `GALACTIC`, `ICRS`), `PSIANGLE` (`BFIELD`), `BUNIT` (`rad`; VGT.jl writes no other unit, so `deg` is not placed), statistics axial. The entry has an `applies` rule (`VGTPROD` is `psi`), so the reliability, support and fit_rbar2 products are not read as orientation maps. No card is invented. `orientation_profiles.py` is the one reader: `fits_header.py` reports `orientation` in the header report through it and keeps its `vgt` block (the cards as written) from the same producer-card list, and `analysis.py` drops a profile's producer cards from files it derives with the same list. The two private card tables are gone.
- **Unresolved.** A field the profile cannot place is `unresolved`: an absent card, a value it does not list, a `BUNIT` that is not an angle unit. Nothing is taken from the WCS or the values. The one convention the code used to supply is removed: when a VGT product had no `PSIFRAME`, the run import declared "pixel frame, radians, B-field" under `vgt-run-adapter`, and a header with `PSIFRAME` but no `BUNIT` got radians "by convention". A run import now declares a psi map only when the profile placed its frame and its unit; otherwise it declares nothing, the map displays, and the researcher declares it (ADR 0042). A reliability pairing the old fallback wrote with that declaration is not written either, since a declaration needs a unit. Analyses that need the frame or the quantity (relative orientation, a sky-frame carry) refuse and say that the convention must be declared first, which the worker already did for a missing declaration.
- **Labels.** A declaration read from a header through a profile is authored `profile:<name>@<version>` (for example `profile:VGT.jl@1`), tier `declared` with the profile version as mapping version, and shown as declared by the file's header, never verified. Rows written before this change keep the author `vgt-file-header`, which is read as the same thing. The `vgtHeader` contract field gains `profile`, `unresolved` and, on `orientation`, `profile`, `zeroDirection`, `sense` and `cards`; the basis value `convention` is gone. The field keeps its VGT name until slice 3 renames it.
- **Stored headers.** A header stored before this change has the cards but no `orientation` reading. At start, in local mode, the API re-reads such headers (`RefreshProfileHeaders`) when the file's size and modification time are what was recorded; a changed or missing file keeps its stored header, which is shown as unresolved with the reason ("register the file again"). Stored `vgt-run-adapter` declarations are left as they are, shown as an earlier assumption the researcher may replace.
- **Validation.** Worker tests read every VGT.jl fixture through the table and check the frame, sky frame, quantity and unit against VGT.jl's documented cards; they cover a missing `PSIFRAME`, an unknown one and a missing `BUNIT`. A HOG-style map with cards of its own (`HOGFRAME`, `HOGANGLE`, `HOGUNIT`, defined by the test, not a public tool's convention) goes through the same reader with a test-only profile. Go tests cover the profile reading, the labels and tiers, a run import with and without a placed header, and the conflict sentences. The existing VGT.jl fixtures give the same declarations as before.
- **Not yet.** Profiles in a project's `.vesqira/profiles/`, a second shipped entry (none is shipped for a tool whose header convention is not public and documented), `proposedPsi` and the contract names (slice 3). The brightness-unit question already excludes a run's psi and reliability outputs (`Server.noBrightness`, by the run's recorded output role), so an unresolved orientation map is not asked for a brightness unit; slice 3 replaces the role check with generic roles.

## Slice 3: run detection and generic output roles (implemented 2026-11-13)
- **Detection is data.** `services/api/internal/runs/run_profiles.json` (embedded with `go:embed`) holds one entry per tool: the record file (an exact name or a pattern), the keys inside it that make it that tool's (`anyKey`, dotted keys allowed), the closed reader that parses it, and the names its outputs have. VGT.jl@1, ROHSA@1 (a `.dat` beside nothing else) and ROHSA-LMC@1 (the run trace plus the `rohsa/<label>` tree) are the three entries. The scan, the import preview, the run import and the ROHSA import look runs up through the registry (`runs.Registry`); the per-tool Go branches in `discover` and `server` are gone. A profile never runs code: the readers are Go code Vesqira ships (`run_metadata` and `rohsa_trace`), and the existing parsers keep their validation. A record that is valid TOML but holds none of a profile's keys is not that tool's run, so the next candidate is tried; an unreadable record is claimed so the reader can say why it cannot read it. What a profile supplies is labelled `profile:<name>@<version>` and is never shown as verified.
- **Where profiles live.** In Go, next to the code that reads them, not beside the worker's `orientation_profiles.json`. `go:embed` cannot reach the worker folder, and the worker's `DEPLOY` manifest takes flat file names only (`make docs` checks it), so a shared file would mean a copy step for a file the worker does not need. The two files meet by name: a run profile's `orientation` field names the worker profile that reads its header cards, and a Go test (`TestEveryOrientationNameIsAProfileOfTheWorker`) fails when a name@version is missing there. Consolidating both into one file is a later step (with the project-level `.vesqira/profiles/` folder, slice 4 or after); it is a move of data, not a change of meaning.
- **Roles.** Eight generic ids, snake_case: `orientation`, `reliability`, `support`, `component_table`, `component_maps`, `model_cube`, `residual_cube`, `crop`. The tool's own name for an output is kept in the new `run_outputs.product` column, so nothing a researcher saw is lost. An output a tool names that fits no generic role is a declared extra: a role id plus an `extra` label in the profile, or, for the many ROHSA maps, no role at all and its own product name.

  | Old role (kind) | New role | Product kept |
  |---|---|---|
  | `psi` (vgt) | `orientation` | `psi` |
  | `reliability` (vgt) | `reliability` | `reliability` |
  | `support` (vgt) | `support` | `support` |
  | `fit_rbar2` (vgt) | `fit_rbar2` (declared extra, label "Fit R̄²") | `fit_rbar2` |
  | `component_g<k>_<name>` (rohsa) | `component_maps` | the old name |
  | `cube_model` (rohsa) | `model_cube` | `cube_model` |
  | any other ROHSA map or cube (`model_*`, `residual_*`, `cube_*`) | unchanged (an extra under its own name) | the old name |
  | any other kind | unchanged | the old role |

  `fit_rbar2` stays an extra: this repository does not document what it measures, and folding it into `reliability` would exclude it from brightness units the way a reliability map is excluded, on a guess. The `.dat` (`component_table`) and the crop (`crop`, a run's input) are roles a profile declares for files beside the run; they are not dataset rows, so `run_outputs` has no row for them. `residual_cube` is in the vocabulary but no shipped profile maps to it: ROHSA-LMC's residual cube file name is not confirmed, and a guessed pattern would mislabel files.
- **Schema 35.** `runs.profile` (text) and `run_outputs.product` (text, now part of the primary key with `run_id`). The migration (`schema.toolProfiles`) rewrites `run_outputs.role` through a fixed table of the mapping above (`schema.LegacyRunOutputRole`, in code, so it does not depend on the live profile file), sets `product` to the old role, and sets `profile` to `legacy` on every existing run. It tolerates a catalog with no run tables and can run twice. Files on disk and dataset links are untouched. A run that was recorded before profiles is not back-stamped `VGT.jl@1`: that would claim a reading nobody did, so it says `legacy` and the run page says "recorded before profiles". Re-importing a run records the profile that read it.
- **Behaviour that changed.** (1) A `run_metadata.toml` or ROHSA trace with none of the profile's keys is no longer taken for a run. (2) `outputs[].role` in the run JSON is the generic role; the old name is in `outputs[].product`. (3) The import preview's built-in roles for run files are `run_<role>` (`run_orientation`, `run_component_table`, `run_component_maps`, `run_product` for a tree map the profile does not place, and so on), replacing `vgt_psi`, `vgt_reliability`, `vgt_support`, `vgt_fit_rbar2`, `rohsa_fit` and `rohsa_product`. The prefix keeps them apart from a researcher's own `orientation` rule role. Run `kind` ("vgt", "rohsa") and the scan's `recordKind` keep their values, because rerun and job code key on them; a `profile` field sits beside them, and a tool with only a profile gets its profile's `kind`.
- **Brightness.** `Server.noBrightness` asks for the generic roles `orientation` and `reliability`, so any tool's orientation or reliability output is excluded from brightness units, with no tool name in the check.
- **Compatibility period.** The dataset JSON carries `orientationHeader` (the generalised `vgtHeader`, same schema, renamed `OrientationHeader`) and the old `vgtHeader` with the same value. `vgtHeader` is marked deprecated in the contract and is removed in schema 36; the web reads `orientationHeader ?? vgtHeader`. `outputs[].role` changed meaning without a rename, so there is no old field to keep: the web accepts the old ids (`psi`) as well as `orientation` for rows an older server returns. Frozen JSON written earlier (figure provenance, reports, pushed items, stored scan rows) is not rewritten and keeps the old ids; nothing in the web displays those role strings.
- **Validation.** A clearly synthetic profile, HOG-synthetic@1 (`services/api/internal/runs/testdata/synthetic_hog_profile.json`, test only, never shipped), and a fixture (`write_hog_run` in `fixtures/generate.py`, folder `hog_run_demo`, with its own `[hog]` key and `hog_run.toml`) go through the scan and the run import: the tool is detected and its three outputs get `orientation`, `reliability` and `support` from data alone, the import declares no interpretation (the profile declares none), the brightness unit endpoint refuses its orientation and reliability outputs, and a server with only the shipped profiles does not take the folder for a run. Other tests cover the profile loader (unknown readers, roles, fields and patterns are refused, a shipped profile cannot be redefined), detection by content, the migration (every row and dataset link kept, the old name in `product`), and both header names in the dataset JSON. HOG is a method, not a file format; the invented record layout proves the mechanism and is not a claim about any real tool.
- **Not done.** Project-level `.vesqira/profiles/` and a profile a researcher can add without a rebuild (the registry already takes extra data through `With`, which is what the tests use); the decomposition record (slice 4); run templates (slice 5); removing `vgtHeader` (schema 36); a read-side normaliser for the old ids in frozen JSON; a content check on the ROHSA `.dat` at detection (the file can be tens of GB; its layout is verified when the index is built); a `residual_cube` mapping.

## Slice 4: the decomposition record (implemented 2026-11-13)

- **The record.** A profile's `decomposition` section declares where a tool writes per-pixel Gaussian components and what each field means. Fields: amplitude (a unit, or `grid` for the crop's brightness unit), centre (unit, index base 0 or 1 for channels, spectral frame), width (`sigma`, `fwhm` or `dispersion`, and a unit), the component order (text) and the source. The source is a `table` (columns, column count, pixel base) or `fits_maps` (HDU per parameter, and either one cube per parameter with a component axis, or one 2D map per component). The reading is the worker's (`decomp.py`); Go validates the same declaration with unknown fields refused (`runs/decomposition.go`), and the worker validates it again, because it is the one that reads the data. A field the profile does not state is unresolved. Nothing supplies a unit, an index base or a width convention by default.
- **Unresolved is shown, not computed.** With the unit, base, frame or width convention missing, or a centre frame that is not the cube's `SPECSYS`, the components reply says `drawn: false` with the sentence, and the panel lists the values as the source states them (`centre_raw`, `width_raw`) and draws and classifies nothing. The amplitude is still listed, because it needed none of the missing facts. A FWHM is divided by 2 sqrt(2 ln 2) in one place and the record says so (`to_sigma`); `dispersion` is read as the standard deviation, as sigma.
- **Units.** The amplitude's unit is the amplitude map's `BUNIT` when it has one (it wins over a declared one, with a note), else the declared unit. A centre or width map's `BUNIT` is used the same way unless the centre is declared in channels. Data and residual are drawn over the components only when the amplitude unit equals the crop's.
- **Absent slots.** A NaN in any parameter of a slot means the tool did not fit it at that pixel. It is not a component and not a zero: the table says "not fitted at this pixel", and the diagram and class maps count it apart (`not_fitted`) from components with a width that is not positive (`invalid_sigma`).
- **ROHSA@1** now declares its `.dat` reading as data: columns 0 to 4 (row, column, amplitude, mean, sigma), five columns, pixel indices from 0, amplitude in the grid's unit, centre in channels counted from 1, width a sigma in channels. ROHSA-LMC reads its components as ROHSA's (`components` link). The worker keeps the same reading as its default for a request that carries no declaration, and a test (`test_decomp.Declaration`) fails if the shipped profile and the worker's default differ. The API now always sends the run's declaration, so the ROHSA numbers are produced through it: the existing ROHSA worker tests and e2e specs pass unchanged, and `test_decomp` compares the same values to closed form. A run stored before this slice has no record and is read as the ROHSA profile.
- **Where it is stored.** `RohsaInfo.Decomposition` (`profile` label, and for maps the file names) in the existing `rohsa_runs.info` JSON, so there is no migration and no schema 36 for this slice. The declaration is looked up from the profile at each request and never copied into the row; a run whose profile this server has not loaded is refused with the profile's name. For maps, `rohsa_runs.dat_path` holds the run's folder. The cache key of a maps run folds the name, size and modification time of every map file, so a changed map never serves old pixels.
- **Bounds.** A `.dat` is still read through the index (a bounded slice per call). FITS maps are read per pixel for the components panel and in tiles of at most 2^21 values per parameter for the review, through the worker's single safe-open path; headers (axes, shape, the sky grid against the cube's) are checked before any allocation, the map files must stay inside the run's folder after links are resolved and are authorized one by one, at most 192 map files and 64 components per pixel. No map goes to the browser whole.
- **Import.** A profile with a `fits_maps` source needs a record and the key that names the cube the fit was made on (`crop`); it may name the key holding the component count (`components`), and a layout with one map per component counts its files instead. File names are matched in the run's folder (an exact name, or a pattern with one group that captures the component number from 1, with no gap), so no path from the author's machine is used. The import is local only: a fit written as maps on a host is refused with a sentence.
- **Compatibility.** Old field names stay. The components reply keeps `amp`, `mean_channel_file`, `mean_channel`, `sigma_channel`, `centre`, `sigma`, `fwhm`, `t_doppler_k`, `valid` and `conventions`; `amp`, `mean_channel`, `mean_channel_file` and `sigma_channel` can now be null (a slot not fitted, a centre that cannot be placed), and `present`, `centre_raw`, `width_raw`, `drawn`, `not_drawn_reason` and `record` are added. `mean_channel_file` is null when the centre is not a channel number. `rohsaRuns`, the index and the review routes keep their names and request bodies, so a client written for ROHSA reads a ROHSA run the same way. The old names stay while the web reads the new fields; none is scheduled for removal in this slice.
- **Derived quantities** (T_D = 121.2 K (km/s)^-2 x sigma^2, the CNM cut at 2.03 km/s) stay optional, labelled and outside the record: they are computed from the resolved sigma when there is one, and the panel's note says they are derived.
- **Validation.** `fixtures/generate.py write_synth_decomp_run` writes a clearly synthetic tool, "synth-decomp" (7 x 5 pixels, 36 channels, three slots, the third not fitted where (x + y) % 4 == 0): amplitude in K and centre in m/s from `BUNIT`, a FWHM in km/s whose map has no `BUNIT` (so the profile declares the unit), as one cube per parameter and as one 2D map per component, plus a record that leaves the centre's frame undeclared. The test-only profiles `SynthDecomp-cubes@1`, `SynthDecomp-maps@1` and `SynthDecomp-noframe@1` (`runs/testdata/synthetic_maps_profile.json`, loaded by tests through `runstest.WithSyntheticMaps` and by the e2e API through `--run-profiles`) declare them. The expected values are the closed form `decomp_truth` and plain loops over it, never the reader: components of a pixel, the sigma-v cells and counts (`count` and `integrated` weights), the width-class maps (half-open at the cut), the pixels behind a cell, both layouts giving the same numbers, and the not-fitted count, in `test_decomp.py` (worker) and `server/decomposition_test.go` (import, index, components, diagram and class maps through the HTTP routes). Negative cases: a missing frame, wrong frame, missing width convention, missing channel base, wrong component axis, a map on another sky grid, a file outside the run's folder, unknown fields in a declaration, a run whose profile is not loaded. An e2e spec with axe and screenshots at 1440x900, 1280x800 and 390x844, light and dark, covers the maps run and the unresolved run in the browser.
- **GaussPy+ and scousepy.** No entry is shipped. This repository holds no verified description of their output layout, and a guessed one would mislabel files, so they stay out until a layout is checked against the tool's own documentation and cited here. The synthetic profile is not a claim about any real tool.
- **`--run-profiles`.** A developer hook on the API: a JSON file of extra profiles added to the shipped ones (a profile that redefines a shipped one is refused). The acceptance tests use it; project-level `.vesqira/profiles/` loading is not part of this slice.
- **Not done.** A host's worker does not read maps (the fit must be on this computer); the `.cells` pixel index of a diagram cell is still a `.dat` feature, so a cell click on a maps run reads the maps again; project-level profiles; run templates (slice 5); HDU names are accepted in a declaration but only HDU numbers are exercised by the tests; an HDU that holds the component axis in a different FITS axis than the declared one is refused, not reordered.

## Slice 5: run templates as data (implemented 2026-11-13)

- **What a template declares.** A profile's `template` section (`runs/run_profiles.json`, compiled by `internal/jobtemplate`): an id (what `jobs.template` holds), a title and the tool's plain name; the repository URL and the pinned commit, with the form's words for the folder and a one-line note of what was checked against that commit; the config (the variable the script keeps it in, the key that names the input cube, how a changed key is written, whether a job must start from a config, a guard that refuses editing a config whose tool runs its own sweep); the editable keys, each with a kind (`number`, `int`, `posint`, `enum`, `bool`, `path`), a section, a range, a label and a plain description from the tool's own documentation, and an optional default with a one-line reason; ties (one setting standing for several keys moved together); the preparation steps; the one command; a progress reader or pattern; the resource defaults with a reason; the probes for the environment record; and a named sizing table. VGT.jl@1 and ROHSA-LMC@1 carry the templates that used to be `configKeys`, `rohsaKeys` and two render functions.
- **A profile never runs code and never injects text.** Rendering, quoting and validating stay in Go (`jobs.RenderTemplate`, `SetConfig`). The template reaches the script only through closed vocabularies: eight step kinds (`export`, `set`, `announce`, `require`, `modules`, `build_if_stale`, `comment`, `ulimit`), six key kinds, four placeholders (`{{repo}}`, `{{cpus}}`, `{{config}}`, `{{var:name}}`) and one probe. The command must start with `srun` and is a list of words, each double-quoted when it carries a placeholder. Every profile string that can reach a script or a config is checked against the character set its place allows when the profile is loaded (no quote, `$`, backtick, backslash or newline, and no `..` in a literal or a path), so there is no free shell text and no profile-defined regular expression of values. Exports of `PATH`, `LD_PRELOAD`, `BASH_ENV` and similar are refused. The profile file is read with unknown fields refused. The repository must be an `https://` address and the commit a full 40-character SHA. A progress pattern must compile in Go's linear-time engine and name the groups `done` and `total`. A default must satisfy its own key. A typed value is checked against its kind and range and then written in a fixed form, so `n_bins = 32; touch x` cannot become a line. The rendered script is what is stored, shown and submitted, as before.
- **The pinned commit is a choice, not a default.** `ExpectCommit` (ADR 0054) makes the job stop before the program starts unless the code folder is at that revision with no changed tracked file. Putting it on every script would make every job on a newer checkout fail, so the template's commit is applied only when the request says `pinProfileCommit` (a checkbox in the form, off by default). The script words it as a pinned commit (`Settings.PinProfile`), never as a strict rerun, and the request records `pinProfile`. A strict rerun keeps the base run's commit in `ExpectCommit`, which is the stronger claim and wins when both apply. Sweeps, reruns and relay requests carry it by the rules in the follow-up section below.
- **Byte-identical output, proven.** Before any change, `jobs/golden_test.go` and 86 files in `jobs/testdata/golden/` were generated from the old code (commit 5008298): VGT and ROHSA config edits, scripts with and without partition, account, `ExpectCommit` and `HashInput`, the refusals (injection, ranges, the guard table, non-table configs) and the setting checks. `golden_test.go` is unchanged since; the rendering and editing now come from the templates and every file is byte-identical except `setting-checks.golden`, three lines of which changed: the kind names printed for `n_gauss`, `memory_gb` and `spectral_kernel` (`intlist`, `gb`, `kernel`) became the generic kinds (`int`, `number`, `enum`). Nothing a request can do changed with them. The environment preamble's Julia probes are left out of a script whose template declares none, and the facts are recorded as unresolved with that reason; VGT and ROHSA declare `julia`, so theirs are the same bytes.
- **A tool that is neither VGT nor ROHSA.** `runs/testdata/synthetic_tool_profile.json` declares `SynthFit@1` (test only, never shipped): an int with a range 2 to 64, a number with a range, an enum, a bool, a path, the output folder, four steps, a command, a progress pattern. `runstest.WithSyntheticTool` loads it on top of the shipped registry, the way `--run-profiles` does. `server/synthtool_test.go` lists it from `GET /api/job-templates`, makes a draft through `POST /api/jobs`, refuses out-of-range, non-numeric, injected, unknown-key, output-folder and non-plain-folder requests with 422, accepts the two range ends, applies the opt-in pin, submits it on the fake Slurm path and checks that the host received exactly the reviewed script, and reads progress with the profile's pattern. `runs/template_profiles_test.go` loads 31 hostile variants of a valid profile and requires each to be refused.
- **Contracts.** `GET /api/job-templates` (`job.read`) returns each template with its profile label. `POST /api/jobs` takes `template` (`custom` or any listed id) and a `tool` body, the same for every tool (`repoDir`, `configPath`, `configText`, `set`, `cpus`, `mem`, `time`, `partition`, `account`, `pinProfileCommit`). The older `vgt` and `rohsa` bodies are read when `tool` is absent, so existing clients keep working; they are not scheduled for removal in this slice. `POST /api/jobs` is now described in `bodies.json` and leaves `undescribed.txt`. The stored request carries the profile label (`profile`, name@version). `Job.template` stays the template id, so no schema change and no migration: schema stays 35. `RenderVGT`, `RenderROHSA`, `SetConfigValues`, `SetROHSAConfig` and the other old function names remain as thin wrappers.
- **The job form** (`apps/web/src/jobs/NewJob.tsx`) is drawn from `GET /api/job-templates`: the Kind list, the folder and config labels, one field per editable key with its label, its description and its range or default, a choice list for a bool or a closed enum, the pinned commit and its checkbox, the starting request and why, and a plain list of what the script does before the command. The sizing hint appears only for a template that names the sizing table. Only the settings the person changed are sent; before this slice the VGT form sent every non-empty field, which rewrote lines the person had not touched. Settings are applied in sorted key order, so one request renders one text. The rerun and sweep forms were drawn from static tables at first; the follow-up section below replaces them.
- **Progress.** A template with a progress pattern is read by it (`vgtlog.ParsePattern`: the last line that matches with sane counts, no estimate otherwise); a template with none is read as before, by VGT.jl's "Done chunk" blocks.
- **Project-level profiles (not built).** A project's `.vesqira/profiles/` file would go through `runs.Registry.With`, the same call `--run-profiles` uses: `LoadProfiles` decodes with unknown fields refused and `Template.Compile` applies every check above, so a project file is held to the same limits as a shipped one. What remains to decide first: where the file is trusted from (it is a repository file anyone with write access can change), whether a job script from a project profile needs a confirmation the shipped ones do not, and how its label shows in the script header.
- **Not done.** No run on a real cluster: the scripts were rendered and submitted on the fake Slurm path only, and the VGT.jl and ROHSA-LMC templates were checked against the repositories at the commits named in each template, not run. Sweeps, relay requests and "run again with..." work for `vgt` and `rohsa` jobs only. Results are imported automatically for those two only. A template cannot declare a command that does not start with `srun`, a config that is not TOML, or a second config file. The one sizing table (ROHSA's crop table) is named, not declared.

## Slice 5 follow-up: the pin through sweeps, reruns and relays; forms and relay checks from the template; VGT on the generic builder (implemented 2026-11-13)

- **The pin is inherited, and a choice can override it.** A draft made from a job copies the job's `pinProfile` (a sweep from its base job, a rerun form from the parent job, a relayed run request's draft from its base run's job). A sweep's request body may say `pinProfileCommit` true or false to change it for every draft; absent keeps what the base did. The rerun form shows a checkbox that starts from the parent's choice. When a draft also repeats a run strictly (or a relay names the run's commit), that commit is the one the script insists on, worded as a strict rerun, and the profile's commit is reported as also asked for and not used. The stored request records both `pinProfile` and `expectCommit`.
- **Every approval view says which commit and why.** A `codePin` object (`commit`, `basis` of `run`, `profile` or empty, and a sentence) is returned by the rerun check, a sweep's review and the relayed request's approval text, from one function (`codePinOf`). The reviewed script carries the same commit in its header lines, as before. A pin the sweep itself chose is not counted as an unexpected difference in each draft.
- **VGT drafts use the generic builder.** `buildVGT` and `buildROHSA` are gone; `buildTool` (through `buildJob`) makes every draft. The one behaviour that differed was `output_dir`: `buildVGT` overwrote a requested `output_dir` without saying so, while the generic builder refused it. The decision is to refuse, with the sentence "output_dir is set by Vesqira", because a job's output folder is how a run is told apart from the next and a silent overwrite hid a request that was never honoured. The forms never offered the key, so no screen sends it. Settings stored by an earlier version may hold an `output_dir` the job never used; `jobs.CarriedSet` drops it when a sweep, rerun or relay draft copies the stored settings, so those still work and the key is not recorded again. The `vgt` and `rohsa` request bodies are still read.
- **Goldens.** `server/draftgolden_test.go` with `testdata/golden-drafts/` holds the scripts of a new VGT job (with and without the pin), a new ROHSA job, a VGT sweep over two settings, a ROHSA sweep over the tied lambda and `n_gauss`, and a configuration repeated on another cube for both tools. They were written from the code before this change and pass unchanged: the drafts are byte for byte the same. `server/pincarry_test.go` covers the pin through sweeps, strict reruns, relayed drafts and the `output_dir` refusal.
- **Forms from the template.** The sweep form and the rerun form take their settings from `GET /api/job-templates`: label, description, range and documented default, a choice list for a bool or a closed enum, and for a sweep the template's ties first. `rohsaSettings.ts` and the static `SETTINGS` table are removed. A sweep row starts on the template's `sweepKey` (an optional field naming one declared key that is neither the output folder nor a path; VGT declares `dn`, ROHSA `n_gauss`, as the static forms did), else on the first setting that is not a tie. The rerun form sends the generic `tool` body.
- **Relay checks from the template.** `relay.CheckRequest` and the settable keys use the template's keys: a key is settable if the template declares it and Vesqira does not fix it (the output folder), and overlapping keys (a tie and its members) are refused together by the template's own ties. The hardening tests, including the injection sweep, are unchanged and pass.
- **Field text.** A key's description now ends with the documented default and the profile's reason for it ("the tool's documented default is 20, the value in VGT.jl's config.example.toml at af0a794"). `Input` and `Select` add a caller's `aria-describedby` to their own description instead of replacing it, so the rerun form's "was" note and the template description are both read with the field.
- **Validation.** `e2e/tests/rerun-sweep-forms.spec.ts` makes a VGT job, finishes it on the stand-in Slurm, imports it as a run, then uses the rerun form and the sweep form: fields and their order come from `GET /api/job-templates`, the description carries the default and its reason, a binning of 0 is refused with "output_bin must be a whole number, 1 or more" in both forms, the keyboard reaches the controls in order, and the code-commit line shows in the rerun check and the sweep review. Axe and screenshots at 1440x900 and 390x844, light and dark. The spec found a real fault: the rerun form read an empty `settings` object as the ROHSA record and showed no starting values for a VGT run; it now decides from the template's config mode.
- **Not done.** No run on a real cluster. A relayed request, a sweep or a rerun still works only for templates that ship with this server; a project-level profile is not built.
