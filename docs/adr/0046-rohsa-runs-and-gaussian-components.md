# ADR 0046: ROHSA decomposition runs and the Gaussian components in the spectrum view

Status: **proposed; implemented, awaiting owner review.** Decided by the implementing agent under the owner's delegation of ADR decisions (roadmap Stage S). The new panel has had no design review and no owner approval.

## Context
The owner's supervisor wants to see a decomposition as curves ("if it's a decomposition, she may want to see the resulting bell curves"), the raw outputs (data, model, residual and component maps) before derived numbers, and CNM against the rest: the ROHSA side trusts only a two-phase "CNM and others" split. Vesqira's run model (ADR 0014) knew one kind, `vgt`.

A ROHSA result is, on the owner's machine: `<region>/rohsa_n<N>.dat` (or `rohsa_<candidate>.dat`), plain text with a comment header and rows `i j amp mean sigma`, one row per (pixel, Gaussian), up to tens of GB; the Fortran namelist `parameters_n<N>.txt`; `rohsa_n<N>_run_trace.toml` and `_products_trace.toml`; the crop `<region>.fits` the fit used; and a product tree `<region>/rohsa/<label>/{maps,cubes}`.

The row conventions were read from the pipeline's reader (`read_rohsa_parameters`, `reconstruct_rohsa_components`) and **checked against its own product maps on a real 128 x 128 x 4 result** (not committed): column 1 is the zero-based row of the crop (FITS axis 2, "y"), column 2 the zero-based column (axis 1, "x"), the Gaussian index runs fastest; `mean` is 1-based in channels; `sigma` is in channels; the pipeline's `mu_kms` map equals the crop's spectral axis evaluated at `mean - 1` (to the map's float32 precision), and `sigma_kms = |dv| * sigma`.

## Decision
- **Run kind `rohsa`, same model.** `POST /api/runs/import` takes a `rohsa_*.dat`, or a folder holding exactly one (and no `run_metadata.toml`). The run's key is the `.dat`'s real path (several fits share a folder). Settings come from the namelist (source `parameters`; the machine's file names dropped), the trace's `[config]` (`config`) and its top-level scalars (`run_trace`), all declared by those files; the products trace's `[fit_metrics]` become declared metrics. No commit, time or environment is recorded because the records carry none: the reproducibility facts say unresolved. A path or user name never enters the run (the rule of ADR 0014). Files outside the source roots are never read.
- **The crop is an input, found by name, never guessed.** `<region>.fits` beside the `.dat`, where region is what the trace declares, else the folder's name (labelled "inferred from the folder's name"). If it is not there, the run imports with a note and no spectral calibration; no other FITS in the folder is tried. The crop is registered as a dataset and linked in the run's record (`rohsa_runs.info`), **not** in `run_outputs`, so the dataset is never reported as produced by the run. Whether the crop is the grid the `.dat` was fitted on is checked when the file is indexed: its row count must equal pixels x Gaussians.
- **Products are outputs.** Each `*.fits` under `rohsa/<label>/maps` is registered and linked with the product's name (the file name without `<label>_`) as its role; `cubes/` files get a `cube_` prefix. Units: the file's BUNIT always wins. A map without BUNIT gets a unit proposed from its name (`_kms` km/s, `_kkms` K km/s, `_cm2` cm^-2, `_k` K) as an ordinary declared unit whose author is `rohsa-run-adapter` (labelled, replaceable, never over a person's own). A map whose BUNIT contradicts its name keeps the file's value and gets a note ("The file says K; its name suggests km/s"). The real pipeline copies the crop's BUNIT onto every map (all 36 maps of the sample say `K`, including `*_kms` and `*_nhi_cm2`), so these notes are expected; that is an upstream pipeline defect, reported to the owner, not corrected here.
- **Worker: one streaming pass, then random reads.** The `.dat` is never loaded. `rohsa_index` verifies, in 32 MiB chunks, that the file is exactly the regular layout (every row is the (i, j, Gaussian) its position says, five finite columns, lines under 512 bytes, rows = nx x ny x N) and records the byte offset of the first row of every pixel: 8 bytes per pixel in a sidecar under the cache folder (`<data-dir>/cache/rohsa`), keyed by a hash of the real path, size and mtime, so a changed file is indexed again and nothing is written next to the data. The pass is **resumable**: each call works about 15 s, saves how far it got and reports `building` with the byte progress; the page calls again. This keeps every worker request inside its 30 s limit for any file size. At the 6.7 MB sample it takes 0.16 s (about 40 MB/s per core, so roughly 8 minutes for 20 GB, once). Any irregularity refuses the file with the count and the first lines (`refused`); nothing partial is served. `rohsa_pixel` reads one pixel with one seek and N short lines and re-checks every row's (i, j) against the pixel asked for.
- **Why not the FITS component maps?** They would be O(1) and need no index, but they are optional outputs, derived by the pipeline (the owner asked for raw outputs before derived numbers), carry the unit defect above, and depend on the pipeline's own channel conversion, which would then be trusted instead of checked. The `.dat` is the one file every fit has. The maps are still imported and browsable.
- **Conventions, applied in one tested place (`rohsa.py`).** `mean_channel = file mean - 1` (0-based index; a Gaussian at raw mean 11 sits at channel index 10). Centre and sigma in km/s come from the crop's spectral axis through astropy WCS (`all_pix2world`, fractional channels allowed), sigma through the uniform channel step; the axis must be a declared velocity axis with a resolved, uniform grid, else centres and widths stay in channels with the reason. The crop has no `CUNIT3` in the real data: the FITS default m/s is used and the unit status `inferred` is carried to the reply and shown. Model = sum of components `amp * exp(-(c - mean)^2 / (2 sigma^2))` evaluated on every channel; a component with `sigma` not positive and finite is listed as invalid and not drawn (no floor is invented; the pipeline's 1e-6 floor is not copied); an amplitude of 0 is a fitted value and is kept. FWHM = 2 sqrt(2 ln 2) sigma. T_D = 121.1 K (km/s)^-2 x sigma^2, the pipeline's constant (m_H sigma^2 / k_B for atomic hydrogen, thermal broadening only: an upper limit on the kinetic temperature); the reply states it.
- **Routes** (owner listener, local files only; a ROHSA file on a remote host is refused by the worker): `GET /api/datasets/{id}/rohsa` lists the runs whose components can be drawn over the dataset: the dataset is the run's crop, or exactly on its grid (`compat.Grids`: shape, axis types, units, reference values and pixels, steps, frame, all required and confirmed). A cube with the crop's axis lengths but another or unconfirmed grid is listed with the reason (409 on use); unrelated files list nothing. `POST .../rohsa/index` advances the index. `GET .../rohsa/components?run=&x=&y=` answers 409 until the index is ready, then a frame: JSON head (components, axis, conventions in words) and float64 axis, model and per-component curves.
- **Spectrum view.** When a run applies, the Spectrum section offers a "Gaussian components" switch (off by default; nothing is read before it is on). The data drawn with the curves is the pixel's own spectrum (a one-pixel region through the existing spectrum route), not the region mean above; the pixel is the pinned one, else the one under the pointer, else the last one. Plot: data, model (sum), each component, and a residual strip drawn as **data - model** with the sign stated in the panel (the pipeline's maps use model - data); a channel with no data has no residual. Data and residual are drawn only when the dataset's brightness unit and the crop's are both known and equal. A table lists amplitude (in the crop's unit), centre, sigma, FWHM and T_D. A **CNM width cut** input defaults to 2.03 km/s, said to be the pipeline's scan-script default and the person's to change; a component is CNM when sigma is strictly below the cut (the pipeline's `s < cut`), otherwise "others". Two groups only: no LNM/WNM label anywhere. Lines differ by dash and weight as well as colour (CNM dashed, others dotted, model heavy).
- **Schema 12**: table `rohsa_runs(run_id, dat_path, info)` (the run's decomposition record; the `.dat` path stays server-side).
- **Discovery**: a folder with a `rohsa_*_run_trace.toml` is shown as a run of kind `rohsa` with the trace's settings, declared.

## Alternatives
Load or memory-map the `.dat` (20 GB of text; not mappable into numbers). A dense per-row index (8 bytes per row instead of per pixel; no gain once the layout is verified). A sparse checkpoint index (needs the same verification pass and a scan per lookup). Building the index in a goroutine (state to track across restarts; the resumable call is stateless). Treating the folder's other FITS as a crop candidate (a guess). Computing T_D from astropy constants (121.2 vs the pipeline's 121.1: the owner's CNM scan uses 121.1).

## Consequences
The first open of a very large fit costs one indexing pass (shown as progress). Only the layout ROHSA writes today is accepted; anything else is refused with a reason. A fit on this machine is read here; a fit on a host is read there (note "A fit on a host" below). A de-rotated run's crop carries its own (shifted) spectral axis; the note in the scan script about moving centres back to the original grid is not applied, and the curves are on the crop's axis.

## Validation
Worker tests on a generated, non-square crop (6 x 4 x 40, three Gaussians, reference pixel not 1, no CUNIT3): every pixel reads back its own row (x and y not swapped); a Gaussian at raw mean 11 peaks at channel index 10; centres, sigmas and the model equal an independent NumPy evaluation and the closed form of the FITS axis; a zero amplitude is kept; invalid sigma is flagged and not drawn; the index is chunked, resumable, reused and written only in the cache folder; a changed file is indexed again; malformed, out-of-order, short and wrong-N files are refused with line numbers. Go: import declares the settings and drops locations, links the products, never gives a declaration to a file that states a unit, notes a BUNIT that contradicts the name, keeps a person's declaration, imports without a crop with a note, refuses `rms_map.dat`; components routes require the grid and an index. Web: classification at the cut boundary, the cut input, the toggle, curves, table, residual sign, unit refusal, progress and refusal. Checked by hand on a real 128 x 128 fit (indexed in 0.16 s, pixel values equal the pipeline's component maps).

## Rollback / Migration
Drop `rohsa_runs` and the three routes; ROHSA runs then show as ordinary runs of kind `rohsa` without a decomposition record. Datasets are unaffected. The cache folder can be deleted at any time.

## Note: run again, editable settings and the sizing table (ADR 0048 follow-up)
Status: implemented, awaiting owner review. No new contract beyond the two routes and fields named here; schema unchanged (13). The new controls (the settings fields in "Run again with...", the new-job form and the sweep form for ROHSA, the sizing line) had no approved mock and no design review.
- **The template embeds the config.** `RenderROHSA` takes the config text and writes it to `$SLURM_SUBMIT_DIR/config.toml` with a heredoc, as `RenderVGT` does, then runs `preprocess.jl --config` on that copy. The script read is the config that runs. The old by-path form (the host's file, whatever it says at run time) is gone for new drafts; drafts already stored keep the script they have, and have no stored request (a sweep from one is refused with that reason).
- **Honest editing, not a rewrite.** `jobs.SetROHSAConfig` replaces only the lines of the settings that changed and keeps every other line byte for byte (comments, order, keys it does not know); a replaced line loses its own trailing comment. It then decodes the result again and refuses unless every changed key reads back as asked, so a layout a line editor cannot follow (a setting over several lines) is refused instead of mangled. The pipeline reads keys by name, not by table (`rohsa/configs.jl` flattens the tables and rejects unknown keys), so a key is replaced wherever the file has it outside `[auto_config]`, and a missing one is added to its usual table. `n_gauss` is written as a list of one (`[16]`), real values as reals (`30.0`). One request renders one text and one hash (keys applied in sorted order).
- **Whitelist** (chosen from the keys the owner's configs vary, `configs/rohsa/README`): `n_gauss`, the six `lambda_*` weights, `lb_sig`, `ub_sig`, `sig_init`, `lb_sig_init`, `ub_sig_init`, `maxiter`, `maxiter_init`, `noise` (true/false), `spectral_kernel` (`none`, `hanning`, `gauss<sigma>`), `crop_size`, `crop_x0`, `crop_y0`. Never `input` (a file of the host's) or `output_dir`, which Vesqira sets inside the host's source roots to a fresh folder per job, so a repeated run cannot write over an earlier one. A config with `[auto_config] enabled = true` (the pipeline's own candidate sweep) is not edited. One tied key `lambda` stands for `lambda_amp = lambda_mu = lambda_sig`, the owner's `smoothNNN` convention, so a sweep over N and lambda is two parameters, not four. When a request names both `lambda` and one of its members, the member wins, always (`ROHSAExpand`: the tie first, then the individual keys); a sweep drops a base-job setting that overlaps a swept one, and refuses a grid that names `lambda` with one of its members.
- **Request kept.** The job's `Request` holds the base config text, the settings changed, and the resources (`jobs.ROHSARequest`, the same record as VGT's).
- **Run again with...** `GET /api/runs/{id}/rerun` now answers for kind `rohsa`: `rohsa` (the request, as for VGT) and `settings` (the editable settings as they were). From a job, `settings` are read by the server from the config the job started from with its changes over them, and the draft starts from that text. For an imported run (the usual case: a fit is imported from a local copy, so no job made it) `settings` are what the run's own records declare: the trace's `[config]` first, then its top-level `n_gauss`, and the namelist (`parameters`) only for what neither says. The pipeline writes the namelist and the trace config from the same options (`rohsa/configs.jl`: `write_rohsa_parameters` and `rohsa_trace_config` both read `opts`; checked on one real run, where the config's `sig_init = 4.84` and `lb_sig = 1.21` are the namelist's `4.84d0` and `1.21d0`), so they agree and the namelist only spells reals as Fortran does and booleans as `.true.`; the page normalises both. The crop and the kernel are not in a trace; once a config is chosen on a host the form shows its values as the "was" and uses its crop for the sizing line. Changed fields are highlighted ("changed - was 16"); `10` and `10.0` are the same number. Imported runs send the declared values explicitly over the chosen file, as for VGT.
- **Sizing.** `GET /api/rohsa/sizing?cropSize=&nGauss=` mirrors, case for case, the table in the owner's `hpc/irgetas/submit_rohsa.sh` (crop up to 512: 16 CPUs 12G 3 h; 1024: 16, 40G, 12 h; 2048: 32 CPUs, N up to 6 100G 1 day, above 6 140G 1.5 days; whole cube: 32, 180G, 3 days; a missing crop reads as 0 and a missing N as 6, and the reply lists what it assumed). It is a suggestion labelled with its source, shown beside the ADR 0045 measured use when the previous job has one, applied only by a click. The script's partition (ZEN4) is shown as information and never applied.
- **Results of a ROHSA job are imported from the host** (superseded: this bullet said the import was local-only, automatic import stayed off, "Import results" answered 409 and no `run.json` was written; see "A fit on a host" below).
- **Validation.** Go: a config shaped like the owner's (header comment, crop keys after the paths, `n_gauss = [16]`, a commented `[auto_config]` axis, a key the editor does not know) round-trips with only the changed lines and the output folder different, comments and unknown keys intact, the same request giving the same text 20 times; refusals for `output_dir`, `input`, other keys, bad types, injected newlines, a multi-line list, an `[auto_config]` base and a top-level key; a key that sits in another table is edited, not duplicated; the tied key and its members never depend on map order, and a sweep over `lambda` from a base that sets `lambda_amp` (or `lambda`) puts every draft's three lines on the swept value; the config read from a path on the host; the sizing function on the script's ten boundary cases and its defaults; a ROHSA job's script embeds its config and gets its own output folder; a rerun draft for a ROHSA run with N changed from 16 to 12 differs from the first job's config in N and the output folder only; the imported run's baseline is the trace's with the namelist filling a gap (`noise`) and never over the config; the sizing route; no `run.json`, 409 on register. Web: the rerun form, the sizing line following N, the imported run's crop read from the chosen config, the new-job form sending only changed settings. **Not verified:** a real Slurm or a real ROHSA run of a rendered script, the owner's real configs (only a fixture shaped like them), a design review.
- **Limits.** `crop_size`, `crop_x0` and `crop_y0` are editable: a changed crop is a different fit grid, so the run's crop dataset (above) differs from its parent's; the sizing line follows `crop_size`. The pipeline's own memory preflight, `memory_gb`, is editable since the remote-fits note below (it was not here at first): the owner's 2048 configs carry `memory_gb = 96` and the pipeline refuses a fit whose estimate is above that budget unless `force_full_cube`, so a raised N can fail there whatever Slurm grants; the job log has the pipeline's message. A job-sourced ROHSA rerun now exists (a completed ROHSA job gets its run by auto-import); that path is covered by tests with a linked run and by the auto-import test, not by a real Slurm flow.

## Note: a fit on a host (import, the index built there, auto-import, one run per job, memory_gb)
Status: **implemented, awaiting owner review.** Decided by the implementing agent under the owner's delegation of ADR decisions. The owner runs ROHSA only on the cluster, so until now a result had to be copied here before it could be browsed (a `.dat` can be tens of GB). Schema unchanged (13): the host id is a field of the run's decomposition record (`rohsa_runs.info`, JSON; `hostId`, absent for a local fit), not a column. The new import choice (Runs: "Where the run is") and the changed job form copy had no approved mock and no design review.
- **Import from a host path.** `POST /api/runs/import` takes `hostId` with the `path`. The path is the `.dat`, or a folder holding one fit (the folder itself or up to three levels below it, at most 40 folders listed, the search stops going down at a folder with a fit); several fits are refused with their names, none with the reason, a link out of the host's roots is `not available`. Everything is read by the host's persistent worker through the roots it enforces: the namelist and the two traces (`readtext`, 256 KiB at most each), the crop FITS and the product maps (registered as remote datasets exactly as other remote FITS are: `resolve`, `header`, host id, the data stays there), `list` for the product folders. ADR 0046's rules are unchanged and run through the same importer behind a `rohsaSource` (local or remote): the crop is an input found by name, products are outputs, BUNIT wins, a name-based unit is the adapter's labelled proposal, a contradiction is a note, no path or user name enters the run. The run's key is `h<host>:<path of the .dat>`, so importing the same fit again refreshes one run, and a local copy of the same fit is another run. The `.dat` is not opened by the import; no index is built until its components are first asked for (tested: nothing is written on the host by an import). Audited: `rohsa run imported from host`.
- **Components at a pixel on a host.** Both the crop and the `.dat` must be on the same host (else 409). The request goes to that host's worker (`planesFor` the crop's host); the `.dat`'s size and mtime come from the host's `stat` and are part of the pixel cache key, so a changed fit never serves old pixels (an index is built again for it and a pixel is refused with 409 until it is). The index is the local one, built by the same code, on the host: one streaming pass in 32 MiB chunks, **resumable** (each call works about 15 s, saves how far it got, reports `building` with byte progress; the page calls again, so every call is inside the worker's timeout whatever the file size), verified layout, 8 bytes per pixel. A pixel read is one seek in the host's sidecar and N short lines of the `.dat`, every row re-checked. Only the JSON state and one pixel's curves cross the connection. Tested for equality: every pixel of the same fixture read through the host's worker and through the local path gives byte-identical frames.
- **Where the host index lives, and why this is not ADR 0039's `WriteFile`.** The sidecar (`<sha256 of path, size, mtime>.json` and `.offs`) is written in `$HOME/.cache/vesqira/rohsa` on the host, the account's own cache, beside where the worker itself is deployed. ADR 0039's mechanism does not fit: it replaces one whole small file (reads at most 200 000 bytes of what is there, hash-checks it) and audits per file, whereas the index is an append-only file of 8 bytes per pixel built over many bounded calls and rebuilt whenever the `.dat` changes. The exception is narrow and enforced by the worker, not by the caller: (1) the folder is fixed by the launcher (`VESQIRA_CACHE`, set in `Manager.worker` next to `VESQIRA_ROOTS`); a request's `cache_dir` is ignored on a host (tested); (2) it is created 0700, must be a real folder owned by the account (a link is refused), and is refused when it would be inside the `.dat`'s own folder (checked before anything is created), so nothing is written next to the data or into a project tree, and the folder is outside the source roots by default (a root that contains the whole home would contain it too; the data folder rule still holds); (3) file names are hashes the worker computes; an existing sidecar that is not a plain file (a link) is refused, never written through (tested); (4) the size is bounded: 8 bytes per pixel, the pixel count bounded by the crop the worker has just read; (5) it is a cache: deleting the folder only costs one indexing pass. It writes no research data, no credential and nothing a person made. Audited from the API, once per index and not per step or pixel: `rohsa index started on host` (host, the cache folder, the `.dat`) and `rohsa index ready|refused on host` (the worker reports `created` and `settled` for exactly that); the host's own path of the sidecar stays out of the page (`cache_file`, `created`, `settled` are removed; the page gets `where: "here"|"host"`, used to say that the host is reading the `.dat` and keeping the index). The deployed worker directory and this one are the only places Vesqira writes in a host's home besides `.vesqira/project.toml` and `run.json`.
- **Auto-import of a finished ROHSA job (ADR 0043 note).** The job's `autoImport` option is on by default for ROHSA as for VGT; at completion the one `rohsa_*.dat` in the job's output folder or just below it is imported as above and the run is linked to the job (the Jobs screen's button does the same by hand). No fit or several: one failed-import notification with the reason, not retried, nothing guessed. The same job's run is therefore the source of "Run again with..." from a job (its stored request) and of a sweep row's metrics: the grid reads the run's declared `fit_metrics` as for VGT.
- **One run per job (no double listing).** ADR 0039's `run.json` is now written for ROHSA jobs too, in the job's output folder, with the job's id, template and output folder in its `vesqira.job` block and the settings of the embedded config (`n_gauss = [16]` reads as `16`). The fit and its trace sit in that folder or below it, so a rescan would list the record and, nested in it, the fit. Discovery now recognises them as one: when a run.json that carries Vesqira's marker names a ROHSA job and ROHSA runs lie below it, the record is not listed, each fit keeps the settings of its own trace and gains the field `job` ("Vesqira job N", declared, from run.json) and a note; a fit in the same folder as the record gets the same field. A record with no fit below it (not produced yet, or failed) is listed as before; a run.json without the marker, or for another template, is never merged (tested). Imported runs are never doubled: the key is the `.dat`'s path (host-qualified), whichever way the import was reached.
- **`memory_gb` is editable.** It is the pipeline's own memory preflight (it estimates what the fit needs and refuses to start when that is above this budget, unless `force_full_cube`). It is a research setting of the config, not a credential, and a larger N is blocked by it whatever Slurm grants, so it joins the whitelist beside the iteration limits. Typed as a number of GB, written as typed (96 stays 96, not 96.0) or the word `auto` (the owner's config shape keeps `memory_gb = "auto"`); added to `[input]` when a config lacks it. The form says what it is and that Slurm's memory is a separate request.
- **Alternatives.** Copy the `.dat` (or an index) here: a multi-GB transfer to show one pixel; rejected (AGENTS.md). Index in a sidecar next to the `.dat`: a write into research data; rejected. Index with ADR 0039's `WriteFile`: wrong shape (above). A caller-chosen cache folder: lets a request pick where the host writes; rejected. Importing by listing the whole output tree: unbounded; the search is bounded and refuses several fits. A schema column for the host: a JSON field of the record suffices and avoids a migration that the transfers branch also claims a number for.
- **Validation.** Go on the stand-in host (ssh runs the remote command locally with `$HOME` moved; real workers on both sides): import registers the crop, every product and the cube as datasets with the host's id, units by ADR 0046's rules, declared metrics, no location in the run, same run on re-import, nothing written on the host by importing, refusals (outside the roots, a link out, not a fit, several fits, no fit, unknown host); the index is built on the host, stored in its cache folder (0700) and not next to the data or in the local cache folder, audited once at start and once at ready and not again, nothing about the host's folder in the page; a 37 MB fit (more than one 32 MiB chunk, 600 x 600 pixels) is indexed through the host's root-enforcing worker in several calls with a tiny time budget (`building` with `created` first, `ready` with `settled` last, never a second `created`), 8 bytes per pixel in the host's cache folder only, and a pixel read from it; a host that goes silent during an import (after the fit was found, on re-import over a good run, or a cancelled request) saves nothing and leaves the good run unchanged (an absent file is a note, a silence is a refusal); pixels equal the local path byte for byte at three pixels; a pixel outside the crop is 400; a changed `.dat` is refused until indexed again; a host that is down answers 502 and serves no cached pixel; a request's cache folder is ignored and a link where a sidecar belongs is not followed; a completed ROHSA job is imported once (watcher, refresh, a direct call and the button all give one run), linked to its job, announced, with a `run.json` that names its job and carries the config's settings, and a rescan of the project lists one run that names the job; no fit and two fits are one notification each and import nothing; a ROHSA sweep's grid shows each run's declared `voxel_rmse` and no "best"; `memory_gb` through a draft and the config editor (kept as typed, `auto`, bad values, added when missing). Python: the host-mode worker uses its launcher's cache folder and ignores a request's, refuses no cache folder, a link, and the data's folder (before creating it), never writes through a linked sidecar, and builds the index chunked and resumable. Discovery: the merge cases above. Web: the import choice sends the host id and says the `.dat` stays there, the host's refusal is shown, the job form's checkbox for ROHSA and its wording, the index progress text on a host, `memory_gb` in the whitelist. **Read in the pipeline's source, not run** (the owner's checkout on this machine, `rohsa/cli/preprocess.jl`, `runner.jl`, `products_stage.jl`; its commit was not recorded): the one command the job runs writes the fit at `<output_dir>/<region>/<run_label>.dat` with its `_run_trace.toml` beside it, and, when `derive_products` is true (the default; several of the owner's configs set it false), the product maps, cubes and `<run_label>_products_trace.toml` with `fit_metrics` in the same folder tree, so the search depth of one below the output folder is the real layout and a finished job imports its maps and metrics. With `derive_products = false` there is a fit and no maps or metrics: the run imports with the note "No product maps were found" and a sweep row has no metrics. The owner's configs carry `memory_gb` as `96` or `"auto"`, the two forms the editor writes. **Not verified:** a real cluster (real ssh, a login shell on the host, a real `$HOME` on a shared filesystem, a multi-GB `.dat`: the chunked pass was tested on a 37 MB fit through the host's worker and in Python with a shrunk chunk, and the 40 MB/s figure above is local), a real ROHSA job through Slurm to import, whether the pipeline tolerates `run.json` appearing in its output folder while it runs (VGT's was not verified either, ADR 0039), and a design review of the new controls; the new import choice and job form were not looked at in a browser by me (the existing e2e specs pass).
- **Limits.** One host per run: the crop and the `.dat` must be on it. Importing a VGT run by path from a host is not offered (VGT results of a job already are). A run imported by path is not linked to the job that made it (only the job's own import is; the scan merges the record and the fit, but a by-path import does not read run.json). A fit with more than 200 product maps links the first 200. The 10-minute bound on an import from a host is a guard, not a measurement.
- **Rollback / Migration.** None needed for the catalog (no schema change; an older build ignores `hostId` and lists no components for a run whose crop is on a host). Delete `~/.cache/vesqira/rohsa` on a host at any time. Removing `VESQIRA_CACHE` from `Manager.worker` makes a host's worker refuse the index op.
