# ADR 0014: Runs and the VGT run adapter

- Status: accepted under delegated merge, 2026-11-04; owner review pending
- Date: 2026-11-04

## Context
ADR 0013 introduces Runs. VGT writes `run_metadata.toml` next to its output maps, recording parameters, the code commit (with a `-dirty` suffix for an unclean tree), the input file and the output paths of the machine it ran on.

## Decision
- **Import.** `POST /api/runs/import` takes a run folder or its `run_metadata.toml`, which must resolve inside a source root like any file. Output files are looked up by file name next to the metadata (the paths inside it belong to the run's own machine and are never followed); each found map is registered as an ordinary dataset and linked to the run by role (psi, reliability, support, fit_rbar2). Re-importing the same folder refreshes the run.
- **Parameters are recorded as the pipeline wrote them**, one row when both sections agree and both rows when they differ. Keys or values that look like a location or a person (file, path, dir, home, root, host, user, anything containing a slash) are dropped when the run is parsed, so no path, host or user name reaches the catalog view, a figure or a reviewer.
- **Code version.** A commit ending in `-dirty` is shown as "not reproducible from the commit" everywhere, including to the reviewer.
- **Input link is a hint.** The run's input file name and size are matched against registered datasets and offered as "inferred from name and size; not proof of identity". The input path is not stored.
- **Proposed interpretation.** The psi map is proposed as axial orientation in radians (the VGT source computes `0.5*atan2(U,Q)+pi/2`), paired with the reliability map when `compat.Grids` confirms the same grid. The declaration records `declaredBy: vgt-run-adapter` and is shown as the run import's proposal, not the file's and not the user's. A user's own declaration is never overwritten by a later import, and the user can change the proposal like any declaration.
- **Figures carry the run.** A figure of a run output includes the run name, role, short commit, dirty flag, finish time and parameters in its reviewer-safe provenance.
- **Dependency.** `github.com/BurntSushi/toml` (MIT) parses the metadata.

## Alternatives
Reading TOML in the Python worker (a process hop for a tiny file); following the paths in the metadata (they refer to another machine and could point anywhere); matching the input cube by name alone.

## Consequences
Runs from other pipelines need their own adapter. Only the VGT metadata layout is understood.

## Validation
Parser tests: parameters kept, every location-like key and value dropped, outputs reduced to names, unknown output keys ignored, dirty versus clean commit, non-metadata and oversized input refused. An end-to-end Go test imports a generated run folder through HTTP with the real worker: four outputs linked, an outside path refused, the adapter's interpretation and reliability pairing, the inferred input link, re-import without duplication, a user's declaration kept, and a reviewer response that shows the parameters and the dirty commit but contains no input path, project path, user name or root. The browser walk-through imports the run and follows it to the reviewer.

## Rollback / Migration
Drop the `runs` and `run_outputs` tables and the routes; datasets are unaffected.

## Amendment: what is known about rerunning a run

A run now carries a list of facts about reproducibility, each marked `declared`, `inferred` or `unresolved`: code version (commit, and whether the run reports uncommitted changes), parameters, input (name and size as declared; a registered file with the same name and size is only *inferred*, and no content hash is recorded), software environment (not recorded by the run metadata, so unresolved), random seed (declared only when a parameter named like a seed exists), output files (registered by reference, no checksums recorded), what counts as the same result (not stated), and evaluations that failed (declared only when the run reports both attempts and failures; cancelled or excluded evaluations are not recorded). The run panel shows them under "What is known about rerunning this". This is not an assessment of the result and never replaces the author's own QC. Recording more (environment capture, hashes) would be done by the pipeline or an explicit Vesqira action, not guessed.

## Amendment: filtering runs and datasets

The explorer lists get a filter box (shown once there are more than three runs or five datasets). Words narrow the list. For runs, `key=value`, `key<value`, `key>value`, `key<=value` and `key>=value` test the run's declared parameters (as numbers when both sides are numbers, otherwise `=` compares text); `qc:passed` tests the author's assessment; other words search the name, kind, commit and input name. A parameter a run does not have never matches: absence is not a value. Datasets are searched by name, host, brightness unit and declared nature. The filtering is done in the browser over the lists already loaded.

## Amendment: typed run results (metrics)

A run's metadata may carry an optional `[metrics]` section (Q130, Q131). Each entry is a bare number or a table with `value`, `unit`, `uncertainty`, `uncertainty_kind` (`standard_deviation`, `standard_error`, `confidence_68`, `confidence_95`, `other`), `n` (independent samples) and `definition` (the run's own words about what the number measures). Rules, all tested: every metric is *declared*, since Vesqira neither computes nor verifies it; a value that is missing, `nan` or infinite is unknown and shown as "not recorded", never 0, while a recorded 0 stays 0; a negative uncertainty is dropped; an uncertainty without a recognised kind keeps an empty kind ("kind not stated") instead of a guessed one; a unit or definition that names a place on a machine is dropped like location-like parameters; at most 50 metrics. Metrics are stored with the run (a `metrics` column added by `schema.AddColumn`), replaced on re-import, shown on the run, carried into a figure's provenance (so a reviewer sees the values that were current when the figure was made) and listed side by side in the comparison inspector. Two runs' same-named metrics are offered as comparable only when both state the same definition and unit; otherwise the row says why not (Q132). The run filter box tests results with the same words as parameters (`alignment_measure>0.3`) when no parameter has that name; a result the run did not record never matches (unknown is not 0). Filtering, a table of every run and a plot of a metric across runs are in ADR 0062.

## Amendment: the adapter also proposes the angle's frame and quantity (removed 2026-11-13, ADR 0068 slice 2: a convention nobody declared)
The adapter proposes `frame = pixel` and `quantity = b_field` for the psi output (ADR 0042), from the pipeline's convention (ψ = ½ atan2(U,Q) + 90°, radians, counter-clockwise from FITS axis 1, already rotated from the gradient). It is a proposal labelled with its author, overridable in the orientation panel; the files carry none of it.

## Amendment: the file's own header declares the angle's frame (issue 118)
VGT.jl now writes `PSIFRAME`, `PSIANGLE`, `VGTPROD` and the run's `VGT*` keywords (and the input beam, `INB*`) into product headers, so the amendment above ("the files carry none of it") holds only for older output. Status: implemented.
- **Reading.** The worker's header report carries the cards verbatim under `vgt`. One reading, `catalog.VGTOf` (mapping version 1), turns them into a declaration. `PSIFRAME=PIXEL` is `frame = pixel`. `GALACTIC` and `ICRS` are `frame = sky` with the *frame of the angle* (`skyFrame`), a position angle east of north in that frame. `PSIANGLE=BFIELD` is `quantity = b_field`. `BUNIT` of `rad` or `deg` is the unit. `VGTPROD` is the product role. An unknown `PSIFRAME`, an unknown `PSIANGLE` or a `BUNIT` that is not an angle unit is not used and a note says so. A missing `PSIFRAME` yields no declaration: it is never read as pixel from the WCS or from anything else.
- **Why `skyFrame`.** Vesqira's `sky` means east of north in the *grid's own* frame (ADR 0042). PSIFRAME names the angle's frame independently of the grid (VGT writes `GALACTIC` on an equatorial LMC grid, where Galactic north is about 100 degrees from the grid's north), so mapping `GALACTIC` to a bare `sky` would be wrong by that local angle. A declaration made by the file therefore carries `skyFrame`. It is computed from the stored header on read (no new column), so it cannot disagree with the file; if the header no longer supports the stored declaration it is marked stale. Every consumer first carries the angle through the sky into the grid's frame at each pixel (`orientation.sky_pa_in_grid_frame`, astropy), then proceeds as for any sky-frame map: relative orientation (map and catalog modes), the worker's single-pixel orientation readout (`orientation_sky`, which has no HTTP caller today), orientation segments drawn over another map in the viewer and in figures (the worker overlay), align and convolve. The viewer's own-map lines use the stored angle as a pixel direction, so for a map whose angle is stated in another celestial frame they are not drawn, and the orientation panel says why. Convolve and align write their result in the grid's (or the reference's) own frame, so a result needs no second frame. The axial difference subtracts stored numbers, so it refuses, with a sentence, two maps whose angles are stated differently (pixel against sky, or different frames), and points to the relative orientation comparison. A window written from a map stated in another frame is left undeclared rather than restated, and a strided window drops `VGTDN`, `VGTKER` and `VGTKFWHM`, which count input pixels that the stride changed. The file's own declaration is not listed as an unconfirmed proposal in the project needs. Confirming such a proposal from the project needs list is refused with a sentence, because a confirmation would restate it in the grid's own frame.
- **Labels.** The author is `vgt-file-header`, shown as "declared by the file", tier `declared` (the file's own words, with the mapping version), per-field basis `file` (the unit is `convention` only when BUNIT states none). A file without PSIFRAME keeps the adapter's convention under `vgt-run-adapter`, labelled as before. Header and convention fields are never mixed under one author.
- **Precedence and conflicts.** The header outranks the adapter's assumption: a run import replaces an adapter proposal or an earlier analysis proposal with the header's declaration. It does not override a declaration by the researcher or by their import rule. The standing rule of this ADR (an import never overwrites the researcher's declaration) is kept, because a declaration is an explicit act and may be informed by something the header cannot know (a header known to be wrong, a rule for a whole folder). The disagreement is never hidden: the dataset carries `orientationHeader.conflicts` (`vgtHeader` until ADR 0068 slice 6), full sentences naming both sides, shown in the orientation panel with "the declaration in force stays in use", and a button, "Use the file's declaration" (`POST .../interpretation` with `fromFile`, the server reads the header and the client sends no values). A person's `sky` is the grid's own frame, so it conflicts with a header that names another frame, and agrees with a Galactic header only on a Galactic grid. Figures record the declared sky frame, so a changed declaration is reported on the figure like any other.
- **Run parameters without run_metadata.toml.** The `VGT*` and `INB*` cards are listed as "declared by the file" in the orientation panel, filtered by the same rule as run parameters (nothing that names a place).
- **Derived files.** The producer's cards (`PSIFRAME`, `PSIANGLE`, `VGTPROD`, `VGT*`, `INB*`) are removed from a convolved result, whose angles and resolution are no longer the original's; align and axial difference build their headers from scratch.
- **run_metadata.toml.** The current VGT writes the project name `VGT` and no longer writes `finalize_mask_mode`, `histogram_edge_mode`, `gradient_sample_mode` or the noise exponents. The parser requires none of them and no project name; an old file that has them keeps them as recorded parameters. `fixtures/generate.py` writes both layouts (`vgt_run_demo`: old, `vgt_run_current`: current).
- **Validation.** Worker tests: each `PSIFRAME` case and its absence; a GALACTIC angle on an ICRS grid against the position angle of the North Galactic Pole at each pixel (astropy), and a relative-orientation case with a known 20 degree offset; no rotation on a Galactic grid. Go tests: the mapping and the "never fills a gap" rules, run import with header, fallback and a user declaration kept, conflict sentences, `fromFile`, the axial difference refusal, and both `run_metadata.toml` layouts.
- **Rollback.** Remove `vgt-file-header` handling; stored declarations from it are read as stale until redeclared.

Note 2026-11-13 (ADR 0068, slice 2): the card table moved out of Go and Python into `orientation_profiles.json`; `catalog.VGTOf` now carries the worker's profile reading instead of mapping the cards itself. A declaration from the header is authored `profile:VGT.jl@1` (older rows keep `vgt-file-header`, read as the same). The fallback described in "the adapter also proposes the angle's frame and quantity" is removed: a psi map the profile cannot place is unresolved and the run import declares nothing for it, and a missing `BUNIT` is no longer radians "by convention".

## Amendment: run this configuration on another cube (issue 121; implemented, awaiting owner review)

**Decision.** From a finished VGT or ROHSA run that a job here made, `POST /api/runs/{id}/rerun-on-input` (preview: `GET`, same path, nothing stored) drafts a job that runs the recorded configuration on a different cube. It is rendered from the run's recorded settings (the config text the job started from, its overrides, the code folder, the resources), never from the script text, the rule sweeps follow (ADR 0048); hand edits to the source script are not carried and the summary counts them. The one change is the input: the config's `input_file` (VGT) or `input` (ROHSA; the two pipelines name it differently) is replaced, line for line, by a cube already registered on the same host as the run's job. Nothing else is touched; the draft's `BaseConfigText` names the new input, so a later "run again with..." or a sweep from it starts from the new cube and never silently returns to the old one. Local mode only: the routes are job routes (`job.read`, `job.submit`) and the group server does not mount them (ADR 0050, 0066).

**What the draft says.** The response and the web panel list what changed (the input, old path to new), what was carried (every effective setting, the code folder, the resources), the new input's identity as the catalog has it (size, sampled fingerprint, and full SHA-256 when one was computed for that size; ADR 0053) and notes to read: the pixel scale of both cubes in arcseconds when they differ (window sizes are pixels and are kept as pixels; nothing is converted), a spectral axis or channel count that differs, a unit that could not be compared. Nothing is computed for the draft: a full hash reads the whole file.

**Refusals, each a sentence, nothing stored.** The run is imported or its job kept no settings; the configuration cannot be read back; the run is not VGT or ROHSA; the mode is strict (it insists on the same input, so a different one cannot satisfy it; best effort, the default, or adapted); the recorded configuration names a `weight_file` (it belongs to the old cube, and a second input is not guessed); a relative recorded input is read as relative to the code folder (where the script runs) for the same-file, unit and pixel-scale lookups, and the summary says so; the cube is not on the job's host, is archived, is not FITS, has a path a script cannot carry, or is the file the run already used; its header is not a cube of two sky axes and a spectral axis in that order (both pipelines read axes 1 and 2 as the sky and 3 as spectral, so another order is refused, not reordered); VGT `dn` larger than either side (the pipeline's own `dn <= nx, ny` check) or `ker` larger than the smaller side; ROHSA `crop_size` larger than the smaller side or `crop_x0`/`crop_y0` outside the cube (1-based, as `rohsa/inputs.jl` reads them); `noise` carried while the data unit of the previous input and the new cube are both known and differ. A unit unknown on either side is a note, never a match. No VGT or ROHSA setting that Vesqira edits is a spectral range, so there is no range check beyond the spectral axis being declared; a range setting would be refused the same way.

**Full input identity on the new run.** The draft's script asks the job to hash its input (`HashInput`, one pass over the file on the compute node, before the program starts, size and modification time read before and after, never failing the job), and the run's environment gains `input.full_sha256`: verified only when computed by the job under those conditions, otherwise unresolved with the reason. The sampled fingerprint is measured at import as before (ADR 0054). The run record's input line says the SHA-256 is the job's own observation when it is. ROHSA jobs now record their input file facts too (they were unresolved because the reader looked for `input_file`).

**Link and grouping.** The job's request keeps `inputRerun`: the source run id, the source's configuration hash, the draft's own, the previous input path and the new input's identity at draft time. A run reports `configHash` and, when made this way, `inputRerun` with `sameConfiguration` (the recorded hashes agree). The configuration hash (`vesqira-config/1`) is the SHA-256 of the whole config, every table, list and key, after the overrides are applied, with `input_file`, `input` and `output_dir` dropped, as canonical JSON; resources and the code folder are not part of it. It is computed, not stored, so runs made before this have one too. The runs query gains `config:<hash prefix>` (a run with no kept settings is "not recorded"), so the cross-run table (ADR 0062) groups runs by configuration, and a run page lists the other runs that share it.

**Not built.** Strict mode pinned to the source's code revision with the input exempt (the strict checks compare the input and would have to learn that exemption); a choice between keeping the window sizes in pixels or keeping the angular scale (both are shown, pixels are kept); a second input for `weight_file`; a column for the hash in the table; cubes with a degenerate fourth (Stokes) axis, which are refused because the pipelines read the cube as three axes and nothing here squeezes an axis; a plain "run again with..." of such a run does not carry the input-hashing flag.

**Validation.** Go: the draft carries every setting but the input (script, summary, request), the identity and link are recorded, the two runs share a hash, a later rerun prefill names the new input, every refusal above leaves no job, ROHSA's `input` key and crop bounds, the hash ignores paths and nothing else, the preamble hashes only when asked and records the real SHA-256 when run under bash, the responses conform to the spec. Web: the action (host filter, preview, refusal sentence, draft), the summary, the link on the run page, `config:`. Not verified: a real Slurm job, a full-size cube's hashing time on a compute node, and the rendered panel and run-page sections, which no one has looked at in a browser (no walk-through, no screenshots, no design review, and the new screens have no approved mock).
