# ADR 0050: Group server: accounts, roles, key custody and storage

- Status: proposed; awaiting owner review — no code until accepted
- Date: 2026-11-11
- Decides the design that ADR 0028 (option B, a shared multi-user server) requires before code. Everything below is **specified**; nothing is implemented.

## Context

Today Vesqira has one principal. The owner API listens on loopback only and has no authentication; `localOnly` (`internal/server/server.go`) refuses a non-loopback `Host` (DNS rebinding), cross-site `Sec-Fetch-Site`, a write whose `Origin` differs from `Host`, and non-JSON write bodies. Everything else reaches the app through capabilities that are not accounts: board review links on `--review-addr` (ADR 0011, `internal/review`, which `internal/arch` confines to the snapshot store) and named reader links on the separate publish server (ADR 0036, `internal/publish`, which may reach no other internal package). The agent CLI and `vesqira mcp` are clients of the loopback API and act as the owner (ADR 0036 states that this is not a boundary against a same-user process).

What the single-owner design relies on, and what a shared server breaks:

- **Remote hosts use the owner's own ssh.** `hosts.Manager` runs the system `ssh` with `BatchMode=yes`, passes only `SSH_AUTH_SOCK`/`SSH_AGENT_PID`, multiplexes through one `ControlPath` directory (`%C`), keeps one worker per host on the host, and never reads a key (ADR 0015). Host destinations may be aliases from the owner's `~/.ssh/config`. Not only job submission goes over ssh: planes, spectra, header reads, folder listing, host text, storage looks (ADR 0045), job status (the watcher, ADR 0043), owed run records and `run.json` writes (ADR 0039), automatic imports and the sweep scheduler (ADR 0048) do too, and several of them run with nobody at the keyboard.
- **Some state is per person but stored once.** `reports.seen_revision` and `notifications.read` are single columns: "what I have read" belongs to the one owner.
- **The service account is the owner.** `fs/choose` opens the desktop chooser, `projects/open` turns any folder the owner picks into a source root (ADR 0030, ADR 0037), `fs/complete`, `files/tree`, `preview`, dataset and catalog registration read by path inside those roots, the editor writes inside them (ADR 0029), and `hosts/ssh-config` reads the owner's ssh config. All of that is "the owner's files" only because the process runs as the owner.
- **The catalog is global.** No table in schema 13 (`services/api/testdata/schema_v13.sql`) carries a project, workspace or author; `datasets.path` is globally unique; the audit log has no actor (ADR 0019 deferred it to this stage). ADR 0030 "projects" are opened folders, not an access unit.
- **One connection.** `catalog.Open` uses SQLite in WAL mode with a 5 s busy timeout and `SetMaxOpenConns(1)`: reads and writes share one connection.
- **One persistent plane worker** serves every request in turn (ADR 0008). It caps its own private memory (`limit_memory` in `plane_worker.py`, `RLIMIT_DATA`, `VESQIRA_WORKER_MEM_MB`, default 3072 MiB) where `/proc` exists. The other worker scripts (`fits_header.py`, `analysis.py`, `catalog_table.py`, `convert.py`, `relorient.py`, `rohsa.py`, `overlay_geometry.py`) do not call it, so the roadmap's "worker memory cap" is only partly done. The other remaining Stage 7 item is the window between the API authorising a path and the worker opening it.

The product decisions this ADR must honour (`docs/product/shape.md` section 9): cluster access, project membership and data-sharing permission are three separate things (Q7, Q44); roles Viewer, Researcher, Maintainer, Owner with a "view effective permissions" panel; project permission never silently reaches files the cluster account cannot read; platform auth never grants SSH or Slurm rights; workers get operations, not secrets (Q71, Q159, Q161); delegated execution with a Requested → Authorised → Submitted lifecycle where approval covers the exact script (Q29–Q31); local projects need no account; SQLite local, PostgreSQL shared (Q153). AGENTS.md: SSH credentials are user-scoped, brokered securely, never exposed to supervisors or agents; permission checks are enforced on the server.

The owner uses local mode daily. It must keep working unchanged.

## Decision

### 1. Deployment shape

- **One binary, two modes.** `vesqira-api` without new flags is today's local mode. `vesqira-api --multi-user --public-origin https://vesqira.example.edu` is a group server for one research group, run as a dedicated unprivileged service account (`vesqira`) under systemd on a group machine or VM, behind a TLS reverse proxy (Caddy example, as for the publish server) or with `--tls-cert/--tls-key`. Browsers are the only interactive clients; the desktop shell (ADR 0037) stays a local-mode program.
- **Local mode keeps one code path with the server.** It gets the same authorisation middleware with a fixed implicit principal, `local-owner`, who holds every permission in the single implicit workspace. Nothing changes for the owner: no login, no cookie, `localOnly` exactly as now, editor and desktop chooser as now, hosts through the owner's own ssh agent. The validation for this is that the existing Go suite and `make e2e` pass unchanged after each slice.
- **What the group server refuses to start with:** `--enable-editor`, `--enable-terminal` (a shell as the server's account, ADR 0029), a `--public-origin` that is not `https` (except `--insecure-dev` for tests), a database on a network file system (detected by `statfs`; SQLite locking is unsafe there), or `--review-addr` on the same address. The review listener and the publish server keep their own modes and stay token-based (section 3).
- **The server must reach the clusters by routing.** Vesqira never runs a VPN on the server (the ADR 0029 VPN button is local only). If a cluster is reachable only through a personal VPN client, compute through the group server is not available for it (section 5, "not supported").

### 2. Identity and sessions

- **Both, OIDC first.** Accounts sign in with OpenID Connect (authorisation code flow with PKCE and `nonce`, via `github.com/coreos/go-oidc/v3` and `golang.org/x/oauth2`; both new dependencies of `services/api`, recorded here). One or more issuers are configured by the admin: the university's SSO when it will register a client, ORCID (a public OIDC provider most researchers already have) for outside collaborators. An identity is the pair (issuer, `sub`), never an email address; the email claim is only used to match an invitation once, and only when `email_verified` is true.
- **Local passwords are a fallback the admin turns on** (`--allow-passwords`) for groups whose university will not register a client. Passwords are hashed with argon2id (`golang.org/x/crypto/argon2`; m=64 MiB, t=3, p=1, per-user salt), at least 12 characters, checked against a bundled list of common passwords, and failed attempts are rate limited per account and per client address. **MFA:** TOTP is mandatory for password accounts (RFC 6238, secret stored wrapped by the server's secret key, section 5), set up at first login, with ten single-use recovery codes. OIDC accounts get MFA from their identity provider; Vesqira does not add a second factor on top. WebAuthn is a later step.
- **Sessions are server-side.** A 256-bit random session id in a cookie `__Host-vesqira`, `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`; only its SHA-256 is stored, with the account, creation, last use, client address and user agent. Idle timeout 12 h, absolute 7 days. The id rotates at login and at every privilege change. Disabling an account or signing out everywhere deletes its rows, so revocation is immediate. A **recent sign-in** (within 15 minutes) is required for enrolling or unlocking an ssh key, creating a personal access token, changing roles, deleting, publishing outside the group, and admin actions.
- **CSRF strategy (multi-user mode).** The `Host` check becomes "`Host` equals the host of `--public-origin`" (still the DNS-rebinding guard; forwarded headers are never trusted for this). Every non-GET/HEAD request must carry an `Origin` equal to `--public-origin` (today a missing `Origin` passes, which is safe on loopback without cookies and is not safe with them; current browsers send `Origin` on same-origin `fetch` writes), `Sec-Fetch-Site` must be `same-origin` or absent, and the body must be `application/json` (a cross-origin JSON write needs a preflight, which the server never grants). With `SameSite=Lax` this is enough; no synchroniser token. The inherited refusal of a cross-site `Sec-Fetch-Site` on **GET** stays for every `/api` route (a foreign page must not make the server read files even by GET), but not for top-level navigations to the app shell (`Sec-Fetch-Mode: navigate` on `GET /` and the app's own paths), the OIDC callback `GET /auth/callback` (arrives cross-site from the identity provider; protected by `state`, `nonce` and PKCE) and the invitation page `GET /invite/{token}` (clicked from webmail). That exemption list is fixed and pinned by a test. A consequence the route guard enforces: **GET routes must not change state.** Two current GETs have side effects that must be revisited in slice 2: `GET /api/hosts/{id}/storage` may make an ssh call (allowed: a rate-limited cache refresh under the caller's own credential, no write) and `GET /api/files/text` records an audit entry (editor, local only).
- **Non-browser clients** (agent CLI, `vesqira mcp`) use personal access tokens: 256-bit, shown once, hashed, with an expiry (default 30 days, at most 1 year), a scope that is a subset of the account's permissions (`read`, `write`, never `admin`, never key unlock), sent as `Authorization: Bearer`. A bearer request is exempt from the cookie CSRF checks because nothing ambient carries it, and a request carrying both a cookie and a bearer token is refused. The MCP tool list keeps ADR 0036's rule (no publish, no resolve). In local mode the CLI and MCP keep calling loopback without a token.
- **Account lifecycle.**
  - *Bootstrap.* The server never has a default password. `vesqira-api admin bootstrap --db ...` on the server machine (shell access to the service account is the root of trust) prints a single-use enrolment link valid for 30 minutes; following it creates the first admin through OIDC or a password with TOTP. A server with no admin serves only a page saying to run that command.
  - *Invite.* An admin or a workspace Owner creates an invitation for an email address and a role: a single-use token, 7 days, revocable. Accepting it binds the signing-in identity. There is no self-registration.
  - *Disable.* Immediate: sessions and tokens deleted, the ssh agent for that account stopped (section 5), host workers closed; jobs already queued on a cluster keep running under the person's own cluster account (Vesqira cannot and must not cancel them without their credential) and are shown as "submitted by a disabled account".
  - *Remove.* Refused while the account is the last Owner of a workspace. Otherwise the account becomes a tombstone (`former member: <name>`): its authored records keep attribution, its sessions, tokens and wrapped key are deleted, and the admin is told to have the person remove the public key from the cluster.

### 3. Authorisation model

- **Principals:** accounts (acting through a session or a personal access token); `local-owner` (local mode only); `system on behalf of <account>` for unattended work (watcher, sweep scheduler, owed records, automatic import), which never has more than that account's current permissions and stops when the account is disabled. **Capability holders are not principals:** review links (ADR 0011) and publish-server reader links (ADR 0036) stay token-based for people outside the group, unchanged, on their own listeners and packages. A group member does not need a link; publishing a link is a workspace action with its own permission.
- **Workspace** is the access unit (shape.md's "project": a persistent shared workspace that references folders and clusters). The schema name is `workspace` because `projects` already means opened folders (ADR 0030); opened folders become folders of a workspace. Every row of user data gets a `workspace_id`; local mode has exactly one workspace.
- **Roles per workspace** use shape.md's names (Q44): **Viewer, Researcher, Maintainer, Owner**. The brief's "collaborator" is Researcher; "reviewer" is not a role but a link holder; a supervisor who is a member is a Viewer (who may comment) or higher. Server-wide there is one more flag, **admin**, which manages accounts, identity providers, clusters, data roots and quotas but is *not* a workspace role: an admin sees workspace content only if also a member (the operator of the machine can of course read the database; the ADR does not pretend otherwise).
- **Per cluster** (a "host" in today's code becomes two records): a **cluster** is declared by an admin (name, ssh host and port, pinned host keys, allowed root patterns, Python command). A **cluster access** belongs to one account: their username on that cluster and their enrolled key (section 5). A workspace lists the clusters it uses. Submitting to a cluster requires Researcher or higher in the workspace **and** the submitter's own cluster access. Platform roles never grant cluster rights.
- **Default deny.** A route without a declared permission does not start (section 4). A resource in a workspace the actor is not a member of answers **404**, the same as a missing id, so ids are not an existence oracle.
- **Ownership rule.** Researchers edit, archive and publish what they created; Maintainers and Owners act on anything in the workspace. Records carry `created_by`.

**Data roots and path authorisation.** Server-side storage is admin-declared and **per workspace, not per user** (the brief asked for per-user roots): data in a workspace is there to be shared with its members, and private storage is simply a personal workspace with one member, which every account may have. Each workspace has data roots (for example `/srv/lab/hi-survey`) that the service account can read; they are canonicalised at declaration (no `/`, no home folders, no credential folders, the ADR 0030 rules). Every path-taking route resolves against **the workspace's** roots, never a global list, through `sourceroot.Roots`. Datasets are unique per (workspace, host, path), so the same file may be registered in two workspaces as two rows. Figure previews and attachments stay content-addressed on disk (deduplication is harmless) but are reachable only through a row in the actor's workspace. Managed copies and derived outputs go to a per-workspace folder.

**Whose ssh serves a read.** A dataset on a cluster is read through the **viewer's own** cluster access, by a worker running under the viewer's cluster account, so the cluster's own file permissions decide (shape.md: project permission never silently reaches files the cluster account cannot read). A member without access to that cluster sees the dataset's catalogued header, its figures and its published material, and a message "you have no access to this file on <cluster>; ask a member who does to make a managed copy". A managed copy into the workspace's server storage (ADR 0018) is the explicit data-sharing act; it is made by a member who can read the file, is audited, and its provenance names who copied it.

### 4. Enforcement architecture

- **Actor in the request context.** One middleware, before any handler, resolves the session cookie or bearer token (multi-user) or installs `local-owner` (local mode) and puts an `authz.Actor` (account id, display name, admin flag, token scope, how authenticated) into the context. A new package `internal/authz` holds the actor, roles, permissions and the decision function; `internal/arch` gains it (it imports only `schema`; `server` may import it; `review` and `publish` may not).
- **Every route declares its permission.** `mux.HandleFunc` is replaced in `internal/server` by `s.route(mux, "POST /api/boards/{id}/items", authz.Need(authz.Board, authz.Edit), s.boardAdd)`. The declaration names the resource kind of the path's `{id}` (dataset, run, figure, board, snapshot, comment, report, job, sweep, region, cluster, workspace, account) or `authz.Workspace` for routes that take a workspace in the query or body, `authz.Self`, `authz.Admin`, or `authz.Anonymous` (login, OIDC callback, health; a short fixed list). The middleware maps `{id}` to its workspace with one indexed lookup per kind (`workspaceOf(kind, id)`), checks the actor's role there, and passes the workspace id to the handler. Handlers still do the **ownership** check (own vs any) and anything that depends on the body (for example the dataset a figure is made from must be in the same workspace as the figure).
- **Mechanical guards.**
  1. `TestEveryRouteDeclaresAPermission`: builds the handler in both modes, enumerates the routes `s.route` recorded, and fails for any route without a declaration; a source check fails on any `HandleFunc` or `Handle` call in `internal/server` outside `s.route` (the static app is registered through the same helper as `authz.Anonymous`).
  2. `tools/contracts.py` already extracts every registration; it learns `s.route(` and writes the permission into `openapi.yaml` as `x-vesqira-permission`, and `--check` fails on an operation without one. The permission table above is then generated from the spec, not maintained by hand.
  3. `TestNoRouteLeaksAcrossWorkspaces`: two workspaces and two accounts, a fixture row of every kind in each; for every registered route with an `{id}`, a request by the other workspace's member gets 404 and the response body contains nothing from the row. A new kind without a fixture fails the test.
  4. `TestDisabledFeaturesAreNotMountedInMultiUser`: the editor, `fs/choose` and `hosts/ssh-config` answer 404 in multi-user mode, as `TestEditorRoutesAreNotOnTheReviewListener` does today.
  5. `TestEveryUserDataTableIsScoped`: reads the schema snapshot and fails for any table that has neither a `workspace_id` column nor an entry on an explicit allowlist of global tables (accounts, sessions, clusters, schema bookkeeping) or of child tables scoped through a foreign key to a scoped parent. The snapshot test must first cover every store (today `projects.Store` creates `projects`, `project_entries` and `project_answers` outside it).
- **Row-level ownership in stores.** List queries take the workspace id and filter in SQL (`WHERE workspace_id = ?`); there is no unscoped list method left in a store once its kind is migrated. Stores remain free of HTTP and of `authz`: the server passes plain ids.
- **Audit with actor.** The audit table gains `actor` (account id; `local-owner`; or `system`), `on_behalf_of`, `workspace_id` and `via` (session, token, system, local). Account events (sign-in, failed sign-in, MFA set, invitation, role change, disable, remove, token created, key enrolled, unlocked, locked, removed) are recorded too. Local mode records `local-owner`, so the local log reads as before plus one column.
- **Background work** runs with an explicit `system on behalf of` actor built from the account that authorised it (job submitter, sweep submitter), re-read on every run so a role change or disable takes effect at the next interval.

### 5. SSH key custody

The options, tested against the constraints (AGENTS: credentials user-scoped, never shared or exposed; shape.md: workers get operations, not secrets; the owner's cluster uses password-less key login behind a VPN; no SSH certificate authority is likely; a group VM has no KMS; background work needs the host without a session):

| Option | Verdict |
|---|---|
| (a) Each user forwards their own agent from the browser | Impossible: a browser cannot speak the ssh agent protocol, and forwarding a personal agent to a shared server would expose every key in it. Rejected. |
| (b1) Per-user key stored server-side, encrypted with a server master key | Works unattended, but on a VM without a KMS the master key sits beside the data: a compromise of the service account yields every enrolled key at once. Rejected as the default. |
| (b2) Per-user **dedicated** key generated on the server, encrypted with the user's own passphrase, unlocked into a per-user ssh agent for a bounded time | Chosen as the target (below). |
| (c) Short-lived SSH certificates from a site CA | The best custody when a site offers it (nothing long-lived on the server). The owner's cluster is not known to offer one. Specified as a pluggable credential source; not built until a site provides a CA. |
| (d) Compute stays on each user's own local Vesqira, which pushes results to the group server | No credential on the server at all. Chosen for the first slices and kept as the permanent path for anyone who does not enrol or whose cluster forbids stored keys. |

**Decision.**
- **Slices 1–4 put no ssh credential on the group server.** Clusters, jobs, sweeps, host reads and host writes are not mounted in multi-user mode until slice 5. Members keep running jobs from their own local instance, as today. Results reach the workspace either through shared data roots (the run folder is on group storage the server reads) or by a **push** from the local instance (slice 4). Intent of the push, to be fixed in its own short ADR before slice 4: a local instance signed in with a personal access token sends **frozen** copies, like an ADR 0036 published revision (figure picture and reviewer-safe provenance, run line, board snapshot, report revision), idempotent by content hash; datasets are not copied, they appear as references "not on this server" unless the same file is under a workspace data root; edits happen on the local instance and a newer push supersedes, so there is no two-way merge.
- **Slice 5, per-user dedicated keys (b2):**
  - At enrolment the server runs `ssh-keygen -t ed25519 -C vesqira:<account>@<server>` itself, with the passphrase handed over through the same askpass helper on a pipe as at unlock (`SSH_ASKPASS` plus `SSH_ASKPASS_REQUIRE=force`, OpenSSH 8.4 or later, checked at start; never `-N` on the command line), so the private key exists only in OpenSSH's own encrypted format (bcrypt KDF) in a secrets directory (`--secrets-dir`, 0700, outside the data directory, excluded from export and backup by construction; a backup of it would still be passphrase-protected). A personal key is never imported or uploaded, so revocation and restriction concern one key that exists only for Vesqira.
  - The user installs the public key on the cluster with a line Vesqira prints: `restrict,from="<server address>" ssh-ed25519 … vesqira:<account>@<server>`. `restrict` turns off port, agent and X11 forwarding and the pty; `from=` makes a stolen key useless from anywhere else. The cluster's own `authorized_keys` is the user's revocation switch, usable without Vesqira.
  - **Unlock.** After a recent sign-in, the user types the key passphrase; the server starts a dedicated `ssh-agent` for that account on a socket in a per-account 0700 directory with `-t <lifetime>` and loads the key with `ssh-add` (the passphrase is handed over through an askpass helper on a pipe, never a command line or environment variable). The Go process sees the passphrase for the duration of that call and **never holds the decrypted key**; ssh operations get `SSH_AUTH_SOCK` for that account's agent only, so `hosts.Manager` keeps its present design and still never reads a key. The user picks the lifetime: default 24 h, at most 7 days (admin can lower it). "Lock now" kills the agent.
  - **Unattended work** (watcher, sweep scheduler, owed run records, automatic import) runs while the submitter's agent is unlocked. When it is locked, the job shows "status unknown until <name> unlocks" (ADR 0043: not answering is not a verdict), sweeps pause before their next submission, owed records wait. Nothing fails silently and nothing is resubmitted.
  - **Per-principal ssh state.** One `hosts.Manager` per (account, cluster), each with its own `ControlPath` directory (a shared directory would let one account's command ride another account's authenticated master connection), its own worker on the host (deployed under that cluster account's `$HOME`, as now), and a server-wide cap on live host workers with idle shutdown. ssh runs with `-F` pointing to a config Vesqira generates per cluster (`HostName`, `Port`, `User`, `UserKnownHostsFile` holding the admin-pinned host keys, `StrictHostKeyChecking=yes`, `IdentityAgent` the account's socket, `IdentityFile` the account's **public** key and `IdentitiesOnly=yes`, so ssh offers exactly that key from the agent and never the service account's default keys), never the service account's `~/.ssh/config`.
- **Delegated execution (Q29–Q31, roadmap bullet 2).** A member files a **run request**: a template name, bounded typed parameters and a note, on a cluster the workspace uses. A request names no path or script and cannot run by itself (the ADR 0028 option A shape). A member with Researcher or higher **and** their own access to that cluster turns it into a draft, reads the exact script, and submits it under **their own** account; the record keeps requested by, authorised by (with the script hash they read), submitted, running, finished. Run requests arrive with slice 5, because they name a cluster. Preapproved templates and budgets for trusted collaborators (shape.md) are deferred to a later decision; every request needs an explicit approval here.
- **Script integrity across people.** `submit` already requires the hash of the script the caller saw (ADR 0016). In multi-user mode the server also records which account fetched which script hash, and refuses a submit whose hash that account never fetched; a draft edited by someone other than the submitter is flagged "changed by <name> since you read it".
- **Not supported:** password, keyboard-interactive or 2FA ssh prompts (`BatchMode` stays); uploading or importing a personal private key; agent forwarding; a VPN on the server; submitting while the submitter's agent is locked; anyone submitting, cancelling or reading host files under another person's cluster account; the terminal and the editor on the server.
- **What this does not protect against, stated plainly.** Someone with control of the running service account (or root) can use any agent that is unlocked at that moment, within its `from=` restriction, until it locks or the user removes the key from the cluster. At-rest encryption protects stolen disks and backups, not a live compromise. All accounts' agents run as the same Unix user, so their separation rests on Vesqira's code and on file permissions inside one account, not on the operating system; one Unix account per Vesqira user is not done (it would need root to manage accounts). The "Vesqira never handles keys" sentence of the `--ssh` flag remains true in local mode only; the multi-user flag text and SECURITY.md must say what slice 5 changes.

### 6. Storage

- **Numbers.** A research group server: 5–30 accounts, under 10 active at once. Writes are human actions (saves, comments, assessments, board edits: well under 1 per second at peak), the job watcher (one status update per host per minute), audit rows and notifications. Even ten times that is far below what one SQLite writer in WAL mode sustains on a local SSD (thousands of small transactions per second). Reads (lists, plane metadata) are the larger load and WAL serves them concurrently, but only if they are not forced through the one connection that writes.
- **Decision: stay on SQLite for the group server**, in WAL mode, with one writer connection and a separate read-only pool (`mode=ro`, 4–8 connections), `busy_timeout` kept, the database on local disk only. This contradicts the "PostgreSQL move" that ADR 0028 listed and shape.md's "PostgreSQL shared" (Q153), so it is an **owner question** below. Reasons: the move would mean a second SQL dialect forever (13 versioned migrations, `user_version`, `VACUUM INTO` backups of ADR 0020, the `sqlite_master` schema snapshot and contiguity tests, export and restore of ADR 0022, `INSERT OR IGNORE` and SQLite date and JSON functions across every store), a second service to run, back up and upgrade on a group VM, and both dialects tested in CI; none of it buys anything at this scale.
- **Measured triggers for a PostgreSQL ADR:** more than 50 accounts on one server; p99 wait for the write lock above 50 ms over a week (measured: the server logs lock waits from slice 2); a requirement for two server processes, replication or high availability; or an operator who mandates a managed database. New store code keeps to portable SQL where it costs nothing, to keep that door open.
- **Schema.** Additive migrations through the existing guard (ADR 0020): `accounts`, `identities` (issuer, sub), `sessions`, `access_tokens`, `invitations`, `workspaces`, `memberships`, `clusters`, `cluster_access`, `run_requests`, `script_reads`, and per-account read state (`report_seen(account, report, revision)`, `notification_reads(account, notification)`, with notifications addressed to accounts) replacing `reports.seen_revision` and `notifications.read`; `workspace_id` and `created_by` on every user-data table (local catalogs get workspace 1 and `local-owner`); actor columns on `audit`. `datasets.path` unique becomes unique per (workspace, host, path), which rebuilds that table inside the versioned migration after the automatic backup. File data stays on disk and on the clusters, never in rows.

### 7. Migration, backups and rollback

- **Local mode upgrades in place.** The new columns arrive by the usual versioned migration with its backup copy; nothing else changes for the owner.
- **Bringing a local catalog into a group server.** `vesqira-api multiuser import <export.tar.gz> --workspace <name> --owner <account> [--map /home/denis/data=/srv/lab/denis]` takes an ADR 0022 export, verifies it against its manifest, and writes its rows into a **new** workspace with `created_by` = the named account and that account as Owner. Paths are rewritten through the explicit `--map` prefixes only, and every mapped path must fall inside the workspace's declared data roots; datasets whose files are not on the server stay catalogued and are shown as missing (the Q83 flag), never guessed. Local hosts are not imported (their destinations are the owner's ssh aliases); their jobs and runs come in as read-only records that keep the old host's name as text, and can be linked to a declared cluster once slice 5 exists. Review snapshots and their token hashes come across, but links pointing to the old review address must be reissued if the address changes; the publisher key is never in an export and is entered again. A dry run lists all of this first. The source catalog is not modified.
- **Backups.** The group server runs the existing export (consistent `VACUUM INTO` plus figures, derived and managed folders, with a manifest) nightly from a systemd timer, keeps 14, and the setup guide includes a restore test into an empty directory. The secrets directory is not in it: the server's own secret key (used to wrap TOTP secrets and workspace publisher keys) is backed up separately by the operator; losing it means re-enrolling TOTP and re-entering publisher keys, never data loss. Wrapped ssh keys are deliberately not backed up; users re-enrol.
- **Rollback.** Each slice is additive and behind `--multi-user`. Local mode can be rolled back by restoring the `.before-schema-*` copy (ADR 0020). A group server can be retired by exporting each workspace back to a single-owner catalog (`vesqira-api multiuser export --workspace`), which drops accounts and keeps attribution as plain names.

### 8. Resource limits (workload classes)

- **Classes.** Interactive (planes, coordinates, spectra, header reads) has its own pool of plane workers (default 2 on the server, 1 locally) so a heavy request never queues ahead of a channel switch for someone else; batch (local analyses, managed copies, catalog registration, ROHSA indexing) has a separate lane with a server-wide concurrency limit and **one running batch item per account**; host workers are per (account, cluster) and capped server-wide.
- **Quotas per account,** admin-adjustable: concurrent batch items (1), queued batch items (10), managed-copy and derived bytes per workspace (default 200 GiB, refused with the current use shown), sweeps of at most 64 jobs (unchanged) and at most one running sweep per account, request rates per route class.
- **Memory.** The plane worker's existing `RLIMIT_DATA` cap stays and is applied to every worker script (today only `plane_worker.py` calls it; this is the roadmap's "worker memory cap" item and lands in slice 3); the group server's systemd unit adds `MemoryMax` and `TasksMax` for the whole service, and the worker count times its cap must fit under it (checked at start).
- **The authorise-then-open window** matters more with several people writing into shared roots (a collaborator could replace a folder with a symbolic link to another workspace's root between the API's check and the worker's open). Decision: the worker opens a source file by walking from the root it is given with `openat` and `O_NOFOLLOW` on every component, and checks that the device and inode match what the API resolved; a mismatch is refused. This lands before any multi-user account other than an admin can register data (slice 3).
  - **Implemented (local mode too, ahead of slice 3).** The worker's one door is `srcopen.py`: the path is resolved and checked against the roots, then opened by walking the resolved components from the deepest root holding it (from `/` when the process enforces no roots) with `O_NOFOLLOW` on every component and `O_NONBLOCK` on the last, and the descriptor must be a regular file (a FIFO or device is refused before it is opened and again by `fstat`). Python has no `openat2`, so the walk is the mechanism; astropy receives the open file object (reporting `denywrite`, so cubes are still mapped read-only and the `RLIMIT_DATA` cap does not count them), never the name. Header reads, fingerprints, catalog tables, ROHSA `.dat` reads, mask files read back and the size and time reported by `stat`, `resolve` and `readtext` all go through it. On the API side `sourceroot.OpenFile` resolves, then opens with `openat2(RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS)` and falls back to the same walk; it replaces the plain opens in the fingerprints, the host transfer hash, the managed copy, the text editor, mask identity, project-folder reads and the ROHSA side records. Honest links that resolve inside the roots keep working. Any refusal is the same "not available". **Device and inode (schema 27).** A location of a file on this computer records the device and inode its file had (`dataset_locations.file_dev`, `file_ino`, written by registration and by adding a location; 0 means not recorded, which is every location from before schema 27). Reading a dataset (`authorize`, `localStat`) compares them after the size and modification time agree; a location with none recorded is accepted and gets its identity recorded then, the same trust the size and time comparison already gives. A different file under the name, with size and time that happen to be equal (`cp -p`, an atomic replace that restores the time, a drive mounted with another device number), is refused with 409 and one sentence: "this name now belongs to a different file than the one that was registered (it was replaced, or its drive was mounted again); check it is the file you mean, then register it again". Nothing is registered again or re-recorded by the refusal; registering the path is the person's decision, and it drops the fingerprints stored for the old file. The plane requests carry the pair as `expect`, and the worker checks it on the descriptor it opens (`srcopen.open_source`, same sentence as code `changed`), so a swap between the API's check and the worker's open is caught across the process boundary. Known limits: the identity is a property of local files only (a host's worker is not given one); the other worker ops reached without `ask` (analyses, masks, jobs, header reads at registration) keep the no-link open but do not carry `expect` yet; and a device number that changes between boots (a removable or network drive) makes the person register that dataset again, by design rather than guessing it is the same file. **Listings.** `GET /api/files/tree` opens the folder once with no link followed (`sourceroot.OpenDir`) and reads names, link text (`readlinkat`) and sizes (`fstatat`) through that descriptor; a link is listed as `kind: link` with `target` (as written) and `points` (`inside`, `outside` or `broken`, resolved only to label it, for the first 500 links of a folder), and is never entered from the listing. A folder reached through a link that stays inside the roots lists as before. The path-completion listing (ADR 0031) is deliberately not limited to the roots; it only marks a link and gives its `target`. Tests: `services/scientific-worker/test_srcopen.py` and `services/api/internal/sourceroot/open_test.go` swap a parent and the file for links between the check and the open (and a listed folder, `OpenDir`); `services/api/internal/server/fileid_test.go` replaces a registered file with one of equal size and time; `filetree_test.go` lists links.

### 9. Staged implementation plan

Each slice is shippable, keeps local mode unchanged (existing suite and `make e2e` green), and adds its own tests.

1. **Actor and permission declarations, local mode only.** `internal/authz`, `s.route` with a permission for every existing route, `local-owner`, guard tests 1 and 2, `x-vesqira-permission` in the spec, actor columns on audit. No behaviour change.
2. **Accounts and sessions (`--multi-user`, one implicit workspace, admins only).** Bootstrap, OIDC and password with TOTP, server-side sessions, CSRF rules, recent sign-in, personal access tokens, disabled-feature guard (test 4), read pool and lock-wait logging. Clusters, jobs and host routes not mounted.
3. **Workspaces, memberships and roles.** `workspace_id`/`created_by` everywhere, invitations, the permission matrix, data roots per workspace, cross-workspace test (test 3), authenticated in-workspace comments, effective-permissions in capabilities, the `O_NOFOLLOW` open, workload classes and quotas. A design for the sign-in, members and effective-permissions screens is approved before this slice's UI.
4. **Bringing work in.** `multiuser import`; the push from a local instance, after its own short ADR (section 5).
5. **Server-side compute with dedicated per-user keys.** Clusters (admin), cluster access, key enrolment, unlock and lock, per-(account, cluster) managers and generated ssh config, jobs, sweeps, host reads and writes under the submitter's or reader's own access, script-read records, run requests. Only after the owner confirms the cluster's acceptable-use policy allows it.
6. **Later, each with its own decision:** SSH certificates from a site CA, preapproved templates and budgets, WebAuthn, PostgreSQL (on a measured trigger).

## Alternatives

- **One Vesqira per person with run requests (ADR 0028 option A).** Smallest change and the security boundary does not move; not chosen by the owner because it gives no shared live workspace. It survives here as option (d) and as the first form of delegated execution.
- **A separate server program instead of a mode.** Cleaner separation, but two binaries would drift in exactly the handlers that must behave the same; one binary with the permission middleware in both modes keeps one code path and lets local mode prove the middleware daily.
- **Local passwords only.** No identity provider to register, but password custody and MFA become Vesqira's job for everyone. **OIDC only.** Best, but some universities do not register clients for a lab VM; ORCID helps with outside collaborators but not with every group. Both, OIDC first, with TOTP required for passwords.
- **Client-side CSRF tokens.** Extra state and a header on every call; with `SameSite=Lax`, a required `Origin` equal to a configured public origin and JSON-only writes they add nothing here.
- **Roles named owner/collaborator/viewer/reviewer** (the stage brief). shape.md's set (Q44) is the recorded interview decision and keeps "reviewer" for outsiders holding links, which have no account.
- **Server-encrypted keys for unattended compute (b1), or one Unix account per user.** See section 5; b1 makes a single compromise yield every key, and Unix accounts need root management on the group machine.
- **A shared group ssh account on the cluster.** Breaks per-person accountability and nearly every HPC acceptable-use policy. Rejected.
- **PostgreSQL now.** See section 6.
- **Serving the reviewer surface from the authenticated API with a "reviewer" role.** ADR 0011 rejected this ("one bug away from exposing data"); outsiders keep tokens on their separate, confined listeners.

## Consequences

- The security boundary moves from "loopback and same Unix user" to "authenticated account, workspace role, own cluster access". Every route gains a declared permission, enforced in one place and checked mechanically.
- Local mode gains a middleware and an actor column and loses nothing; the owner never signs in locally.
- New dependencies: `github.com/coreos/go-oidc/v3`, `golang.org/x/oauth2`, `golang.org/x/crypto` (argon2), a TOTP implementation (`github.com/pquerna/otp` or 60 lines of RFC 6238 against its test vectors; decided in slice 2). System tools on the group server: OpenSSH `ssh`, `ssh-agent`, `ssh-add`, `ssh-keygen`.
- A group server is a machine somebody must operate: TLS, updates, backups, the secret key, and the decision about which clusters and data roots to declare.
- Members without access to a cluster see figures and published material from it, not its files, unless someone makes an audited managed copy. This is the intended boundary, and it will sometimes feel restrictive.
- Unattended job tracking on the server depends on the submitter keeping their agent unlocked; a lapsed unlock shows as "status unknown", not as a failure.
- The plane worker becomes a small pool; memory per server grows with it.
- SECURITY.md, the `--ssh` flag text and `docs/product/shape.md`'s persistence line must be updated when the corresponding slices land.

## Validation

Per slice, in addition to the existing suite and `make e2e` passing unchanged:
- **Slice 1:** guard tests 1 and 2 (every route declared, no bare registration, the spec carries a permission per operation); audit rows carry `local-owner`.
- **Slice 2:** OIDC flow against a test issuer (state, nonce and PKCE mismatches refused; an unverified email never binds; (issuer, sub) identity); password hashing parameters, lockout and TOTP against RFC 6238 vectors; session cookie attributes, rotation at login, idle and absolute expiry, immediate revocation on disable; CSRF: missing `Origin`, foreign `Origin`, foreign `Host`, cross-site `Sec-Fetch-Site`, form-encoded body, cookie plus bearer, all refused; tokens limited to their scope; editor, `fs/choose`, `hosts/ssh-config` 404; bootstrap link single-use and expiring.
- **Slice 3:** the cross-workspace test over every route with an `{id}` and the scoped-table test (guard 5); lists contain only the actor's workspace; a Researcher cannot edit another's board, a Viewer cannot write; path routes refuse anything outside the workspace's roots, including through a symbolic link swapped in after the check (worker-level test with a race harness); quota refusals carry the current use; an e2e with two accounts in two browser contexts.
- **Slice 4:** import refuses unmapped paths and paths outside roots and leaves the source catalog untouched; push validation is set by its own ADR.
- **Slice 5:** the decrypted key never appears in the Go process (enrolment and unlock tested with a fake `ssh-add` that records how it was called: passphrase only on the askpass pipe, never argv or env); two accounts on one cluster never share a `ControlPath` or an agent socket; generated ssh config pins host keys and ignores the service account's config; a locked agent stops submissions and shows "status unknown" without changing job state; a submit with a hash the account never fetched is refused; a run request carries no path or script and cannot reach a submit; job log, result and refresh by a non-submitter are refused; disable stops the agent at once. Against a real cluster: one manual enrolment and job by the owner, recorded as evidence, not as a CI test.
- Before slice 5 ships: a separate security review of the custody code and of the threat model below.

## Rollback / Migration

All schema changes are additive versioned migrations with the automatic backup copy (ADR 0020); restoring that copy rolls a local catalog back. Every multi-user behaviour is behind `--multi-user`; stopping the server and starting it without the flag is not supported on a group catalog (the server refuses a catalog with more than one workspace in local mode, with a message to export one workspace). Retiring a group server: `multiuser export` each workspace to a single-owner catalog. Revoking server-side compute: lock or delete keys on the server, and each user removes the `vesqira:` line from their cluster `authorized_keys`, which works even if the server is gone.

## Appendix: threat model

Assets: cluster access (the most valuable: compute allocation, the user's cluster files, a foothold on a shared HPC system), unpublished data and results, scientific provenance, account sessions, and outsider-facing links.

| Threat | Mitigation in this design | Residual risk |
|---|---|---|
| **Cross-user data access** (IDOR through integer ids, a list without a workspace filter, a shared cache) | Workspace resolved from `{id}` in middleware; 404 for other workspaces; SQL-scoped lists; caches keyed by resource and consulted only after the check; cross-workspace test over every route | A handler that reads a second id from the body without the same-workspace check; covered by review and by fixtures per kind, not proven |
| **Confused deputy through job scripts** (a collaborator edits a draft someone else submits under their account; a run request smuggles a command) | Jobs run only under the submitter's own account; submit requires a hash the submitter's account fetched; edits by others flagged; requests carry template and typed parameters only, never script text or paths | The submitter approves a script they did not read carefully; that is their decision, recorded |
| **Confused deputy through host writes** | Writes only through `hosts.Manager.WriteFile` (ADR 0039 scripts) under the acting account's own access, inside that cluster's declared roots | Same as ADR 0039 |
| **Cross-account use of ssh state** | Per-(account, cluster) ControlPath and worker, per-account agent socket in its own directory, generated ssh config with `IdentitiesOnly` and `IdentityAgent` | All agents run as one Unix user (section 5) |
| **Key theft** | Dedicated key, passphrase-encrypted at rest, plaintext only inside a time-limited agent, `restrict,from=` on the cluster, user-revocable without Vesqira, never exported or backed up | Live compromise of the service account during an unlock window |
| **SSRF and network pivoting through hosts** (a user points ssh or the publish client at an internal address) | Only admins declare clusters and the publish server address; users supply a cluster username validated like today's destination; ssh options cannot be injected (ADR 0015 patterns); host keys pinned | An admin declares a malicious destination |
| **Privilege escalation** (Researcher to Owner, member to admin, token to more than its account) | Role changes need Owner and recent sign-in, Maintainers may invite only Viewer and Researcher, the last Owner cannot be removed, admin is a separate flag only bootstrap or another admin grants; token scope never exceeds the account and never includes admin or unlock; `system on behalf of` re-reads current permissions | Bugs in the decision function; the guard tests cover declarations, unit tests cover the decision table |
| **Session theft** (XSS, a stolen cookie, CSRF, session fixation) | `HttpOnly`, `Secure`, `__Host-`, `SameSite=Lax`, rotation at login, server-side revocation, idle and absolute expiry, recent sign-in for sensitive actions, `Origin` required on writes, the existing CSP (no raw HTML in reports, KaTeX `trust: false`, ADR 0036) | A browser extension or malware on the user's machine |
| **Malicious collaborator uploading crafted FITS, VOTable, Notion zip or images** | Existing confinement: worker process with its memory cap, header validation before allocation, catalog and image decoders with size caps, zip-slip checks (ADR 0036); `O_NOFOLLOW` open against symbolic-link races in shared roots; files are registered from data roots, not uploaded through the API | A parser bug in astropy or numpy reachable by a crafted file; the worker is a separate process but not an OS sandbox (seccomp or a container is a later step) |
| **Denial of service by heavy analyses** | Workload classes with a reserved interactive pool, one running batch item per account, queue and byte quotas, sweep limits, systemd `MemoryMax`/`TasksMax`, rate limits on auth and comment routes | A member with a legitimate need saturating the batch lane within their quota; admins can lower it |
| **Brute force on sign-in and links** | Per-account and per-address rate limits for passwords; TOTP; review and reader links keep their identical 404 and failure limits (ADR 0011, 0036) | Credential stuffing against an OIDC provider is that provider's to handle |
| **A compromised identity provider or invitation email** | Identity is (issuer, sub); invitations bind once, expire in 7 days and require a verified email; admins see sign-ins in the audit log | A compromised university SSO account is a compromised Vesqira account |
| **Insider operator** | Not defended: whoever runs the machine can read the database and use unlocked agents. Stated in the setup guide | By design |

## Open questions for the owner

1. **Database.** Accept SQLite (WAL, one writer, a read pool) for the group server with the measured triggers above, instead of ADR 0028's PostgreSQL move?
2. **Identity provider.** Will the university register an OIDC client for the group server, or should slice 2 ship with passwords plus TOTP and ORCID?
3. **Cluster policy.** Does the cluster's acceptable-use policy allow a key held on a group server (passphrase-protected, unlocked in an agent for up to 7 days, restricted by `from=`)? Slice 5 waits on this answer. Does the site offer SSH certificates?
4. **Network.** Where will the group server run, and does it reach the cluster login node without a personal VPN client?
5. **Who is in it first.** Which people and roles, and is a supervisor a Viewer who comments?
6. **Naming.** Call the access unit "workspace" in the UI, or reuse "project" and rename today's opened folders?
