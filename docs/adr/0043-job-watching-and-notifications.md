# ADR 0043: Watching jobs while the app runs, telling the owner when they end, importing results once

Status: **proposed; implemented, awaiting owner review.** Decided by the implementing agent under the owner's delegation of ADR decisions (roadmap Stage L). Real Slurm is not verified (see Validation); the new UI has not had a design review.

## Context
A job's state was read only when the Jobs screen was open (every 15 s for the selected job) or Refresh was pressed. A job that ended overnight stayed "running" until someone looked, and its results had to be found and imported by hand. The owner's words: "so that you know exactly when it finishes."

## Decision
- **A server-side watcher** (`Server.WatchJobs`, started by `main` with the shutdown context; flag `-job-watch`, default and minimum `1m`, `0` turns it off) looks at jobs in `submitted` or `running` and, for a finished job, at an owed run record (ADR 0039). It does nothing, not even a host call, when no job is active.
- **One status call per host per interval.** Jobs are grouped by host and asked about with one command: `squeue -j a,b,c` and `sacct -j a,b,c` (`jobs.BatchStatusCommand`), then split per job (`ParseBatchStatus`) and parsed by the same rules as a single job (`ParseStatusFull`; `ParseStatus` is a wrapper). The next call to a host is not made before `interval` has passed; the slot is taken before the call, so a slow answer cannot cause a second one.
- **Backoff when a host does not answer** (VPN down): the wait doubles per consecutive failure (2, 4, 8 intervals) up to 15 minutes, and the first answer resets it. An unreachable host changes nothing about its jobs and notifies nothing: not answering is not a verdict. Jobs in `submitting` are not polled: whether Slurm holds them is the owner's decision (Check on the host, or reopen as a draft).
- **One refresh path.** The Refresh button, the page's timer and the watcher all end in `applyJobStatus`. The state change is guarded by the state (`UPDATE ... WHERE state IN ('submitted','running')`, `Store.ApplyStatus`), so a late "running" cannot overwrite an end state and, when two callers read the same end state, exactly one wins; only the winner announces the end, writes the run record and may import. The cancel route's note is guarded the same way.
- **Owed run records** are retried by the watcher too, for jobs finished within 24 h, at most three per host every five minutes, and only when the host is due. The debt is still cleared exactly as in ADR 0039.
- **Notifications** are a small table `notifications` (schema 8), not the audit log: audit is append-only, has no read mark, and answers a different question. A row has a unique `dedupe` key (`job:<id>:end`, `job:<id>:unknown`, `job:<id>:import`), so an event exists at most once however it is reached. Kept: the newest 500. Routes (owner listener only): `GET /api/notifications?limit=` returns the list and the unread count; `POST /api/notifications/read` takes `{ids}` or `{all}`. The reviewer's handler has no such route (tested), and the owner's routes refuse a non-loopback Host and a cross-site request (`localOnly`).
- **Words.** Titles and bodies state what Slurm reported and never say "success": `Job X finished (exit 0:0) — results not yet checked` with "That means the job ran to its end, not that its result is valid"; `failed (exit 1:0)`; `stopped at its time limit` (Slurm word TIMEOUT, read from the scheduler's own word, not from the folded state); `was cancelled`; and `unknown`: Slurm no longer lists a job that was submitted more than 15 minutes ago, so how it ended is not known; the job's state is left as it was (never marked failed or finished). The exit code is quoted only when `sacct` supplied one. `ParseStatus` still folds TIMEOUT and the like into `failed`; stored job states did not change.
- **Automatic import, once.** New columns `jobs.auto_import` and `jobs.auto_import_tried` (schema 8; existing jobs get 0 and 0, so nothing already submitted is imported behind its owner's back). The option is set when the draft is created (default on for VGT, off for the others; `true` for another template is refused with 422) and may be changed in the submit body while the job is still a draft; the Jobs screen shows it as a checkbox beside the script the owner reads. When the end is `completed` and the option is on, `autoImport` claims the attempt with one guarded update (`auto_import_tried`: one winner, for the life of the catalog, restarts included) and then runs the existing `importFrom` on the job's output folder, the same code as the "Import results as a run" button, followed by `LinkRun`. Nothing new decides where results are: `importFrom` reads the VGT pipeline's `run_metadata.toml` and the output files named in it. Vesqira's own `run.json` is a record of the request, not a run description, and has no importer, so a finished job whose folder has only a `run.json` is reported as not imported. A failure becomes one notification with the reason and "not retried; open the job to import them by hand", is audited, and the manual button keeps working. A success is a notification that says the files were registered and nothing was checked.
- **Delivery to the person: polling every 30 s, not a stream.** The web app asks `GET /api/notifications` every 30 s, when the window gains focus or becomes visible, and on mount. SSE would pass the proxy (no `WriteTimeout` on the owner listener, the request logger flushes, `localOnly` passes a same-origin GET) but buys nothing here: events are rare, the watcher's own granularity is a minute or more, so a stream saves at most half a poll interval; it holds one of the browser's six connections per origin while the viewer fetches many planes; `http.Server.Shutdown` waits for open handlers, so every stream would need a shutdown hook; and every test would have to cancel its client before closing the server. A poll is one indexed `COUNT` and one 50-row select on a local SQLite file. Revisit if notifications ever carry something that must arrive in under 30 s.
- **In the window.** A bell in the title bar with the unread count as text (also in its accessible name); its panel lists recent events with the kind as a word, a "New" mark for what was unread when it opened, and "Open job" / "Open run". Opening the panel marks what it shows as read. When something new arrives the app refreshes runs and datasets before a link can be followed.
- **On the desktop.** The Jobs screen has a "Notify me when jobs finish" button; the browser's permission prompt is requested only from that click (`enableDesktop`). A notice is shown for an event newer than the last one shown, not older than 10 minutes, only when chosen and allowed. The first run with nothing stored records the current newest event and shows nothing. If `Notification` is missing the screen says so; if permission is denied it says so and offers no dead button. The choice and last id are per-viewer conveniences in `localStorage`, guarded.
- **Desktop shell (Tauri on WebKitGTK).** The shell loads the app as a normal page and adds no notification plugin. Whether that webview exposes a working `Notification` is **not verified**; the code handles both cases, and the bell works regardless. Adding `tauri-plugin-notification` is the follow-up if the webview does not show them.

## Alternatives
- **Poll from the page only** (what existed): nothing happens when the window is closed or another screen is open. Rejected.
- **One status call per job**: more load on a shared login node with several jobs. Rejected; the single-job command stays for the Refresh button.
- **Reuse the audit log for events**: no read state, append-only, and "unread" would need a side table anyway. Rejected.
- **SSE**: see above.
- **Mark a vanished job failed**: invents an outcome. Rejected; it is announced as unknown and left alone.
- **Retry a failed import**: a missing or half-written folder may be fixed by hand, and endless retries hide the cause. Rejected; one attempt, one reason, a button.

## Consequences
- A cluster login node receives at most one `squeue` and one `sacct` per host per minute while jobs are active, and ssh attempts at a decreasing rate while a host is down. A real Slurm may answer a list containing an id it already purged differently from the stand-in; `sacct` is asked for the same ids, and a job missing from both is announced as unknown after 15 minutes.
- Schema 6: `jobs.auto_import`, `jobs.auto_import_tried`, table `notifications`. An older build refuses a version 6 catalog (ADR 0020). `schema_v6.sql` is the snapshot.
- The `unknown` event can precede a later terminal event for the same job if the job reappears; the two have different keys.

## Validation
Go tests with stand-in `ssh`, `sbatch`, `squeue` and `sacct` (the ssh stand-in logs every command so calls are counted): no call with no active job or only a draft; one call for two jobs on one host naming both; none inside the interval; one after it; none once nothing is active; the interval is clamped to a minute; backoff 2, 4 intervals, capped, reset on success, no state change and no notification while unreachable; one notification per end state when the watcher and three concurrent refreshes race, for completed, failed, timeout and cancelled, with the texts above and no "success"; a late "running" does not overwrite an end state; unknown announced once and the state kept; the option's defaults by template, 422 for a non-VGT job, change at submit, frozen after; a completed job imported once, linked to its job and to the run list, announced with the run id, and not again by a refresh, a second pass or a direct call; the option off imports nothing; a failed import is one notification with a reason, no retry from refresh, watcher or a direct call, and the manual import still works; the reviewer handler has no notification route; a non-loopback Host and a cross-site request are refused; notification store dedupe, unread and read marks, retention; the batch parser against the single-job parser; schema 5 to 6 migration and the v6 snapshot. Web tests: badge count in the name and as text, the list, marking read on open with the "New" mark, links to job and run, Escape, polling every 30 s with no backlog replay and no repeats, permission requested only from the click, a desktop notice only for a new event once chosen and allowed, none when not chosen, the unsupported and denied texts, and the checkbox on a VGT draft and its absence otherwise. **Not verified:** a real Slurm (the batched `squeue -j`/`sacct -j` behaviour with purged ids, accounting disabled), a real ssh host, a desktop notice actually appearing in a browser or in the Tauri window, and a design review of the bell and panel.

## Rollback / Migration
`-job-watch=0` stops the watcher; the Refresh button and page timer work as before. Remove the `Notes` field from the server wiring to drop the routes and the bell shows nothing. The two job columns and the table can stay; nothing reads them then. Restoring a pre-6 backup (made automatically before the migration) removes them.
