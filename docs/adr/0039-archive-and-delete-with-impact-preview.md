# ADR 0039: Archive and delete catalog entries, with an impact preview

Status: **proposed; implemented, awaiting owner review.** Roadmap Stage 5, Q145.

## Context
The catalog only grows: a dataset registered by mistake, a run imported twice, a board used as scratch paper all stay in every list. Removing them is risky in a research workspace because other things are built on them: figures are pinned evidence made from a dataset, boards hold figures, a published review is a frozen snapshot a supervisor may be reading, reports embed figures by revision, runs list datasets as outputs, derived datasets name their sources in their provenance. AGENTS.md also fixes two rules this feature must not bend: an original is never altered or removed by Vesqira (invariant 8), and destructive actions need a policy check. Vesqira owns bytes in exactly two places: managed copies (ADR 0018) and analysis results under the derived folder.

## Decision
- **Two verbs.** *Archive* hides an entry from the lists by default; it is instant, restorable, and the entry still resolves by id and for everything that refers to it. *Delete* forgets the entry in the catalog. The explorer filters take `archived:yes` (only archived), `archived:no` (the default) and `archived:all`; the API takes `?archived=all|only` on the four list routes; every entry the server sends carries `archived`.
- **Per entity.**
  - **Dataset:** archive and delete. Delete removes the catalog row and what is keyed to it (declared unit, nature and orientation declaration, saved regions, its own provenance record, run-output links). Figures made from it stay (pinned evidence with their own picture and provenance), so do boards, published reviews and datasets derived from it (their provenance then names a dataset no longer in the catalog). Delete is **blocked** while another dataset uses it as the reliability map of its orientation declaration: clearing that is a decision about the other dataset, not a side effect.
  - **Run:** archive and delete. Delete removes the run, its output links and the author's QC assessment with its history (listed in the preview, because it is the researcher's own judgement). Output datasets stay; jobs that produced or were drafted from it are unlinked; reports that mention it keep their text.
  - **Figure:** archive and delete. Delete is **blocked** while the figure is on a board or embedded in a report: those are working documents that would silently lose a panel or a picture. Published reviews do not block it.
  - **Board:** archive and delete. Delete is **blocked** if any review was ever published from it (live or not): a published review is pinned evidence and its owner screens (comments, revoke) hang off the board. Archive it instead.
  - **Published reviews are never deleted or archived here.** A snapshot freezes its own copy of every title, caption, provenance and the preview's content hash, and the reviewer endpoint serves the preview by that hash. Deleting a dataset or figure therefore cannot break a published review, provided the preview bytes stay: a figure's preview file is removed on delete only when no other figure and no snapshot's frozen copy references its hash.
- **Never delete a source file.** Delete is catalog-only; nothing in `internal/lifecycle` touches the file system. The preview and the dialog say so ("The file on disk is not deleted."; for a run, "The run folder on disk is not deleted."). Files on hosts are never contacted.
- **Bytes Vesqira owns.** A dataset whose file lies inside the managed-copy folder or the analysis-result folder (after resolving symlinks, a regular file) is reported as `ownedBytes`. Deleting it requires a separate, explicit `ownedBytes` choice, `keep` or `remove`; there is no default and the dialog cannot be confirmed without choosing. `remove` deletes that one file after the catalog change has committed; the original a copy was made from is never touched. `ownedBytes: "remove"` on a registered file is refused (400). If removal fails the entry is still gone and the response and audit entry say the bytes remain. Two analysis results or copies never share a file (registration paths are unique).
- **Impact preview and the digest.** `GET /api/{datasets|runs|figures|boards}/{id}/impact` lists the dependents in plain words, each with an effect word (`stays`, `unlinked`, `removed`, `blocks`; never colour alone) and a `digest` over the exact set of dependents. `POST …/delete` must carry that `impactDigest`; the server recomputes the impact inside the delete transaction and answers **409** with the new impact when it differs, and 409 with the impact when something blocks. Nothing is deleted on either. Counts alone would miss "one figure replaced by another", so the digest covers ids.
- **Audit.** Archive, restore and delete are recorded in the audit log (kind dataset, run, figure or board; an archive repeated while already archived is not recorded again). A delete entry says whether any bytes were kept, removed or could not be removed.
- **Storage.** One side table, `archived_entries(kind, entity_id, archived_at)`, so no existing table changes and no store needs a filter in every query. It is **schema version 5** (migration "archived entries", snapshot `testdata/schema_v5.sql`; `schema.EnsureArchive` and `schema.ArchivedExpr` are what the stores use, because the reviewer-facing `boards` package may import only `schema`). An upgrade copies the catalog aside first, like every schema change, and archives nothing.
- **UI.** The dataset's inspector ("Archive or delete"), the run page and the board list offer *Archive* (instant, with Undo and Restore) and *Delete…* (the preview in a dialog, then "Delete from catalog"). Figures have the API only; the explorer lists show archived entries only under `archived:yes` and the board list under "Show archived boards".

## Alternatives
- **A `deleted_at` column per table (soft delete).** Rejected for delete (the request is to forget) and for archive (needs a migration per table and a filter in every query); one side table touches nothing existing.
- **Cascade deletes (figures with their dataset).** Rejected: figures are pinned evidence, and boards and reports would silently lose panels.
- **Allow deleting a board with published reviews and keep the snapshots orphaned.** Rejected: the owner could no longer reach the reviewer's comments or revoke the link from the UI.
- **Delete managed-copy bytes by default (they are Vesqira's).** Rejected: bytes may be the only copy of a file that was since moved or changed at the original path; the choice is explicit and separate.
- **A count in place of the digest.** Rejected: it cannot see a dependent swapped for another.

## Consequences
- Analysis result files under the derived folder are treated like managed copies (owned bytes). A derived dataset's files are otherwise never cleaned up automatically; "remove" is the only way they go.
- Deleting a dataset leaves figures whose `datasetId` no longer resolves; the viewer's "open the source" for such a figure is unavailable. Their provenance (by file name) is intact.
- A reliability map can only be deleted after the declarations that use it are cleared; a report that embeds a figure blocks that figure's deletion until the figure is taken out of the text.
- Reports are not archivable or deletable here (they have their own delete). Hosts and projects are out of scope.
- The impact computation reads other packages' tables with plain SQL (`internal/lifecycle`), because the dependents are spread over them; a new table that refers to datasets, runs, figures or boards must be added there.
- An older program refuses a version 5 catalog ("newer than this program"; see Rollback).
- Routes added: `GET …/impact`, `POST …/archive`, `POST …/restore`, `POST …/delete` for datasets, runs, figures and boards, and the `?archived=` query on the four list routes. `packages/contracts/bodies.json` is not changed: the routes are listed, their bodies are not yet described.

## Validation
Go: impact lists the dependents (figures, boards, published reviews, runs, derived datasets, regions, declarations, jobs, report links, QC review); delete with a stale digest or after a new dependent appeared is 409 and changes nothing; a published review still renders, picture included, after its dataset or figure is deleted; a figure on a board and a board with a published review cannot be deleted; the source file exists after every delete; the managed-copy rule (400 without a choice, `keep` keeps, `remove` removes and leaves the original, refused for a registered file); archive hides from the default lists, shows under `archived=all|only`, still resolves and restores; audit entries; cross-site requests are refused like every owner route; the 4 to 5 migration keeps every row. Web (vitest): the confirmation flow (preview text, the digest sent, a changed impact shown again and not deleted, blocked, the bytes choice) and the `archived:` filter.

## Rollback/Migration
Schema 4 to 5 adds one table and moves no row. To roll back the feature, remove the routes and the `archived` reads; the table is inert and can be dropped, but the catalog stays at version 5 and an older program refuses it, so go back by restoring the pre-upgrade copy (`<catalog>.before-schema-5-…`) or a backup. Deleted entries cannot be restored from inside Vesqira (the catalog is backed up before every schema upgrade and by `backup`, which is the way back); managed bytes removed on request are gone.
