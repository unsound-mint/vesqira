# ADR 0039: Vesqira writes two small files on a host, and nothing else

Status: **proposed; implemented, awaiting owner review.** Decided by the implementing agent under the owner's delegation of ADR decisions (roadmap Stage W). Real-ssh behaviour is not verified (see Validation). Revised after a security review.

## Context
ADR 0030 left two things open for a project or a job that lives on another machine: a project opened on a host could not get its `.vesqira/project.toml` ("an external write that needs its own authorization"), and a job submitted through Slurm left no record of what it was asked to do next to its outputs, so a rescan of the folder found a result with no settings. Both are writes on the researcher's own account, on a machine Vesqira reaches only through the researcher's own ssh configuration. AGENTS.md requires such a boundary to be documented, authorized, audited, and never to alter what the researcher or another program made.

## Decision
- **Two files, one mechanism.** `hosts.Manager.WriteFile` is the only way Vesqira writes on a host. It runs fixed `sh` scripts through `RunShell`, the path every other host command takes (the user's `ssh` binary, config and agent; no new credential, no new connection, no new port). The scripts are constants; the root, folder, file name, byte count, digests and flags reach them as positional arguments, each single-quoted by the same `quote` the other remote commands use (embedded quotes become `'\''`) and used only inside double quotes (after `--` or `set -f` where a glob or an option could matter). The content goes on stdin. Nothing caller-supplied is ever concatenated into shell text.
  1. `.vesqira/project.toml` in a project folder, after the same explicit confirmation a local project uses (`write: true` on the project-file route, or an answer with `write` or an existing file).
  2. `run.json` in the output folder of a job Vesqira submitted (VGT and analysis jobs, which are the templates that name an output folder).
- **Login shells.** sshd runs the command through the account's login shell. Each script is therefore one line (no newline: csh rejects one inside single quotes) with no single quote, backslash or `!` (csh, tcsh and fish read them specially), and a name containing NUL, newline, carriage return or a backslash is refused before anything is sent (`TestScriptsSurviveAnyLoginShell`, `TestWriteFileRefusesBackslashNulAndNewlineInNames`).
- **Where it may write.** The root must lexically be inside one of the host's source roots (`Host.InRoots`; for a project, the project folder is itself a root; for a job, the root that holds its output folder). On the host the script resolves the root (`pwd -P`), walks the relative folder one component at a time refusing a symbolic link or a file at any step, checks that the resolved folder is still inside the resolved root, and refuses a link or a non-regular file at the target. File names are one plain name (no `/`, not `.` or `..`).
- **Folders.** Everything is checked before the first `mkdir`: a refusal (link, file in the way, a changed or unexpected target, a stream that did not arrive intact) creates no folder. `.vesqira/` inside a confirmed project folder is created (`Create`). A job's output folder is never created: it belongs to the job, and the write is refused as `absent` until the job has made it.
- **Never clobber a foreign file, and never lose an edit.** Every file carries a marker. Before writing, Go reads the existing target (`ReadExisting`: the same path checks, at most 200000 bytes, verified against the host's byte count and sha256, so a cut stream is an error and never a short file) and decides whether it is Vesqira's: for `project.toml` its first line must start with `# Written by Vesqira` (a mention further down does not count); for `run.json` it must parse as a JSON object whose top-level `vesqira` block has `"record": "vesqira-run-record"` (the script cannot parse JSON, so this is Go's check). A file that is not Vesqira's is refused (`foreign`), a larger one is refused (`toolarge`), nothing changes. The script then receives the sha256 of the bytes that were read, or `-` for "must not exist", and refuses (`changed`) if the file differs at the moment of the write. Callers that built the new text from a read (the project routes) pass the hash of exactly those bytes, so an edit made on the host between their read and the write is not overwritten; for `run.json` the read is repeated inside `WriteFile`. For project.toml this means a file the researcher wrote, or from which they removed the line, is left alone: answers stay in the catalog with a note, and the project-file route answers 409. This is stricter than a local project, where answers are appended to a hand-written file; on a host the risk is higher (the file may be shared, no undo) and the cost of the stricter rule is a note.
- **Atomic and verified.** The script stages stdin in a private 0700 folder made inside the deepest existing folder and refuses (`truncated`) unless its `wc -c` byte count and sha256 equal the ones Go computed, so a stream cut mid-way (the remote `cat` exits 0 at EOF) never reaches the target. It then renames the staged file over the target (atomic on one filesystem). The staging folder is removed on every refusal. The digest is `sha256sum`, else `shasum -a 256`; with neither the script refuses (`nosha256`, "the host has no sha256sum or shasum") before touching anything. The window between the hash check and the rename is not closed (another process of the same account could change the file in between); accepted, because both folders are the researcher's own and no lock exists on a shared filesystem.
- **Modes.** The umask is not overridden and nothing is chmod-ed. A new file gets the account's default mode (the redirect that stages it applies the umask). A replacement is a copy of the old file made with `cp -p` (POSIX, portable, no `stat` or `chmod --reference`) overwritten in place, so it keeps the old file's mode; a file that is not writable is refused (`readonly`) rather than made writable.
- **Audited.** `project file written on host`, `project file write on host refused`, `run record written`, `run record not written`, each with the host name and path.
- **Never git.** Vesqira does not stage, commit or touch `.gitignore`; the health list still suggests ignoring `.vesqira/`.
- **The run record is `run.json`**, a format discovery already reads (top-level or `settings` entries are the run's settings). Its only top-level keys are `settings` and the `vesqira` block, because discovery would show any other top-level scalar as a setting. `settings` are the flat scalars of the config inside the submitted script (`section.key`), the analysis operation and options, and the Slurm resources, i.e. what the script says, not what the program ended up using. The `vesqira` block holds the job (id, name, template, Slurm id, script SHA-256, host, submit and finish times), the state, the input references, the code identity, and a `provenance` map that labels each fact per invariant 7: settings and inputs `declared` (inputs are paths, never hashed), script hash and Slurm id `verified` (computed or returned by sbatch), code `unresolved` (the repository commit on the host is not read; `commit` is `null`). No start time or commit is written at the top level. Completion is not scientific validity (invariant 9).
- **State says where it came from.** `state` has `value`, `as_of` (when the state was obtained, not when the record was written; `written_at` is separate), `source` and a provenance label. Right after sbatch: value `submitted`, source `sbatch returned job id <n>`, label `verified: sbatch returned this job id at as_of; the job's progress has not been read since ...`. After a refresh: source `reported by squeue/sacct on the host`, label `verified: reported by squeue/sacct at as_of; not a scientific validation`. After an unconfirmed submission is found on the host: source `found by squeue/sacct ...`. The `as_of` of a record written later (a retry, a terminal job) is the time the state was read.
- **When.** Submit: the Slurm id is known and the answer is returned at once; the record is written afterwards in a background goroutine with its own 3-minute bound (read plus write, each bounded), and the job's detail line and the audit log say if it failed. The record is written only once the job's output folder exists, since Vesqira never creates it: at submit if the folder is already there, otherwise on the first refresh that finds it (the job has started). It is rewritten when a refresh first sees a terminal state (completed, failed, cancelled), not for intermediate states. The job carries a persisted debt (`jobs.record_owed`, schema 5): set when a write is started, cleared when the record is written or refused for a reason retrying cannot cure (link, file in the way, foreign or oversized file, read-only, no sha256 tool, folder outside the roots, or a finished job whose output folder never appeared). A missing folder on a running job, a file that changed meanwhile, a cut stream, a temporary folder that could not be made, or an unreachable host leave it owed (silently for a missing folder, audited otherwise), and every refresh retries, including for a job that is already finished (written from the stored end state, with no squeue call). A failed write never fails the submission (the job is already in Slurm): it is audited and the detail line says `run.json not written next to the outputs (reason)`.
- **Local analyses write no run record**: they produce a single FITS file in the derived folder, not a run directory, and are described by the catalog's own derived record. A local project's file is unchanged (ADR 0030).

## Alternatives
- **A dedicated daemon or the host worker writes.** Rejected: the worker deliberately reads only; giving it write access would widen the one process the roots protect, and a new channel is a new credential path.
- **sftp/scp.** Rejected: a second protocol with its own quoting and no atomic rename guarantee across servers; the shell script path is already trusted and tested.
- **Append to a foreign project.toml (as local does).** Rejected for now as above; revisitable with compare-and-swap on a content hash if researchers ask.
- **`provenance.json` as the record name.** `run.json` chosen: `provenance.json` is a convention other tools write into the same folders, which makes a collision (and a "foreign" refusal) more likely, and the VGT pipeline's own `run_metadata.toml` takes precedence over both in discovery.
- **Create the output folder so the record can be written at submit.** Rejected: the folder is the job's, a pre-made one could change how the pipeline behaves, and Vesqira would be writing outside what it was asked to.
- **Write the record before sbatch.** Rejected: the Slurm id is not known and a failed submission would leave a record of a job that does not exist.

## Consequences
- The researcher's cluster folders gain `.vesqira/project.toml` (confirmed) and `<output>/run.json` for every submitted VGT or analysis job. Both are inert to other programs. Whether the VGT pipeline tolerates a pre-existing file in its output folder is not verified here; it writes its own `run_metadata.toml`, which discovery prefers to `run.json` once present, so for VGT runs the Vesqira record is the full story only until the run finishes and stays as provenance beside it.
- A job whose output folder is not under a root has no record (the job form already requires it inside a root).
- Rescanning a project on a host after the record exists finds the run with settings (`readRecord`); no new route and no new client types.
- The worker's `walk` refused a null `skip_globs`, which made a remote project with no skip list unscannable; fixed in the same change (the globs are sent as an empty list).

## Validation
Go tests with a stand-in ssh that runs the remote command locally. `hosts/write_test.go` and `hosts/write_safety_test.go`: create, replace its own file, no temp left; umask 077 gives 0600 and a replacement keeps the old mode; a read-only file is refused; a stdin cut short is refused with the original intact and no folder or temp left; no sha256 tool is refused clearly, and `shasum` alone works; a file that changed, appeared or vanished after it was read is refused unchanged; no folder is made without `Create` or when a later check refuses; the scripts contain no newline, quote, backslash or `!`; backslash, NUL, newline and CR in a name are refused; the marker must start the first line; a custom recogniser decides ownership; `ReadExisting` reports absent, exact bytes, too large and links; refuse a foreign file, a directory or link target, a link out of the folder, `..`, absolute and slash names, a missing marker, a root that is gone; hostile root, folder, file and marker with spaces, quotes, `$(...)`, backticks and `;`, and an option-like marker, proving no command ran. `server/projects_remote_test.go`: project.toml written after confirmation, foreign file refused on both routes, answers appended, link never written through, audit counts. `server/runrecord_test.go`: no output folder is created at submit and the debt is kept; the record is written on the first refresh after the folder exists and read back by `discover.Scan` with its settings and no claimed commit or start time; the final state is rewritten at completion; a foreign run.json, or one that only mentions the marker, is untouched with the job saying so; a linked parent is not written through; audit; at submit the state source is "sbatch returned job id"; `as_of` is the obtained time, not the write time; the submit answer precedes the record; a failed terminal rewrite is retried on the next refresh and then settled; the run.json and project.toml ownership rules; an analysis record round trip. `schema/recordowed_test.go`: the migration. Background writes are awaited in tests through a `WaitGroup`, with no sleeps. **Not verified:** a real ssh host and a real Slurm cluster (login-shell banners, BusyBox or BSD `head`/`mktemp`/`mv`, NFS rename behaviour, a VGT run in a folder that already holds `run.json`).

## Rollback / Migration
Schema 5 (`jobs.record_owed`, migration "run record owed", snapshot `testdata/schema_v5.sql`); an upgrade copies the catalog aside first, and an older build refuses a version 5 catalog (see ADR 0020). Remove the two `WriteFile` call sites (`server/hostwrite.go`, `submitJob`, `checkSubmitting`, `refreshJob`) to go back to read-only hosts; files already written stay and are inert. Delete `.vesqira/project.toml` or `run.json` on a host by hand at any time; Vesqira will not recreate a project file without a new confirmation.

## Note: run.json for ROHSA jobs, and one cache write that is not this mechanism (ADR 0046)
- `run.json` is now written for ROHSA jobs as for the others (same `WriteFile`, same checks). Its `vesqira.job` block gains `output_dir`, and the settings of a ROHSA job are read from the config the script embeds (`cat > "$config"`; a list of one, `n_gauss = [16]`, is that value). The earlier reason for leaving ROHSA out (a rescan would list the folder as a second run) is gone: discovery merges a ROHSA job's record with the fit it produced (`discover.mergeJobRecords`, ADR 0046).
- "The worker deliberately reads only" is no longer exact. The host's worker writes one thing: the index of a ROHSA `.dat`, a rebuildable cache in the account's own `~/.cache/vesqira/rohsa`. It is not a research-data write and does not use `WriteFile`: that path replaces one whole small file, reads at most 200 000 bytes of what is there and is audited per file, while the index is 8 bytes per pixel appended over many bounded calls. The exception, its limits and its audit are in ADR 0046 ("A fit on a host"); it never writes under a source root or next to the data.
