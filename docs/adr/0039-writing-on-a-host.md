# ADR 0039: Vesqira writes two small files on a host, and nothing else

Status: **proposed; implemented, awaiting owner review.** Decided by the implementing agent under the owner's delegation of ADR decisions (roadmap Stage W). Real-ssh behaviour is not verified (see Validation).

## Context
ADR 0030 left two things open for a project or a job that lives on another machine: a project opened on a host could not get its `.vesqira/project.toml` ("an external write that needs its own authorization"), and a job submitted through Slurm left no record of what it was asked to do next to its outputs, so a rescan of the folder found a result with no settings. Both are writes on the researcher's own account, on a machine Vesqira reaches only through the researcher's own ssh configuration. AGENTS.md requires such a boundary to be documented, authorized, audited, and never to alter what the researcher or another program made.

## Decision
- **Two files, one mechanism.** `hosts.Manager.WriteFile` is the only way Vesqira writes on a host. It runs one fixed `sh` script through `RunShell`, the path every other host command takes (the user's `ssh` binary, config and agent; no new credential, no new connection, no new port). The script is a constant; the root, folder, file name and marker reach it as positional arguments, each single-quoted by the same `quote` the other remote commands use (embedded quotes become `'\''`) and used only inside double quotes. The content goes on stdin. Nothing caller-supplied is ever concatenated into shell text.
  1. `.vesqira/project.toml` in a project folder, after the same explicit confirmation a local project uses (`write: true` on the project-file route, or an answer with `write` or an existing file).
  2. `run.json` in the output folder of a job Vesqira submitted (VGT and analysis jobs, which are the templates that name an output folder).
- **Where it may write.** The root must lexically be inside one of the host's source roots (`Host.InRoots`; for a project, the project folder is itself a root; for a job, the root that holds its output folder). On the host the script resolves the root (`pwd -P`), creates the relative folder one component at a time and refuses a symbolic link or a file at any step, checks that the resolved folder is still inside the resolved root, and refuses a link or a non-regular file at the target. File names are one plain name (no `/`, not `.` or `..`, no NUL).
- **Never clobber a foreign file.** Every file carries a marker (`# Written by Vesqira` as the first line of project.toml; `"record": "vesqira-run-record"` in run.json) that the content must contain (checked before sending). An existing target is replaced only if its first MiB contains the marker; otherwise the host refuses (`foreign`) and nothing changes. For project.toml this means a file the researcher wrote on the host, or from which they removed the line, is left alone: answers stay in the catalog with a note, and the project-file route answers 409. The researcher keeps control by deleting the file (then Vesqira may write one) or keeping their own. This is stricter than a local project, where answers are appended to a hand-written file; on a host the risk is higher (the file may be shared, no undo) and the cost of the stricter rule is a note.
- **Atomic.** The script writes a temporary file in the same folder and renames it over the target, so a reader (or a rescan) never sees half a file. A leftover temporary file is removed on failure. The window between the marker check and the rename is not closed (another process of the same account could create the file in between); accepted, because both folders are the researcher's own and no lock exists on a shared filesystem.
- **Audited.** `project file written on host`, `project file write on host refused`, `run record written`, `run record not written`, each with the host name and path.
- **Never git.** Vesqira does not stage, commit or touch `.gitignore`; the health list still suggests ignoring `.vesqira/`.
- **The run record is `run.json`**, a format discovery already reads (top-level or `settings` entries are the run's settings). Its only top-level key is `settings`, because discovery would show any other top-level scalar as a setting; everything else sits in a `vesqira` block. `settings` are the flat scalars of the config inside the submitted script (`section.key`), the analysis operation and options, and the Slurm resources, i.e. what the script says, not what the program ended up using. The `vesqira` block holds the job (id, name, template, Slurm id, script SHA-256, host, submit and finish times), the state with the time it was read, the input references, the code identity, and a `provenance` map that labels each fact per invariant 7: settings and inputs `declared` (inputs are paths, never hashed), script hash, Slurm id and state `verified` (computed or reported by the scheduler), code `unresolved` (the repository commit on the host is not read; `commit` is `null`). No start time or commit is written at the top level, so discovery does not show either as declared. State carries the text that completion is not scientific validity (invariant 9).
- **When.** Written right after sbatch returns an id (settings known), also when a "submitting" job is later found on the host, and rewritten once when a refresh first sees a terminal state (completed, failed, cancelled). Not rewritten for intermediate states (not cheap enough to justify a round trip each refresh). A failed write never fails the submission (the job is already in Slurm): it is audited and the job's detail line says `run.json not written next to the outputs (reason)`.
- **Local analyses write no run record**: they produce a single FITS file in the derived folder, not a run directory, and are described by the catalog's own derived record. A local project's file is unchanged (ADR 0030).

## Alternatives
- **A dedicated daemon or the host worker writes.** Rejected: the worker deliberately reads only; giving it write access would widen the one process the roots protect, and a new channel is a new credential path.
- **sftp/scp.** Rejected: a second protocol with its own quoting and no atomic rename guarantee across servers; the shell script path is already trusted and tested.
- **Append to a foreign project.toml (as local does).** Rejected for now as above; revisitable with compare-and-swap on a content hash if researchers ask.
- **`provenance.json` as the record name.** `run.json` chosen: `provenance.json` is a convention other tools write into the same folders, which makes a collision (and a "foreign" refusal) more likely, and the VGT pipeline's own `run_metadata.toml` takes precedence over both in discovery.
- **Write the record before sbatch.** Rejected: the Slurm id is not known and a failed submission would leave a record of a job that does not exist.

## Consequences
- The researcher's cluster folders gain `.vesqira/project.toml` (confirmed) and `<output>/run.json` for every submitted VGT or analysis job. Both are inert to other programs. Whether the VGT pipeline tolerates a pre-existing file in its output folder is not verified here; it writes its own `run_metadata.toml`, which discovery prefers to `run.json` once present, so for VGT runs the Vesqira record is the full story only until the run finishes and stays as provenance beside it.
- A job whose output folder is not under a root has no record (the job form already requires it inside a root).
- Rescanning a project on a host after the record exists finds the run with settings (`readRecord`); no new route and no new client types.
- The worker's `walk` refused a null `skip_globs`, which made a remote project with no skip list unscannable; fixed in the same change (the globs are sent as an empty list).

## Validation
Go tests with a stand-in ssh that runs the remote command locally: `hosts/write_test.go` (create, replace own file, no temp left, refuse foreign file, directory or link target, refuse a link out of the folder, refuse `..`, absolute, slash names, missing marker, a root that is gone; hostile root, folder, file and marker with spaces, quotes, `$(...)`, backticks, `;`, newline, and an option-like marker, proving no command ran), `server/projects_remote_test.go` (project.toml written after confirmation, foreign file refused on both routes, answers appended, link never written through, audit counts), `server/runrecord_test.go` (record on submit read back by `discover.Scan` with its settings and no claimed commit or start time, final state rewritten at completion, a foreign run.json untouched with the job saying so, a linked parent not written through, audit; an analysis record round trip). **Not verified:** a real ssh host and a real Slurm cluster (login-shell banners, BusyBox or BSD `head`/`mktemp`/`mv`, NFS rename behaviour, a VGT run in a folder that already holds `run.json`).

## Rollback / Migration
No schema change. Remove the two `WriteFile` call sites (`server/hostwrite.go`, `submitJob`, `checkSubmitting`, `refreshJob`) to go back to read-only hosts; files already written stay and are inert. Delete `.vesqira/project.toml` or `run.json` on a host by hand at any time; Vesqira will not recreate a project file without a new confirmation.
