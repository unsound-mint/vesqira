# ADR 0039: Unit conversions and frame transforms in the viewer's readout

Status: **proposed; implemented, awaiting owner review.** (Roadmap stage 4, Q204 and Q209.)

## Context
The readout showed a spectral value in the file's own unit (m/s, Hz), a pixel value in the file's `BUNIT`, and sky positions in the file's celestial frame. Researchers read the same cube in km/s, GHz or Galactic coordinates. The risk is not the arithmetic, which astropy does, but the premises: a velocity needs a rest frequency and a convention that FITS only sometimes states, Jy/beam and K are related only through a beam and a frequency, and a file with no `RADESYS` still has a frame (by the FITS default) that must be said. Declared units (ADR 0038) must keep their "declared by you" label through a conversion.

## Decision
- **The worker converts, the UI selects.** Two new worker operations in `services/scientific-worker/convert.py`: `conversions` (what the file allows, and why the rest is not) and `convert` (for one pixel and channel: native value beside converted value, with the basis, or a refusal reason). Routes `GET /api/datasets/{id}/conversions` and `/convert?x&y&channel&spectral&convention&frame&to&value`. The API validates the request (unit text by `catalog.ValidUnit`, closed lists for convention and frame, finite value) and refuses a brightness conversion of an orientation map (409). The browser sends the pixel value it already holds, so the plane is not read again.
- **Spectral axis (astropy.units equivalencies only).** Targets: Hz, kHz, MHz, GHz, m, cm, mm, um, m/s, km/s. Frequency and wavelength convert with `spectral()` and need nothing else. A velocity needs a rest frequency from the file (`RESTFRQ`, else `RESTFREQ`, else `RESTWAV`; the card used is reported). For a velocity axis (`VRAD`, `VOPT`, `VELO`) the file's convention is used and a different one is refused. For a `FREQ` or `WAVE` axis the file states no convention, so the person must pick radio, optical or relativistic; the picker starts on radio, the request carries it, and the readout says "chosen by you". Without a rest frequency the velocity (or, for a velocity axis, frequency and wavelength) options are disabled with the reason. `AWAV` (needs a refractive index) and legacy `VELO-LSR` spellings are not converted.
- **No reference-frame change.** `SPECSYS` is reported and never altered; the controls say that a frame change such as TOPOCENT to LSRK is out of scope (a real implementation needs observatory, epoch and direction, and is a later decision).
- **Brightness.** Only within one dimension (`K`, `mK`, `uK`; `Jy/beam`, `mJy/beam`, `uJy/beam`) with astropy units, or Jy/beam with K through `astropy.units.brightness_temperature` (Rayleigh-Jeans), only when `BMAJ` and `BMIN` are in the header and the plane's frequency is known from the spectral axis (a velocity axis goes through the rest frequency and its convention). The beam solid angle is the Gaussian definition from the two FWHMs (2 pi sigma_maj sigma_min, sigma from astropy's `gaussian_fwhm_to_sigma`); this one line is the only math not delegated, and it is checked in tests against a separately written closed form. No beam, no frequency, an unrecognised unit, an incompatible dimension (K to km/s) or no unit at all is refused with its reason; with no unit nothing is offered. A declared unit (ADR 0038) converts and the converted value is labelled `user` the same way. A unit astropy does not recognise is never guessed.
- **Sky frame.** ICRS, FK5 (J2000) and Galactic, by `SkyCoord` from the file's frame built with `wcs_to_celestial_frame` (RADESYS/EQUINOX/CTYPE). The native frame is reported with its status: `declared`, `inferred` (RADESYS absent, taken from EQUINOX) or `assumed` (neither present: wcslib's FITS-standard default, ICRS, said in the readout even when no conversion is chosen). A request for the frame the file already has returns the native numbers unchanged. Ecliptic and other frames are not sources or targets.
- **Native values stay.** The native rows are never replaced; converted values are extra rows with the basis (formula, rest frequency and its card, convention and who chose it, beam, frequency) in the same list.

## Alternatives
- **Convert in the browser.** Rejected: unit and frame arithmetic belong to a validated provider, and the browser would need the beam, rest frequency and frame to do it.
- **Default to the radio convention silently.** Rejected: the file does not state one for `FREQ`; a default would be an invented premise. The UI preselects radio but the choice is visible and reported as the person's.
- **Compute the beam area with a library (radio_beam).** Not installed here; adding a dependency for one formula is not worth it yet. Revisit if beams with other shapes are needed.
- **Convert the whole plane.** Deferred: this slice is the readout only; figures, histograms and exports still use the native unit.

## Consequences
- Two read-only routes, no schema change, no change to stored data. `convert.py` is a new worker file: it is deployed with the worker to remote hosts (`main.go`, the RPM script) and the remote-host tests copy it.
- `bodies.json` has no entries for the new routes (routes only, like `coord`); the web types for them are written by hand in `api/planes.ts` until bodies are described.
- Not done: figures, plane display and spectrum plot in the converted unit; the compare view's second pane; other brightness units (K km/s, Jy/pixel, MJy/sr); beam from `CASAMBM` tables or per-channel beams; pixel values of a reduced preview.

## Validation
`services/scientific-worker/test_convert.py`: HI 1420.405751768 MHz is 0 km/s (radio) both ways; a 1420.0 MHz channel gives the radio, optical and relativistic velocities of closed forms; 60 arcsec beam at 1.42 GHz, Jy/beam to K against the closed form and against astropy's equivalency, round trip and per-channel frequency; refusals (no rest frequency, no beam, half a beam, no spectral axis, unknown or unrecognised unit, K to km/s, AWAV, legacy VELO); a declared unit converts and stays `user`; Galactic centre (266.405, -28.936) ICRS gives l, b near 0; FK5, FK4 (inferred from EQUINOX) and Galactic sources against astropy; an undeclared frame is "assumed". `convert_test.go` (real worker end to end, orientation map 409, malformed requests never reach the worker, the declared unit travels and keys the cache), `convert.test.tsx` (offers, disabled reasons, convention picker, converted rows and labels, state handling). Not verified: the pixels of the controls in a real browser at the three viewport sizes beyond the e2e run recorded with the change.

## Rollback / Migration
Remove the two routes and `convert.py`; nothing is stored. An older web client never calls the routes.
