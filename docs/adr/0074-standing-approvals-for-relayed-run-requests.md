# ADR 0074: Standing approvals for relayed run requests

- Status: implemented (schema 37); decided under the owner's delegation, the owner reviews it afterwards
- Date: 2026-11-13 (amended 2026-11-14)
- Related: ADR 0016 (approval binds to the script hash), 0048 (sweeps), 0050 (group server; deferred "preapproved templates and budgets"), 0054 (strict rerun pins the commit), 0066 section 3 (relayed run requests), 0068 slice 5 (run templates, declared keys, the commit pin)

## Context
Since ADR 0066 slice 5 a collaborator without cluster access files a run request on the group server, the key holder's own computer pulls it, renders it into a draft with the shipped template, and the key holder reads the exact script and approves it. Every request needs that click. For a trusted labmate who runs the same configuration with a few settings changed, week after week, the click is friction without information: the key holder approves the same kind of script each time. ADR 0050 deferred "preapproved templates and budgets for trusted collaborators" and roadmap Stage 7 lists it as the last open item.

What must not change: the SSH key and the cluster account stay on the key holder's computer; the group server never sees a script, path, host or Slurm id; the script that runs is the one the shipped template renders; the key holder's computer validates every request itself and never trusts the server's claim that it is acceptable.

## Decision
**A standing approval (a grant) is a record on the key holder's computer that lets one named collaborator's requests be submitted without a per-request click, inside narrow terms and a budget.** The computer re-checks every term for every request; the group server only carries the request and the grant's id.

### What a grant holds (local table `relay_grants`)
- **Who.** One collaborator, by the group server's account id (never the display name, which can change or collide). The key holder chooses from the workspace's members, which the computer asks the group server for with its relay token (`GET /api/relay/members`, account id and name only), so the id is one the server knows. The requester's account id travels on the pulled request only when the request names a grant (`requesterId`, omitted otherwise, so a page without grants is byte for byte what an older computer decodes).
- **Where and what.** One inbox label (and the host it stands for when the grant is made; if the label is later pointed at another host the grant no longer applies), one template (`vgt` or `rohsa`), the profile label at creation, and one code commit: the profile's pinned commit, or a 40-character commit the key holder types (for example the commit of their own recent runs). A relayed draft already insists on the base run's commit when the base recorded one (ADR 0054, ADR 0066 slice 5), and that is never replaced. When the base gives no commit, a draft rendered for a request that names the grant takes the grant's commit (the profile's pin, or the typed commit as the expected revision), and the draft view says so. A granted draft is submitted only when the commit its script insists on equals the grant's commit; a base that insists on another one waits for the key holder.
- **Which settings.** A list of keys, each narrowed to a numeric range (both ends given) or a choice list. Every key must be settable by a request (`relay.Settable`), must be in the label's inbox for that template, and its range must lie inside the template's own declared range and inside the inbox bound; every choice must pass the template's validator and the inbox bound. Never wider. A key the grant does not list is outside it. The terms are checked against the template as loaded now both when the grant is made and when it is used.
- **Inputs.** A request never names an input; the input comes from the base run's job (ADR 0066). The grant lists input folders and exact files on the host (at most 16), each an absolute, clean path (`jobs.ValidPath`, `path.Clean(p) == p`, not `/`) inside one of the host's source roots. When the grant is made, the host's worker resolves each folder (`canon`, it must be a folder) and each file (`resolve`, refused outside the host's roots), and the grant stores the real paths, which must still lie inside the roots. When a request is checked, the worker resolves the granted draft's input (`jobs.InputPathFor` on the config the draft was rendered from) the same way, and the real path must equal a stored file or lie under a stored folder. Names are not trusted: a collaborator who can write in a granted folder (a shared group folder) could otherwise put a link there to other data the key holder's account reads. A refusal by the worker or a real path outside the grant falls back with `input` and a sentence naming the resolved path; a host that does not answer leaves the request `pending`, never allowed. When the real path differs from the name the draft used, the computer renders the draft again from the same base with the real path written into the config, and checks the new draft in full; the script it submits therefore names the file the check found, and a link swapped after the check changes nothing the job reads. That script is the one whose hash is reserved, claimed, audited and shown afterwards. The request on the group server keeps what the requester asked, and the job note and the request here say "resolved to <real path> on the host". Paths never leave the computer.
- **Budget.** Max jobs in total, max total requested core-hours (CPUs times the time limit, from the rendered draft, because a zero resource in a request means the base's value), per-job maximum CPUs, memory and wall time (each within the inbox label's limit for the template when that limit is set, otherwise within the relay's own maximum), max jobs queued or running at once, and an expiry date (at most 180 days ahead).
- **Revocation.** `revoked_at`. Revoking is immediate and final; a revoked grant is kept for the record.

### When a request goes through a grant
In each relay pass, after the pull, the computer looks at drafted requests that name a grant and have not been decided. A request is submitted under the grant only when all of these hold, in this order:
1. The grant exists on this computer for this group server, is not revoked and has not expired; its collaborator is the request's `requesterId`; its label and template are the request's; the label still stands for the grant's host.
2. The request was filed after the grant was made and has not expired by this computer's clock; it is in `requested` or `waiting_review`.
3. The request has no grid (a sweep waits for the key holder: reserving and approving a whole grid at once is a later decision), and every setting it changes is a key of the grant, inside the narrowed range or choices.
4. The base resolved by itself through this computer's own push records (a base the key holder must choose waits for them), and the draft was rendered from it with no change and no hand edit by the key holder.
5. The draft's input, resolved on the host, is inside the grant's folders or files; its CPUs, memory and wall time are within the per-job caps; its script insists on the grant's commit.
6. The budget takes it: one conditional `INSERT … SELECT … WHERE` statement checks revocation, expiry, jobs used, core-hours used plus this job, and the jobs not yet ended, and writes a use row. `UNIQUE(relayed_id)` on the use rows means one request takes at most one slot, whatever replays or retries. SQLite runs the statement atomically, so two requests at once cannot both take the last slot.
7. The claim on the group server, bound to the rendered script's hash and carrying the grant id, succeeds (the same one-winner claim as a manual approval). A claim that is refused (withdrawn, expired, gone) gives the slot back. A server that does not answer gives the slot back and the next pass tries again.
8. `submitDraft` submits the exact script, as a manual approval does. When step 5 rendered the draft again with the real input path, steps 1 to 5 ran again on that draft first.

The claim-and-submit core is shared with the manual approval (`approveRelayed`), so both submit the same way. The pass and the manual approval hold the same lock; revocation does not (see the amendment of 2026-11-14), so it reads the grant again just before `sbatch`.

**Anything outside the grant falls back to the normal manual approval and says why.** The draft stays a draft, the key holder sees "Waiting for you: outside the standing approval: <reason>", and the reason is kept on the mirror. Toward the group server only an enumerated code crosses with the review (`unknown`, `revoked`, `expired`, `stale` for a request filed before the grant or already expired, `outside`, `grid`, `base`, `input`, `commit`, `budget`, `edited` when the key holder changed the draft), shown to the collaborator as a fixed sentence, never the computer's own sentence (which could name a path). Two states are not verdicts and send no review yet: `waiting`, when the jobs-at-once limit is full (tried again each pass, and the slot frees when a job under the grant ends), and `pending`, when the group server did not answer the claim (the slot is given back and the next pass tries again). The key holder can approve either by hand.

**After the fact.** Every auto-submission writes an audit row ("run request submitted under a standing approval", with the request, the grant id, the job and the script hash); these rows are not subject to the refusal audit budget. The job's note says which grant allowed it. The key holder's inbox lists the request as "submitted under standing approval <id>", and its detail shows the exact script that ran, as for a manual approval. The group server's approval record names the grant.

**Revoking.** Revoking stops further submissions at once: the next request naming it falls back with "revoked". Jobs already queued or running under it are listed in the answer and on the grant, never cancelled by Vesqira; cancelling stays the key holder's act.

### The group server
- The key holder's computer publishes, with its inbox, an **offer** for each live grant: id, collaborator id, label, template, the narrowed keys, the per-job caps, the budget and what was used when it was published, the expiry. No path, host, commit or root. A use or a revocation marks the inbox for publishing again.
- `GET /api/run-inboxes` shows each member only the offers made to them.
- Filing with a grant id is refused (422) unless the addressee's published inbox offers that grant to the filer for that label and template, and it has not expired. The server stores the grant id on the request.
- `POST /api/run-requests/preview` tells the collaborator before sending whether the request fits an offer ("will go through standing approval <id>, unless the key holder's computer finds the base run's input, its code commit or the budget outside it") or will wait for review, and why. The preview also refuses (422) a base the filer cannot use, as filing does. It is advisory: the server sees neither inputs nor the live budget.
- A claim that names a grant is accepted only when it is the grant the request was filed under. The server records the claimed script hash as it does for a manual approval; it never compares it with anything the requester sent (the requester never sees a script), so the hash of a draft rendered again with the real input path needs nothing new on the server.

### Limits stated, not solved
**(c) What the job reads beyond the named input is read as found at run time.** The submitted script names the input by its real path, so a link swapped after the check cannot redirect it, but the job itself is not confined: if the tool reads a folder, or other files next to its input, it reads whatever is there when it runs. A collaborator who can write in a granted folder can change the files inside it, and can replace a folder on the real path with a link after the check. The host roots are enforced by the worker only on Vesqira's own reads, not on the job's. A grant on a folder the collaborator can write therefore trusts them with what lies there, which is why a grant names folders narrowly. The same holds for the code that runs: a person who can write in the run's code folder, or in the Julia depot the templates keep inside it (`{{repo}}/.julia-vesqira`), can plant untracked code that runs as the key holder, and the commit pin does not see it (it checks tracked files). So a grant is refused when the code folders of the key holder's own runs of that template on the host, or their depots, are writable by group or others, and a request is refused at use when the code folder of its base run is (the host's worker answers with the permission bits of the path itself, op `modes`). The check does not cover the files inside the folder or the folders above it; a shared parent directory that others can rename in is not found.

**(a) The key holder's computer cannot verify who filed a request.** It trusts the group server for the requester's identity, as every relayed request does. A compromised group server can forge requests in the grantee's name that fit the grant, and the computer will run them. A forged request also chooses the base run (from the grantee's pushed runs on that server), and the base supplies what the grant does not list: every setting a request does not change, the Slurm partition and account, and the code folder. When the job ends its outputs are pushed back to that same server. The grant bounds the rest: only the grant's keys and ranges, only its inputs, only its commit, and at most its budget before it expires. That is why a grant has a budget and an expiry, and why it is narrow by construction. Forged, expired, revoked and another person's grant ids are refused by the computer. A possible later step is to pin the base runs a grant may start from, so a forged request cannot pick another one; it is not built.

**(b) A replayed or duplicated request is a liveness and compatibility matter, not a replay risk.** The mirror of a request is unique by (origin, server id), a use of a grant is unique by request (`relayed_id`), and the pass decides only requests that are received or drafted and not yet decided. A server that sends a request again, or a second request with the same content, therefore cannot make this computer submit one request twice; it can only make requests wait, or use up the budget with distinct requests, which (a) bounds.

### Amendment, 2026-11-14: findings of the security review
- **D1. The hash that was checked is the one submitted.** The pass kept the hash it checked, reserved, claimed and audited, but reloaded the draft before submitting and passed the reloaded hash, so `submitDraft`'s comparison could never fail, and an edit of the draft between the claim and the submission (the edit route does not take the pass's lock) would have sent another script. Now the checked hash is passed, and a draft whose hash changed is not submitted: the request is marked `stopped` with the sentence that the draft changed after it was checked. The claim on the server names the checked script, so a manual approval of the changed draft is refused; the key holder detaches the draft as their own job or declines the request.
- **D2. A refusal before Slurm does not hold a slot.** A submission refused before `sbatch` (too many active jobs, a strict-rerun refusal, an automatic import the template cannot do, a revoked grant, a changed draft) used to leave the use open, so the jobs-at-once slot stayed taken for good. A refusal for "too many jobs queued or running" now leaves the use open and is tried again at the next pass, at most 5 attempts in all, the count kept in the request's note; after that, and for every other refusal before `sbatch`, the use ends and the request is `stopped` with the reason. Ending a use frees the slot only: the claimed job and its core-hours stay counted, as before. A job that reached `sbatch` without a confirmed answer keeps its use open until it ends.
- **A. The filing time.** The check that a request was filed after the grant was made also compares the time this computer first stored the request with the grant's creation, because the `createdAt` the server sends can be forged. Both must be later than the grant.
- **H1. Revoking does not wait for a pass.** A pass holds the relay lock for all its requests (a host that does not answer costs a 60 second timeout per call). Revoking now writes `revoked_at` without that lock; reserving a slot reads it in the same statement, and the pass reads it again just before it sends a reserved draft. A request whose slot was taken before the revocation is then not submitted and ends `stopped`. A submission already inside `sbatch` cannot be recalled. A host that did not answer once in a pass is not asked again for the rest of that pass.
- **H2. The input is read the way the tool reads it.** A template that edits by name (ROHSA) reads its input key in any table, not only `[input]`. The grant check now reads the key across all tables (outside the template's guard table) and falls back to the key holder when the config names it in more than one place.
- **C. Writable code folders.** See limit (c): `modes` is a new read-only worker op that reports the permission bits of absolute paths, answered outside the source roots like `canon`.
- **State.** `stopped` is a new grant state on the mirror (contract enum): claimed on the group server, not submitted, the note says why. It is never sent to the server.

## Alternatives
- **The computer picks a matching grant itself and the request names none.** Smaller wire, but the collaborator would not know before sending whether a request goes through, and the audit could not say what the requester asked for. Rejected.
- **Grants held by the group server.** Breaks the rule that the server's word is never trusted; a compromised server could widen a grant. Rejected.
- **Budget as a counter column updated after submission.** A counter decremented after `sbatch` races; the conditional insert of a use row is one statement and leaves a record of each use. Chosen.
- **Grids under a grant.** Reserving N slots and approving a sweep without a click is possible, but doubles the paths to test. Deferred; a grid waits for the key holder.
- **Cancelling queued jobs on revocation.** Rejected: a revocation is about future requests, and cancelling someone's running work silently is the kind of irreversible act Vesqira leaves to a person.

## Consequences
- A trusted collaborator's routine request runs without the key holder at their computer, on the key holder's account, within terms the key holder set.
- The key holder must look afterwards. The inbox shows every auto-submitted request with its script; the audit log has the row.
- A compromised group server can spend a grant's budget. It cannot exceed it, change the code commit, choose inputs outside it, or set keys outside it.
- One more local table pair and three columns; two server columns.

## Validation
- `internal/relay/grants_test.go`: grant terms validation (a range wider than the template's or the inbox's, a missing end, a choice the template refuses, an unsettable or unlisted key, a path that is not clean or outside the host's roots, `/`, budget and expiry bounds); the fit of an ask (a key outside the grant, a value outside the narrowed range, a grid); the budget under concurrency, run with `-race`: many goroutines reserving against one remaining job, and against core-hours that admit exactly two, exactly that many win; a second reservation of the same request takes nothing; a revoked or expired grant reserves nothing.
- `internal/server/relay_grant_test.go` on the relay end-to-end setup of ADR 0066 (TLS group server, local instance on the stand-in Slurm host, every ssh command logged): a granted request is submitted exactly once with no click, the claim carries the rendered hash and the grant id, the audit row and the job note name the grant, the server's record names it; a request outside the grant (key, range, resources) waits as a draft with the reason; a forged grant id, an expired grant, another person's grant and a revoked grant fall back; an input outside the grant's folders (including a path with `..` in the base config) falls back; a link in a granted folder that points out of the grant falls back with the resolved path in the reason and only the code on the wire, a link to another place inside the grant goes through, a grant made through an alias of its folder is stored resolved, a granted file that links out of the host's roots is refused at creation, and a host that does not answer leaves the request pending until it answers; the submitted script names the real path of a linked input (not the link), the hash claimed on the server and kept here is that script's, both notes say where the input resolved, and swapping the link afterwards does not change the submitted script; a commit other than the grant's falls back; the budget stops the next request; a replayed page does not submit again; a request filed before the grant was made falls back; a compromised server's forged in-grant requests stop at the budget; revocation lists the running job and cancels nothing; filing with a grant not offered is refused and the preview says which way a request goes; the wire carries no path, host or commit in the offer.
- `e2e/tests/zzzzzzzzzzzz-standing-approvals.spec.ts`: the "Standing approvals" section and the collaborator's preview, rendered against stubbed API answers (the Playwright stack has no TLS group server), with axe, keyboard order and screenshots at 1440x900 and 390x844 in light and dark. ## Rollback / Migration
Schema 37 adds `relay_grants` and `relay_grant_uses` on the key holder's computer, `grant_id`, `grant_state` and `grant_note` on `relayed_requests`, and `grant_id` on the server's `run_requests`. Nothing is rewritten. Rolling back the code leaves the tables unused; an older computer ignores them and every request needs a click again. Every grant field on the wire is omitted when empty, so a computer with no live grant talks to an older group server exactly as before. The older server's strict body readers do not know the fields, though: while the key holder has a live grant, an older server refuses the inbox publish (400, shown on the inbox status), and a review or claim that carries a grant code or id. To roll the group server back, revoke the live grants first (or let them expire); requests then need a click again. The added columns stay and are ignored.
