# ADR 0057: Undo and exploration history

Status: **proposed; implemented, awaiting owner review.** Decided by the implementing agent under the owner's delegation of ADR decisions (roadmap Stage 3, "Exploration history and continue from here" Q96 to Q98; Stage 6, "Command registry with undo for board and review edits" Q175). The History section, the Undo and Redo bars and the timeline rows have had no approved design direction and no visual review.

## Context
ADR 0042 made every change to a viewer pane's scene one serialisable action of a pure reducer, "so a command registry with undo can wrap it later". Boards are edited through position-based API calls (add, move, remove, note) with no revision, and a review has comment replies and resolves. AGENTS.md separates ephemeral state (viewer cursor), mutable working state with targeted edit history (drafts, board layouts) and pinned evidence (review snapshots), and forbids making every change an immutable version.

## Decision

### 1. Undo is per surface, bounded, and session-long
- **Viewer pane** (`apps/web/src/undo/sceneCommands.ts`). `commandName` is the one table of command names: each `SceneAction` has a case (a new action cannot be added without deciding its name). `viewerReducer` wraps `paneReducer` and keeps `past` and `future` lists of `{name, key, before, after}`. The inverse is computed from the state before the action: undo takes the scene from `after` back to `before` by changing only what differs between those two (`revert`), so it never reverses an action by hand and a property test over random command sequences checks undo and redo are exact when nothing else happened. What changed in between that is not the command's is kept: a declaration that made the map axial (and its orientation overlay), a linked pane following its partner, the shared-scale group, the worker's spectral value for the same channel; the catalog's `mapping` is never restored. Facts are not commands: the worker's spectral value, the saved-region mirror, the link group, the shared-scale group, and a linked pane following its partner (`dispatchFact`). `revert` also keeps the current saved regions (server rows) and link group; continuing from a history step replaces the whole scene except those two. Commands of the same kind within 800 ms join (dragging a region, scrubbing channels, zooming is one command; one that ends where it began is dropped). Depth 100. A new dataset (`resetForDataset`) clears the stack, as a new scene starts. Primary and compare panes each have their own stack; the keys act on the active pane.
- **Boards** (`undo/boardCommands.ts`, `undo/stack.ts`). One stack per board for the whole session (it survives leaving the board screen; it does not survive a reload), depth 50. Each command is done through the existing API and carries its inverse: add (remove the appended panel), move (the opposite move), remove (add the same figure or run again, move it up to its old place, restore its note), note (set the old note), resolve comment (reopen). Publishing a review has no command: a snapshot is pinned evidence and `revoke` is its own reviewed action. An owner's reply has none either: the reviewer may have read it and there is no delete route. Pinning a finished run's result over its panel is automatic (a system action in `JobPanel`), not an edit; undoing it would only pin again.
- **Conflicts.** The server has no board revision (items are addressed by position), so the position endpoints take an optional `expect` (`kind`, `id`, and optionally `note`: what the client last saw at that position). `POST /api/boards/{id}/items/{pos}/move|remove|note` then check the panel and apply the change in one transaction (`boards.editTx`: its first statement is a write, so the check and the edit see the same state and a second writer waits instead of failing on a stale read). If the panel is not the expected one, or the position is gone, nothing is changed and the reply is 409 `{error, board}` with the board as it is now. Without `expect` the edit is as before (404 for an unknown position), so older clients work unchanged. Undo and redo of a move, a removal, a note edit and the removal that undoes an add send `expect` and turn a 409 into a conflict: the command is dropped with the whole redo stack and the surface shows what happened ("Could not undo “move panel”: the board has changed since... The board was not changed."). `expect` carries the note as plain text, not a hash: notes are capped at 2000 characters, so a hash saves nothing. Putting a removed panel back (`reinsert`) and redoing an add start with an append, which has no position to guard: they still read the board and check its length first, which is not atomic, and a multi-step inverse that fails half way says what it did (the panel was put back at the end). The moves and note of that re-insertion carry `expect` for the panel they act on.
- **Keys.** Ctrl or Cmd+Z undo, with Shift (or Ctrl+Y) redo, on the viewer (when a map is open) and on the board screen. A key aimed at a text field, text area or editor is left to the browser's own undo (a note being typed). Buttons "Undo: <command>" and "Redo: <command>" show the name.

### 2. Exploration history is mutable working state in the catalog
- **What is a step.** A meaningful scene state of the primary pane: dataset opened, channel held 1.5 s, region drawn, overlay added, link changed, or "continued" (below). Zoom, colour map, stretch and limits are not steps; they are in the scene a step stores. `history/recorder.ts` classifies changes, debounces by kind (a later change of the same kind replaces a waiting one; a different kind writes it first, with the scene it had), skips a state equal to the head step, and chains writes so each step's parent is the head when it is sent.
- **Storage.** `exploration_steps` (schema 19; `project_id` 0 is "no project open", `parent_id`, `dataset_id`, `kind`, `label`, `scene` JSON, `at`). The scene is read by the same strict `scene.Parse` a figure's scene goes through, capped at 64 kB, and its base dataset must exist. 500 steps per project; the oldest are pruned in the insert's transaction. `parent_id` is deliberately not a foreign key: pruning must not delete or rewrite descendants, and a step whose parent was pruned is shown as continuing a pruned step. No thumbnail: a step holds a scene, not pixels (a thumbnail would be a rendered copy of data; revisit if cheap and measured). Routes (owner listener only): `GET /api/history?project=`, `GET /api/history/{id}` (one step with its scene), `POST /api/history`. There is no update or delete route.
- **Continue from here** restores the step's scene through the same reducer as one `applyScene` command, so it is undoable, opening the dataset first when it differs. The head moves to that step and a `continued` step is written as its child; later steps branch from it. Nothing after the step is deleted: the timeline lists every step with "branched from "…"" where a step does not follow the one listed before it. A step whose datasets are no longer in the catalog is refused with the ids named.
- **Lifecycle.** Steps are keyed to a dataset (`exploration_steps.dataset_id`). Deleting a dataset deletes the steps that open it (`deleteSteps`), and the impact preview says so (group `history`, "removed"): a step only restores a view, so keeping one that can no longer be opened would be clutter, and it carries no evidence. Steps of other datasets whose overlays name the deleted dataset stay and are refused on continue, with the reason. The guard test `TestEveryKeyedTableIsHandled` passes with `exploration_steps` handled, not allow-listed.
- **Reviewers.** The history holds the owner's dataset ids and what was looked at. The reviewer listener has no history route (`TestReviewListenerHasNoExplorationHistory`) and `internal/review` cannot import the store (`internal/arch`).

## Alternatives
- **A command object with do and undo for every scene action.** More code, and an inverse written by hand per action can drift from the reducer; restoring the previous state cannot.
- **Undo as server state.** The viewer scene is ephemeral; a server round trip per zoom is wasted. Boards' state is on the server, so their commands carry API inverses.
- **Immutable versions of boards and scenes.** Rejected by AGENTS.md: drafts get targeted edit history, evidence gets revisions.
- **Record every scene change as a step.** Floods the list with scrub and pan states; the undo stack already covers those.

## Consequences
- Undo of a board edit is a sequence of API calls, not a transaction. Each guarded step is atomic; the length check before a re-insertion or a redone add is not (another window can append between the read and the append, which at worst puts the panel one place from where it was).
- History is per project and per machine (the catalog), not part of the project folder, and not shared.
- Only the primary pane records steps; the compare pane has undo but no history.

## Validation
- `sceneCommands.test.ts`: exact undo and redo over 60 seeded random sequences of 40 commands, the name table, coalescing, bounds, facts and the preserved mirrors. `boardCommands.test.ts` (inverse API calls in order, conflicts send nothing, partial undo reported) and `boardUndo.test.tsx` (the board screen: buttons, Ctrl and Cmd shortcuts, text fields left alone, conflict message, no undo for publishing). `keys.test.tsx`.
- `recorder.test.ts`, `history.test.tsx` (debounce, branch parents, persistence across a reload as stored steps, continue refusal). Go: `internal/history` (tree, project isolation, pruning, input checks), `internal/server/history_test.go` (routes, validation, lifecycle delete and impact), migration test, schema snapshot v19, reviewer test.
- Browser acceptance in `e2e/tests/zzzz-undo-history.spec.ts`: draw a region and move a panel, undo both, redo; continue from an earlier history step.
- Guard: `boards/expect_test.go` (matching, mismatched, gone, wrong kind or note leave the board unchanged; eight concurrent guarded removes apply once), `server/boards_expect_test.go` (the routes: 409 with the current board and no change, match applied, no `expect` still works, empty remove body, 404 vs 409 for an unknown position), `boardCommands.test.ts` and `boardUndo.test.tsx` (undo sends `expect`, a server refusal is a conflict).
- Not verified: two real browser windows editing one board at the same moment (the race is covered at the store and route level), and the visual design of the new controls.

## Rollback / Migration
Schema 19 adds `exploration_steps` (and an index) and nothing else; an older build ignores the table. Dropping it loses only history. No stored scene, figure or board changes.
