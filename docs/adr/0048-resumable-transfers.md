# ADR 0048: Resumable transfers between this computer and a host

Status: **proposed; implemented, awaiting owner review.** Decided by the implementing agent under the owner's delegation of ADR decisions (roadmap Stage 5, Q36 to Q38). Real ssh, a real VPN drop and a real cluster were not exercised: see Validation. The Transfers panel has not had a design review. This ADR amends ADR 0039, whose title says Vesqira writes two small files on a host "and nothing else": an upload now writes a file or folder on a host, on the owner's explicit request, as described below. Schema 13 and this number are the implementer's choice; another branch may have taken either, and a merge renumbers (the contiguity test in `internal/schema` pins the result).

## Context
Cubes are 4 to 11 GB, the university VPN drops and kills `rsync`, and the owner restarts by hand with `rsync -az --partial`; on a hotspot a plain download failed outright; the HPC home quota is 400 GiB. A copy that is "done" because a command exited is not evidence: AGENTS.md says a path or a filename does not prove bytewise identity, and the verification state must be `verified`, `declared`, `inferred` or `unresolved`, never implied. Until now a downloaded file was copied by hand, and an upload could not be done at all.

## Decision
- **One mechanism: the system `rsync` over the app's own ssh.** `hosts.Manager.RsyncArgv` builds an argument vector (never shell text) and `RunRsync` runs it with an explicit environment (no inherited `RSYNC_*`, `LC_ALL=C`). The ssh command given to `-e` has the same options as every other host command (batch mode, keep-alives, the multiplexing socket), so no new credential, connection or port exists. Paths are single argv elements after `--`; the remote one is `host:/abs/path`, and `--protect-args` makes the host's side receive its arguments over rsync's own channel, not through the login shell. Flags: `-rltp --safe-links --protect-args --partial-dir=.vesqira-partial --timeout=60 --no-i-r --info=progress2 --no-h`, `-z` by default (the owner's habit; a checkbox turns it off), `--bwlimit=N` when a limit is set, `--ignore-existing` on every transfer except an explicit replace, `--checksum` on a copy-again. Not `-a`: owner, group and devices mean nothing without root and a special file does not belong in a research folder; `--safe-links` drops a link inside a copied folder that points outside the copied tree. Never `--inplace`, `--append`, `--delete` (except in the dry-run check below) or `--remove-source-files`.
- **Resume: `--partial-dir`, not `--append-verify`.** `--append-verify` writes in place, so a truncated cube would sit under its final name, look like a finished file, and could be registered or opened. With `--partial-dir=.vesqira-partial` the unfinished file lives in a hidden folder next to the destination and gets its name only when rsync renames it on completion; the next run uses it as the basis and matches the bytes already there (measured with rsync 3.5.2 on a 40 MB file cut at 17 MB: the resume sent 23 MB literal data and matched 17 MB; the same after killing the transport in both directions). The cost is that rsync reads the partial file and checksums it at the start of a resume, which is I/O, not network. Folders that rsync leaves behind are named `.vesqira-partial`, are skipped by project scans and the remote scan (`discover.SkipNames`), and a file or folder cannot be given that name. Verified by experiment: a SIGKILL on rsync leaves a hidden temporary file in the destination and no partial, a SIGTERM keeps the partial; so cancel and shutdown send SIGTERM (kill only after 20 seconds), and a transport that dies (the VPN) is rsync exit 12 with the partial kept.
- **Availability, and no fallback.** Both ends are probed (`HostRsyncProbe`: `command -v rsync`, its version, whether a sha256 tool exists; the local one at queue time): GNU rsync 3.1 or newer here (`--info=progress2`), 3.0 or newer on the host (`--protect-args`), otherwise the transfer is refused with the reason in words. There is **no scp or sftp fallback**: neither can resume a cut file without trusting the partial bytes, and a resume that cannot be checked is worse than a refusal. The host's rsync path found under the login shell is passed as `--rsync-path` when it is a plain absolute path (a module-provided rsync is not on a non-login `PATH`).
- **Authorisation on both sides, and again at every attempt.** A *download* reads a path inside the host's source roots (lexical `Host.InRoots` at queue time; at start the host resolves the root and the folder with `pwd -P`, refuses a folder that leaves the root through a link, and refuses a source that is itself a link) into an existing folder inside this computer's source roots (`Roots.ResolveDir`, canonicalised, so a link out of the roots is refused). An *upload* reads a file or folder inside this computer's source roots (`Roots.Resolve`/`ResolveDir`; the canonical path is what is stored and sent) into an existing folder inside the host's roots, resolved on the host the same way. A remote source containing `*`, `?` or `[` is refused, because rsync expands those on the host even under `--protect-args` (observed); NUL, newline, carriage return and backslash are refused in every path and name (the host-side stat and hash scripts go through the login shell, `hosts.quote` and double quotes only, exactly like ADR 0039's scripts); a name is one plain name and not `.vesqira-partial*`. Queueing needs the paths to be acceptable, not the host to be reachable. A symlink inside a copied folder that stays inside it is copied as a link; no link is ever followed to read content. An upload is an external write on the researcher's own account: it happens only for the transfer the owner queued, only inside a source root, never over an existing file unless the owner chose replace, and it is audited (`transfer queued`, `transfer done/failed/skipped/cancelled`, `transfer conflict decided`).
- **Conflicts: never silent.** The destination name is checked at the start of the first attempt, and again by `--ignore-existing` for the whole transfer. Policy `ask` (default): a file that is already there with the same size and the same sha256 on both ends is "already there" (done, verified, nothing sent); a different file or folder puts the transfer in `conflict`, nothing changed, and a notification asks. `skip` leaves it; `keep_both` picks `name (2).ext`, `(3)`, … and stores the chosen name before the first byte moves, so every retry resumes the same partial file and never picks another; `replace` is the owner's explicit choice (the panel asks twice) and never replaces a file with a folder or the reverse. The conflict unit for a folder is the top-level entry; a replace of a folder merges and updates files that differ (rsync), it does not delete extras. A file that appears after the check is never overwritten (tested). Copy-again on an unverified transfer is the one case where the transfer replaces its own destination, and only because the owner pressed it.
- **The queue is persistent.** Table `transfers` (schema 13; `transfers.Store`): requested paths, policy, chosen name, state, progress, attempts, backoff, verification. One transfer per host at a time (the host's slot is taken by `running`/`verifying` in the database), different hosts in parallel; the runner is `transferOnce(ctx, now)`, a pass every 3 seconds, shaped like the job watcher's `watchOnce` so tests need no sleeps. At start, transfers left `running` or `verifying` are queued again (`Recover`) and resume from their partial file. On a clean shutdown the runner stops rsync with SIGTERM and puts the transfer back in the queue; a crash leaves the row `running` and an orphaned rsync, which is the one case this design does not cover beyond the restart recovery (a second rsync on the same partial file is not started until the orphan, which ends by itself when its connection or the destination goes, is gone: `--timeout=60` bounds it).
- **Retry with backoff, like the watcher.** A lost connection (rsync exit 5, 10, 12, 14, 30, 35, 255, or a signal) or an unreachable host puts the transfer in `waiting` with the wait doubled per failure in a row (20 s, 40 s, … capped at 10 minutes). A failure that moved bytes resets the count. After 30 failures in a row that moved no data (about five hours) it fails with the reason. Refusals that retrying cannot cure fail at once: exit 23 and 24 (a file could not be read or vanished), 11 (a full disk, with a hint), a refused path, a missing rsync, a source that disappeared or is a link, no room on this computer (`Statfs` against the file size minus the partial already held). A lost connection while hashing is a retry, not "unverified".
- **Verification, recorded honestly (invariant 7).** After rsync exits 0, a file is hashed on both machines (Go's sha256 here; `sha256sum` or `shasum -a 256` on the host, the same script family as ADR 0039) and the sizes compared; the result is stored with both hashes. `verified` only when size and sha256 match on both ends, computed after the transfer, so a source that changed meanwhile shows as a mismatch. Otherwise `unverified` with the reason in words: hashes differ, sizes differ, no hash tool on the host (the sizes are reported), the destination is not a file, a side could not be read. A folder is checked by an rsync dry run with `--checksum --delete --itemize-changes` (nothing is changed or deleted): empty output means every file's content matches and the file lists are equal, recorded as method `rsync-checksum` and worded "rsync's checksum, not SHA-256". An unverified transfer is announced as a problem, never as success; it cannot be registered; "Copy again and compare contents" requeues it with `--checksum`. `done` says the bytes arrived; the verification field says what was checked. Computational completion is not scientific validity (invariant 9): nothing here looks inside the FITS.
- **Registering a download as a dataset.** `POST /api/transfers/{id}/register`, only for a verified downloaded file, and only if the file on disk still has the verified hash. It uses the ordinary registration, then writes a derived record `op: transfer` whose summary names the host, the remote path, the hash and method, and says in words that the host file is an **external reference** that may have changed or gone (AGENTS.md: a path does not prove identity; this is "verified at transfer time"). Only the record's `policy` sentence travels with a figure to a reviewer (`derivedSummary`), and it names neither the host nor a path (tested). Deleting the dataset clears the transfer's link (`UPDATE transfers SET dataset_id=NULL`, in the dataset delete steps). The managed copy of ADR 0018 still refuses a remote dataset, now with a pointer to Transfers; no copy is made by default anywhere.
- **Progress and notifications.** rsync's `--info=progress2` line (bytes, percent, rate, estimate; `\r`-separated, parsed for rsync 3.1 to 3.5 formats) is stored at most once a second and shown with a `<progress>` element and text; unknown totals show "so far", never zero. A transfer that finishes verified, fails, arrives unverified or needs a decision is announced once in the notification list (kinds `transfer_done`, `transfer_failed`, `transfer_conflict`; ADR 0043's store). A cancel or a shutdown is not announced.
- **Quota awareness.** Queueing an upload compares its size (a file's, or a folder's walk, bounded) with the host's last storage look (ADR 0045), if there is one, with no new call to the host: a file system whose available space is smaller, or a quota entry the upload would pass, gives a warning stored on the transfer and shown on its row. It only warns; the host's own quota decides, and a full disk fails with its own message. A host never looked at gives no warning.
- **Cancel.** A running transfer is stopped with SIGTERM; its partial file is kept so Try again resumes it, or deleted with "Cancel and delete the partial file" (download only). A partial file on a host is never deleted by Vesqira (a delete on the researcher's account that this ADR does not authorise); it stays in `.vesqira-partial` there and the owner removes it, which matters at 395 of 400 GiB.
- **Routes, owner listener only.** `GET/POST /api/transfers`, `POST /api/transfers/{id}/cancel|retry|resolve|remove|register`; described in `bodies.json`; `undescribed.txt` did not grow; the reviewer handler has none of them (tested). `GET /api/capabilities` reports `features.transfers`. The web panel is `hosts/Transfers.tsx` in the Hosts screen; a server without the queue answers 404 and the panel renders nothing.

## Alternatives
- **`--append-verify`.** Rejected: a half file under the final name (see above); it also rereads and hashes the whole prefix on both ends on every resume.
- **`--partial`.** Rejected for the same reason: the partial keeps the final name.
- **scp/sftp with resume.** Rejected: no verified resume; a second protocol and quoting model.
- **Doing it inside the Go process (an sftp library or the worker's channel).** Rejected: a new transfer implementation to get right (resume, compression, checksums, bandwidth limit) where rsync is installed on every HPC site and already written; the worker deliberately reads planes only.
- **Verifying a folder with a hash manifest.** Rejected for v1: names with newlines and escapes in `sha256sum` output, and hashing every file of a run folder on a login node twice; rsync's own checksum comparison is recorded under its own name instead of pretending to be sha256.
- **Queueing only when the host is reachable.** Rejected: the VPN is usually down when the owner thinks of it; paths are authorised lexically and locally at queue time and again, with the host, at each attempt.
- **A `--delete` mirror for replace.** Rejected: replace updates what differs and removes nothing.

## Consequences
- The researcher's host folders can now receive a file or folder Vesqira uploaded (and a hidden `.vesqira-partial` folder while it is unfinished or after a cancel), inside the source roots only.
- An unfinished transfer needs disk: a resumed 11 GB cube holds its partial file next to the destination; a cancel keeps it unless told otherwise.
- The first resume of a large partial file reads it on the receiving machine before any byte moves.
- `-z` costs CPU for little gain on float FITS cubes; it is a checkbox.
- A folder with symlinks that point outside it is copied without them (`--safe-links`), and the dry-run check then lists them as differences: the transfer shows as unverified with the first differences named. That is honest, not pretty.
- The SIGTERM-on-shutdown design relies on the process exiting only after the runner has stopped (`main` waits up to 30 seconds).
- The panel depends on `/api/transfers` being polled (3 s while something is live, 20 s otherwise); there is no event stream.

## Validation
Go tests with a stand-in ssh that runs the "remote" command in place and real `rsync` between temp folders (they skip when rsync is not installed). `hosts/transfer_test.go`: version parsing (GNU 3.x accepted, 2.6.9 and openrsync refused), progress parsing in both rsync output generations, exit-code classification, argv with spaces, quotes, `$()`, `;`, backticks, a leading dash and a colon in names as single elements and never in an option, refusal of newline, CR, NUL, backslash, relative and over-long paths, remote globs, `..`, an option-like destination, a negative limit, reserved names, an ssh path needing both quote kinds; hostile names transferred in both directions with no command run (a `touch PWNED` in a name never ran); a connection killed mid-file in both directions leaves the partial in `.vesqira-partial`, nothing under the final name, and the resume matches the bytes and ends at 100 %; SIGTERM keeps the partial; the dry-run check lists a same-size same-time different file and an extra file and changes nothing; the stat script on files, folders, links, absent names, a link out of the root, a missing folder, a path outside the roots, hostile names, and a host without any hash tool (no hash is invented). `transfers/transfers_test.go`: claims are exclusive, one slot per host, retry timing, the final name written once, progress only while running, verification written only from the expected state, the restart (a second store on the same file), remove only when finished. `server/transfers*_test.go`: end-to-end downloads and uploads verified; folders compared by content and worded as such; one transfer per host and hosts in parallel; 20 refused paths on both sides with nothing queued and nothing sent to the host; a host link out of the root and a link as the source fail with the reason; missing rsync here and on the host refused with the reason and no fallback; the quota and free-space warnings and that they call no host; a different file waits (data unmoved, notification), skip, keep-both with a persisted name across a retry, identical files not transferred, replace only on choice and never across kinds, a file that appears mid-queue not overwritten; a corrupted host hash and a host without a hash tool are unverified with the reason, announced as a problem, not registrable, and verified after Copy again; backoff 20 s doubling to the 10-minute cap and giving up after 30 fruitless attempts; a mid-file drop resumed and verified in both directions; closing the app keeps the partial and queues again, a crash is recovered, and the transfer finishes from the partial file; cancel of a running, queued, waiting and conflicted transfer with and without discarding the partial; registering sets an external-reference record whose shared summary has no host or path; capabilities; responses validated against `openapi.yaml`. `review/notifications_test.go`: the reviewer handler has no transfer route. `schema/transfers_test.go` and `testdata/schema_v13.sql`: the migration. `discover/partial_test.go`: the partial folder is never listed as data. `lifecycle/guard_test.go`: the table is part of the delete guard. Web: `hosts/Transfers.test.tsx` (words never say Done alone, unknown totals, running/waiting/verified/unverified/conflict rows, Replace needs a second click, queue form body, bad limit blocked, polling cadence, row errors, absent queue) and `e2e/tests/transfers.spec.ts` (download, verified hash, identical file, conflict, keep both, axe). **Not verified:** a real ssh host, a real VPN drop (a killed transport stands in), rsync below 3.5 or on macOS, BeeGFS or Lustre behaviour with a partial folder, a login shell that prints a banner to stdout during `rsync --server`, and the panel's design review.

## Rollback / Migration
Schema 13 (`transfers`, migration "transfers", snapshot `testdata/schema_v13.sql`); an upgrade copies the catalog aside first, and an older build refuses a version 13 catalog (ADR 0020). Remove the `Transfers` store from `main.go` to turn the queue and its routes off (the panel then hides itself); files already transferred stay, and `.vesqira-partial` folders can be deleted by hand at any time (the next attempt of a transfer that needed one starts that file again).
