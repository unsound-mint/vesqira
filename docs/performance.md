# Performance

The viewer must stay responsive on cubes far larger than memory (shape.md section 10, Q149, Q164, Q169, Q182). This page says what is measured, how, and what is not yet.

## What `make bench` measures

`tools/bench.py` builds a sparse FITS cube (default 1500 x 1500 x 600, 5 GiB logical; a few channels hold random data, the rest are holes) and drives the scientific worker over its own stdin/stdout protocol, the way the API does. It reports first-call, median and p95 time and the worker's resident memory for: header read (`view`), a plane, a coordinate readout, a small and a box-sized region spectrum. `--check` compares with `tools/bench_budgets.json`; CI runs it with budgets about five times the development-laptop numbers.

Limits of the numbers: a sparse file in the page cache measures access pattern and software overhead, not a disk or a network. No concurrent requests (contention lives in the Go worker pool, not here). The `plane_4d`, `spectrum_small_4d` and `spectrum_box_4d` rows read the same cube with a fourth, length-1 STOKES axis in the header (budgets as for the 3D rows). Each row also reports the worker's peak resident memory (`VmHWM`) and the bytes of its replies.

## What `make viewer-bench` measures

`tools/viewer_perf.mjs` runs the real app in headless Chromium on a 2048 x 2048 x 24 float32 cube (real data in every channel): key press to pixels on screen for 12 channel steps, the longest main-thread task per step, the CPU plane renderer (linear and asinh) and histogram on one plane, and the worst frame gap during 20 quick steps. Budgets are in `tools/viewer_perf_budgets.json`. Software rendering, same-machine API, page-cache reads: it measures main-thread cost, not disk, network or GPU. Not part of CI (needs Chromium and a free port 8787 and 5173). Before the GPU renderer (ADR 0034): key to pixels p95 250 ms, longest task 135 ms, worst frame gap 83 ms. After it and the histogram worker: p95 about 150 to 280 ms, no task over 50 ms, a new 4.2 MP plane drawn in about 20 ms and a stretch or range change in under one frame. The linear and asinh render and histogram rows are the CPU fallback path. `--profile` prints where the main thread spends its time while stepping.

## Reference numbers (development laptop, 2026-11-05)

| operation | before | after |
|---|---|---|
| plane (2.25 MP) | 42 ms | 42 ms (dominated by the percentile statistics) |
| spectrum, 10 x 10 px, 600 channels | 49 ms | 4 ms |
| spectrum, 187 x 187 px, 600 channels | 791 ms | 150 ms |

The gain comes from slicing the memory-mapped file instead of astropy's section reader and from reading channels in blocks with one vectorised mean per block. Files that cannot be mapped still fall back to the section reader.

## Real disk, ssh, 4D, transfers (`make bench-disk`, measured 2026-11-13)

`make bench-disk` writes a dense 5.0 GiB cube (every channel holds data) on a real file system, evicts its pages from the page cache without root (`posix_fadvise(DONTNEED)`; `fincore` is read right after each eviction and printed per row in the `cached %` column: 0.00 in every row of every run, so the first call of each row really read the disk, even though the worker keeps the file mapped), then reads it cold (first call) and warm (the calls after). The second series goes through a real `ssh` to a user-mode `sshd` on loopback that launches the worker the way `hosts.go` does, so it includes ssh's crypto and channel costs but no network latency or bandwidth limit. The third cuts a 1 GiB `rsync` download through the same ssh and runs it again with the app's flags. No budgets: the machine and file system decide these numbers.

Machine: AMD Ryzen 9 7940HS, 16 threads, 14 GiB RAM, Micron 2400 NVMe, btrfs, Linux 7.2. It was shared with other work (load average 7 to 21 during the runs), so the spread of four runs is given, not one lucky figure.

| operation (1500 x 1500 x 600 float32) | cold, local disk | warm | cold through ssh | reply bytes | worker peak memory |
|---|---|---|---|---|---|
| header read | 6 to 24 ms | 2 to 5 ms | 7 to 20 ms | 0.9 KiB | 82 MB |
| plane, 2.25 MP | 60 to 276 ms | 46 to 161 ms | 133 to 807 ms | 8.6 MiB | 150 MB |
| coordinate readout | about 1 ms | 0.3 ms | about 1 ms | 0.2 KiB | 150 MB |
| spectrum, 10 x 10 px | 1.3 to 2.3 s before the fix, 20 to 23 ms after | 7 to 12 ms | 1.4 to 2.3 s before, 20 ms after | 12.5 KiB | 150 to 170 MB |
| spectrum, 187 x 187 px | 2.0 to 4.5 s before, 0.36 to 0.96 s after | 170 to 1400 ms | 2.1 to 4.9 s before, 0.33 s after | 12.5 KiB | 820 to 865 MB |
| next five channels (scrub) | 55 to 125 ms each (420 ms at load 21) | | 57 to 375 ms each | 8.6 MiB each | 150 MB |

What the numbers say:

- A cold plane costs about 20 to 40 ms more than a warm one on NVMe, so channel scrubbing is bound by decoding and the 8.6 MiB reply, not the disk. Through ssh on loopback the warm plane is the same as locally (about 50 ms): the link's software cost is small; a real link's bandwidth is not measured here, which is why large planes on a host go out as a block-mean preview first.
- The first spectrum on a cold cube was the slow operation, and the cause was bytes, not latency. Measured with the load-independent counters of the worker (`/proc/PID/io read_bytes` and major page faults, columns `read MiB` and `majflt` of `make bench-disk`): a 10 x 10 box over 600 channels asked the disk for **2400 MiB** in 600 faults (one fault per channel, each reading a readahead window of 4 MiB), where the box needs about 36 MB; the 187 x 187 box read 4093 MiB where 673 MB is touched. The worker reads through a memory map, so there is no read() call to count with strace; the faults are the reads.
- The fix is a hint, not a different reader (`Cube._hint_block`, used by every block read: spectra, orientation statistics, PV diagrams, channel grids): `madvise(MADV_RANDOM)` on the file's mapping switches the oversized readahead off, and `MADV_WILLNEED` over the exact byte span of the box in each channel of the next block queues those reads together instead of one fault at a time. Values are untouched: `test_read_hints.py` compares hinted, unhinted and an independent astropy read on random boxes and channel ranges, for a float cube with NaN and a fourth axis, and for an int16 cube with BLANK, BSCALE and BZERO. The block size, and so the memory bound, is unchanged. Result on the same cube and machine: 10 x 10 box, cold, 1312 ms to 21 ms, disk read 2400 MiB to 34 MiB, major faults 600 to 0; 187 x 187 box 2077 ms to 362 ms (first run after the fix 957 ms while the machine was busier), disk read 4093 MiB to 642 MiB (about the 673 MB the box touches), faults 600 to 0 to 209. Through ssh the same: 20 ms and 325 ms. Warm times did not change.
- A plane read after a spectrum is not slowed by that hint: the advice is on the mapping of one open, and every request opens the file itself. Measured with the plane on another channel, cold (evicted after the spectrum), 3 runs each, in a worker with the hints off and one with them on: 16.5 MiB read and 2 major faults in all 12 runs, 56 to 104 ms with them on and 70 to 105 ms off (one off run took 308 ms while the machine was busy). The row `disk_plane_after_spectrum` of `make bench-disk` repeats that sequence.
- Peak memory of the box spectrum is 820 to 865 MB for a 187 x 187 x 600 selection, inside the worker cap (3072 MB) and above the `rss_mb` budget of the CI row, which checks resident memory at the end of the scenario, not the peak.
- Connecting, logging in and starting the worker over ssh took 440 to 700 ms before the first answer.
- 4D: a cube with a length-1 fourth axis (CASA's STOKES) reads as fast as the 3D one (differences between the 3D and 4D rows stayed inside the run-to-run noise, in both directions). A cube whose fourth axis has more than one plane (a real Stokes cube) is refused with "extra axis of length above 1 (axis 4); only one channel axis is supported": the viewer has no way to pick a Stokes plane yet, so the number measured for it is "not supported", not a time.
- Resumable transfers: a download through ssh was stopped with SIGTERM (what the app sends on a cancel, a quit, and, through `Pdeathsig`, when the app is killed) and run again with rsync's `--partial-dir`. The second run sent only what was missing (for example 297 MiB of 1024 after 727 MiB were kept; 145 of 256 MiB after 111 kept), matched the rest, exited 0, left no partial file, and the file hashed like the source. Resuming costs a pass of rsync's checksums over the kept part on both ends, about 140 to 380 MiB/s of kept data here. So it wins whenever the link is slower than that: at a limit of 20 MiB/s a 256 MiB file took 7.6 s resumed against 12.9 s from nothing. On unlimited loopback (about 640 MiB/s) it lost: 2.6 to 5.7 s resumed against 1.6 s from nothing. A VPN to a cluster is the first case. The earlier figure of a break-even at "50 to 100 MB/s" came from a run limited to 256 MiB/s and was wrong; it is withdrawn.
- A transfer cut by SIGKILL of rsync itself (the kernel's OOM killer, a power cut) used to keep nothing: rsync moves its hidden temporary file (`.name.XXXXXX`, in the destination folder) into `.vesqira-partial` only when it is told to stop, so that file restarted from zero and the temporary stayed behind. Fixed for downloads: before an attempt, `hosts.AdoptOrphanTemp` takes the biggest regular file named exactly `.<destination name>.` plus six letters or digits in the destination folder and moves it into the partial folder (unless a partial file at least as big is there), and removes other such files of the same name; nothing else is read, moved or deleted (links, other names, wrong suffix lengths are left alone, tested). The content needs no trust: rsync matches a partial file block by block against the source and the result is hashed on both ends. Tested by SIGKILL to rsync's process group mid-copy (`TestAKilledRsyncLeavesATempFileThatTheNextAttemptResumesFrom`) followed by the resume, and by `TestAdoptOrphanTempKeepsABiggerPartialAndRemovesOnlyItsOwnOrphans`. Uploads are not covered: the temporary file lives on the host, and Vesqira does not delete there (ADR 0051).

The behaviour of interrupted transfers (resume after a dropped connection, after an app restart, cancel keeping or deleting the partial file, never overwriting a file that appeared meanwhile, hash on both ends, one transfer per host at a time and the hosts in parallel, so the number of simultaneous transfers is the number of hosts; there is no global cap) was already built under ADR 0051 and is covered by `TestResumeAfterTheConnectionDropsMidFile`, `TestAConnectionDropMidFileIsResumedAndVerified`, `TestAClosedAppResumesTheTransferAtTheNextStart`, `TestCancelStopsARunningTransferAndCanDiscardItsPartialFile`, `TestAFileThatAppearsAfterTheCheckIsNeverOverwritten` and `TestOneTransferPerHostAtATime` (real rsync, a stand-in ssh that cuts the connection at a byte count).

## Long lists

The dataset list and the run list (sidebar) draw a window of rows once they hold more than 200 (`ui/VirtualList.tsx`): rows are placed by index in a box as tall as the whole list inside the nearest scrolling ancestor, so the scroll bar and the layout stay as before. Every row is a `listitem` with `aria-posinset` and `aria-setsize`, so a screen reader hears "3 of 5000". The list is one tab stop; arrows, Home and End move by index and scroll the target row into existence; the row that holds the tab stop is always drawn. Measured with 5000 datasets in jsdom (`virtualList.test.tsx`): 1020 ms and 5000 rows before, 44 ms and 36 rows after. In Chromium (`e2e/tests/zzzzzzzzzzzz-list-scale.spec.ts`, 5000 datasets and 5000 runs at once, served by a route intercept): the lists are ready 0.9 s after a reload with 738 DOM nodes in the whole page. The runs table is not windowed: it shows 300 runs at a time with "Show 300 more" (`RunsView`, `STEP`); with 5000 runs it was ready 190 ms after the click with 3211 DOM nodes in the page. The Runs list in the sidebar is now one tab stop with arrow keys (it was one tab stop per run). Other lists in the app (comments, locations, masks, overlays, hosts' folders) hold tens of rows.

## Preview and prefetch

On a remote host, a plane larger than about a quarter of a megapixel is first requested reduced (`step=N`, at most 64; the worker returns the mean of the finite pixels of each N x N block, NaN where a block has none, and marks `preview` in the header as "not for measurement"). The viewer draws it on the full grid, so pixel indices, readouts and regions keep their meaning, shows "preview, reduced N×" under the picture, and requests the full plane 150 ms after the last channel change. When the full plane arrives, the next and previous channels are requested so the server cache already holds them. Readouts of coordinates always come from the full data (`coord`), never from the preview. Local datasets skip the preview: the reduction still reads the whole plane, so it only helps when the link is the bottleneck.

## Workload classes

Scientific work has three classes (ADR 0056), each with its own concurrency budget and its own worker processes, so capacity reserved for interactive viewing is never taken by heavier work:

| Class | Work | Budget flag (default) |
| --- | --- | --- |
| interactive | planes, coordinate readouts, overlay geometry, small readouts | `--workers-interactive` (2 worker processes) |
| heavy | spectra over large regions, orientation statistics, PV diagrams, channel grids, catalog and ROHSA index reads, and analysis programs (moment, cutout, convolve, relative orientation, ...) | `--workers-heavy` (2 tasks at once) |
| background | header reads that catalog files, fingerprints and full file hashes (a project scan queues up to a thousand) | `--workers-background` (2) |

Header reads a person is waiting on (register preview, registration, catalog registration, transfer and analysis-output registration) run in the interactive class by caller intent (`worker.WithClass`); only project scans and background fingerprinting use the background class. At most one full file hash runs at a time, and it waits for that token before taking a background slot, so with the default budget of 2 a long hash never occupies the last slot that scan header reads and sampled fingerprints need (with `--workers-background 1` it must take that slot). Each budget is 1 to 16. With the defaults at most 5 Python worker processes exist, and analysis programs run inside the heavy budget. Interactive capacity is reserved by construction: there is no shared pool a heavy task could take a slot from. A request that exceeds the timeout, or any broken reply, kills only that process; a heavy or background request whose caller gives up is stopped by killing only its own process (about 0.3 s cold start next time), an interactive one is allowed to finish. Transfers (rsync) and remote host workers are outside these budgets (ADR 0051).

When a request waits for a slot the API knows why: `GET /api/workload?request=<id>` (the id the client sent as `X-Request-Id`) answers `waiting` with a reason such as "waiting: 2 heavy analyses are running (relative orientation, PV diagram); interactive viewing is unaffected". The panel that asked polls it after 700 ms and shows the sentence in place of a silent spinner. The reason names operations only, never files or datasets. Without an id the route lists budget, running and waiting counts per class.

Covered by `TestInteractiveRequestIsNotDelayedByAFloodOfHeavyAndBackgroundWork` (a flood of heavy and background requests against fake workers that take 300 ms each; a plane request must finish within 150 ms), `TestQueueReasonNamesWhatIsRunning`, `TestBudgetLimitsConcurrencyPerClass`, `TestBudgetsAreValidated`, `TestAHeavyRequestNeverBlocksInteractiveOnesAndCancelKillsOnlyTheHeavyLane` and `TestHeaderUsesItsOwnLaneAndMapsErrors`, `TestFullHashDoesNotBlockHeaderReads` and `TestWithClassPromotesOnlyBackgroundOps`.

`make bench` has a `plane_under_load` row: planes on one worker while a second worker serves large-region spectra and a third header reads, back to back. Budget p95 450 ms (`tools/bench_budgets.json`); measured on a loaded laptop at about 130 to 200 ms against about 50 to 100 ms for an unloaded plane. It catches contention the separate processes do not isolate (CPU, memory bandwidth, page cache), not a queue. On a machine busy with other work the unloaded `spectrum_small` first call can already exceed its own budget; that is independent of the load case.

Registering a file used to start one `fits_header.py` process per file (median 188 ms on the development laptop); the registration lane keeps one worker, and `tools/bench.py` reports the `register` row (300 small files per request, budget p95 50 ms). The reply is the same JSON, checked by `TestPersistentHeaderEqualsOneShotScript`; a crash on one file fails only that file (`TestHeaderCrashMidBatchFailsOnlyThatFile`).

A project scan on a host registers its files with `register_many`: up to 32 files per worker request (fewer when their paths would pass 6 KiB, since the request line is capped at 8 KiB), each file authorized, read for its header, and sampled-fingerprinted exactly as the single operations do, with a refusal per file and a 20 s time budget after which the worker returns the files done and the API sends the rest again. Before, each file cost three round trips (`resolve`, `header`, `fingerprint`), so a scan was bound by the link's latency, not by the host. Measured by `TestRemoteScanBatchesRegistrationAndStoresWhatOneByOneStores` through a fake ssh (counts worker requests, not time): 102 files, 3.2 requests per file one by one (3 per file, plus the scan's own reads of run folders, which both runs make) against 0.04 batched (4 requests, about 26 files each); the catalog rows, sampled fingerprints and refusal texts are equal in both runs. No wall-clock gain on a real cluster has been measured; it should approach the round-trip count ratio when latency dominates. A worker without the operation answers `bad_request`; the scan then registers one by one for the rest of that scan.

## Memory cap

The plane worker and each analysis run (`analysis.py`) set, through the shared `memcap.py`, `RLIMIT_DATA` to what it holds once numpy and astropy are loaded (about 2 GB of address space) plus `VESQIRA_WORKER_MEM_MB` (default 3072; 0 disables). Files are opened read-only and memory-mapped, which the limit does not count, so a 10 GB cube opens as before; an allocation over the cap (for example a 3000 x 3000 plane with a 40 MB budget) makes that request fail with "over the memory cap (N MB)" and the worker serves the next one. Linux only; elsewhere nothing is limited. Covered by `test_analysis.py` and `test_a_request_over_the_memory_cap_fails_alone_and_the_worker_keeps_serving`.

A reduced preview is a display aid only: while it is shown the pixel readout says "preview only", the histogram and the compared pixel counts are hidden, and a figure cannot be saved. Orientation maps (declared axial) are never previewed, since a block mean of angles is wrong; the API refuses it. If the preview fails after the full plane arrived, or succeeds after the full plane failed, it changes nothing.

Files read through the memory map must be as long as their header says; a shorter file (copied part way, or still being written) is read through astropy's section reader, which serves the planes that exist.
