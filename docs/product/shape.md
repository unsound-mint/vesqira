# The shape of Vesqira

One compact reference for what the product is meant to be, distilled from the 226-question requirements interview (`docs/design-history/vesqira-chatgpt-transcript.txt`) and the owner's later direction. It replaces re-reading the transcript. `Q<n>` points to the interview question; "owner:" marks his own words or later direction; "(deferred)" means decided but not for the first releases. Status of what is built lives in `docs/roadmap.md`, not here.

Every decision below was chosen by the owner; for most he picked option D of the interview together with the expanded shape the interviewer wrote for it, not the bare option text. Read an entry as "D plus its shape".

## 1. What it is

- **One workspace where a researcher never has to leave.** Inspect a cube, see a problem, change parameters, run on HPC in one click, put the result on a board with the supervisor, discuss it, remember it. Owner (2026-11-05): no DS9, no Canva, no separate terminal, editor or VPN client; everything interconnected; a run is nested like a Notion page (a default result first, more results of the same run, config, logs added on demand); a board can show a run that is not finished. Founding pain: results reviewed as hand-made Canva grids with no record of how each panel was made; the professor asked "why is AM different?" and nothing answered.
- **Not** a better CARTA, Open OnDemand or experiment tracker; it is the layer connecting data, computation, visualisation and discussion across HPC (brief, evaluation). TensorBoard + IDE + GitLab for researchers, UX-first.
- **Discipline-extensible** (turn 235): one strong core (projects, datasets, experiments, jobs, viewers, figures, papers, citations, provenance, collaboration), scientific extensions (astronomy first; biology later; each contributes only capabilities and never reimplements core), external connectors (Git, SSH/Slurm, literature APIs, archives, Zotero, MCP). Astronomy code must not know biology and the reverse. Extension contract changes need an ADR (Q156).
- **Scope now:** astronomy only (FITS, WCS, spectral cubes, VGT outputs, ROHSA, boards, supervisor review); v0.2 SSH/Slurm and Julia pipelines; later biology (TIFF/OME-TIFF/CZI, segmentation, calibrated measurements, QC; the `nuclear-morphometry` repo is the reference case; MetaMorph TIFFs keep calibration in per-page XML, never defaulted), LaTeX, literature, archive federation (turn 244).
- **Identity:** Vesqira, CLI `vesqira`, tagline "Your research, connected." License AGPL-3.0-only (Q69; the AGPL does not force publishing researchers' data). Governance: founder-led, moving to core maintainers and RFCs as contributors grow (Q70). Open-source platform, paid managed services only (hosted AI, workers, storage, backups, institutional integrations, support); never charge for reproducibility, verification or basic collaboration; data and exports portable between hosted and self-hosted (Q64, Q66, Q67, Q68). Name clearance (trademark, domain, org) not done.
- **UX is the point, and performance is part of UX** (Q148 owner: "UX-first also means performance-first … if we can do something faster by writing more code, we should"; code is no longer the bottleneck).

## 2. People and the core loop

- **First user:** computational researcher plus scientific supervisor with no cluster access (Q77). Acceptance: the supervisor independently understands and reviews an experiment someone else produced, with no figure transfers, config reconstruction or "which output belongs to which run" explanations.
- **Loop:** Explore, analyse, select, present, discuss (Q10). Journey for release one: open a project, run an experiment, explore results, prepare a board, collaborate (Q76). End-to-end but deliberately limited at each step.
- **Build order:** slice 1 existing results to scientific review (import VGT runs, discover parameters, inspect and compare FITS, board, share with the professor); slice 2 connect to Irgetas over SSH, submit the existing Julia pipeline via Slurm, track it, and outputs appear in the same explorer (Q80, Q81). Exploration must work independent of what executed the run, so other tools' outputs are first-class.
- **UX validation:** pass/fail task criteria, starting with the owner's lab; example test: the supervisor finds two VGT runs, identifies config differences, compares figures, adds a finding to a meeting board, unaided (Q79). Analytics optional and privacy-respecting.
- **Onboarding:** progressive and role-adaptive. Supervisor default home: recent results, boards, investigations; researcher default: experiments, source files, active jobs. No mandatory tutorial (Q78). Interface complexity scales with the workspace: one project means one-level navigation (Q43 owner).

## 3. Information architecture and workspace

- **Project-first (Q1):** a project is an independent persistent collaborative workspace that references local folders, Git repos and one or more clusters; not a folder or repo (Q2). It stays available when the laptop is off or VPN down. Per-project policy decides what is shared offline: previews only, plus explicitly published artifacts, or auto-synced outputs; the UI shows what remains available (Q3).
- **Browser and desktop (Q4):** same projects and backend; browser for persistent collaboration, review and visualisation; desktop for local development and cluster work; desktop never the only place meaningful work happens. First launch offers: create a local project (no account), join a workspace, set up a shared server; a local project can later move to a shared workspace and the UI says what uploads (Q5).
- **Explorer (Q6):** source-based sidebar (Local, Git, connected hosts) with the physical location always visible; disconnected sources stay listed with status; unified cross-source search planned. A separate **Datasets** view is the logical catalog (Q137).
- **Home (Q8):** customisable dashboard by default (recent experiments, latest figures, active jobs, discussions needing attention, collaborator activity, connected infrastructure), pinned views, restore last session. Three kinds of state: shared project, personal preferences, personal session (open tabs, plots, terminals).
- **Navigation (Q9):** GitLab-like sections (Files, Experiments, Jobs, Boards, Discussions) with VS Code-like tabs and split panels for opening files, plots and experiments; saved boards add their own layouts. Open a figure's source, its job and its thread without losing the current comparison.
- **Operations centre (Q41, Q43):** one dashboard for local processes, Slurm jobs, pending approvals, requests and transfers; two levels (global across projects and per project; grid of tiles for status, table for detail); respects project and cluster permissions; telemetry that is missing is shown as missing, never as zero usage. Notifications are rule-based per user, project, cluster, pipeline (Q42 owner: "I'd like to know about each completed run, while other users may want to know when everything finishes"); a 20-run sweep gives the owner 20 events and the professor 1; preferences never alter event history.
- **Commands (Q175):** one typed registry; mouse, shortcut, palette, plugin and agent invoke the same validated command; context-aware palette; reversibility per kind (view change local undo; board move undoable with collaborators; saved region undoable before publication; metadata correction a new revision; Slurm submit needs authorisation and no false rollback; publication changes are corrections or withdrawals). High-frequency interactions bypass dispatch. Configurable shortcuts with conflict detection.
- **UI system (Q173):** tokens and interaction contracts, application primitives (panels, tabs, palette, virtualised lists, inspectors), scientific primitives (FITS canvas, spectral axis, WCS cursor, linked regions, comparison, plot surfaces), workflow layer. Compact and information-dense; plugins inherit tokens.
- **Accessibility (Q176):** every scientific operation doable by pointer, keyboard or typed input; coordinate readout; cyclic perceptual colormaps and non-colour encoding for axial orientation; spectral plots with inspectable numbers and keyboard markers; tables keyboard-filterable; real scientific tasks tested; state limits honestly.
- **Cross-view interaction (Q174):** typed scientific context between viewers with configurable link groups; meaning is never inferred from matching numbers (channel 42 is not channel 42 elsewhere; use verified spectral coordinates); link, temporarily unlink, several independent groups; linked selections are interface state until saved as a region or measurement; cheap interactions immediate, costly ones throttled and cancellable; presentation boards never change because another workspace was used.
- **Desktop shell (Q147, Q148):** shared web frontend plus local backend, shell-specific code isolated, web app fully works without native APIs; Tauri or a native companion only when OS capability, performance or security needs it; Monaco and xterm.js for editor and terminal; prototype Electron vs Tauri on four tasks (local project with Julia in a terminal; SSH and remote files; a large cube beside an editor; fully offline project). Code-OSS rejected as foundation.

## 4. Runs, experiments, execution

- **Model (Q18):** Experiment (investigation) → Configuration (parameter variant) → Execution (one attempt, local or HPC) → Artifact (output). A Slurm job is not a run; one execution may launch several jobs. The UI shows a plain run list; the hierarchy stays mostly invisible.
- **Explorer (Q19–Q21):** default is a data table (sortable parameters and metrics, status, powerful filters, expose any parameter column), switchable to gallery and comparison views; one query model shared by text search, structured filters and column filters (`gradient_method:central_checked block_size:32`), with ranges, units, dates and status, autocomplete, saved column and filter sets; imported runs never vanish because a parameter was not inferred; results show physical location and connection state; indexed results survive a disconnected HPC. Owner: he finds runs by remembering the sequence, so chronological browsing stays familiar. Sweep explorer and experiment explorer share components (Q129).
- **Run overview (Q22, Q23):** structured summary, results first (previews, graphs, key metrics), config, provenance and execution details compact and secondary; running or failed runs lift progress and errors; artifacts open in tabs and split panels. Same entry whether local, Slurm or imported. Owner (2026-11-05) extends it: nested, default result plus alternates, config and logs on demand, usable while running.
- **Run experience (Q32):** pick a pipeline, set scientific parameters, Run; environment, defaults and Slurm handled; advanced settings optional; the same form for a user without credentials produces a request instead of a submission (permissions choose the action, not two UIs).
- **Pipelines (Q33–Q35):** discovered from scripts, configs and Slurm files then confirmed by the researcher (discovery is not safe to execute; permissions and limits set separately); explicit manifests and SDKs remain. Development channel (latest code, may be uncommitted) and Published channel (immutable approved revision plus parameter schema) with deliberate promotion; material change triggers re-approval (Q34). Code source is chosen once per pipeline: Git revision, synchronised working tree or existing remote source, always shown before execution; every execution records the exact snapshot; sync never overwrites remote edits without warning (Q35).
- **Environments (Q40, Q124):** full management where permitted (local venvs, Julia deps, containers); discovery plus existing environments plus approved configuration on restricted HPC; every editor, terminal and run shows its active environment; capture dependency files (Project/Manifest, locks, conda), runtimes, modules, threads, seeds; containers supported not required; never modify cluster environments; distinguish described, reconstructed, and independently reproduced.
- **Rerun modes (Q125):** reproduce the original environment (stop if it cannot be rebuilt), best-effort reconstruction (document substitutions), run in a new environment (adapted); dependency diff and approval; every rerun is a new attempt linked to the original, never labelled exact reproduction.
- **Reproducibility (Q121–Q123, Q198):** no single green badge; separate rows for documentation, input availability, environment reconstruction, execution, output validation, each verified / failed / incomplete / not performed; documentation alone is not reproduction; tolerances and thresholds are recorded, never invented, ideally fixed before the rerun, changes after seeing results are recorded as such. Validation profiles are versioned (built-in numeric checks, project profiles, existing Julia/Python scripts); profile (how to test) differs from validation record (what ran). Triggers: manual, post-run basic checks, before review or publication, Git/CI; automatic triggers never bypass approval; a successful Slurm job is not a validated output. Stochastic runs state a contract: exact, numerical (tolerances), statistical (distribution criteria) or unspecified; capture seed, RNG, libraries, hardware; a matching seed is not a guarantee.
- **Pipelines of stages (Q126, Q127):** existing scripts and workflow engines (Snakemake, Nextflow) stay authoritative; stage graph visualised; intermediates are first-class artifacts; a preflight plan per stage says reuse (verified), reuse (existing), recompute N variants, or validate, each with a reason; identical files and parameters do not guarantee interchangeable outputs; no competing workflow engine; first HPC slice is Julia scripts plus Slurm dependencies, not a DAG editor.
- **Sweeps (Q128, Q129):** defined by grids, templates, config files or SDK; preview of variants, reuse, scheduler limits and cost before submission (3×4×5 = 60 variants); a variant is not a Slurm job (arrays vs several jobs); "explore variations" starts a sweep around a selected result; linked views (parameter table, charts, map gallery, metric summaries) with selection shared; incomplete, failed and missing-metric variants stay visible; ranking only with an explicit objective and validation profile; optimisation and adaptive sampling deferred but supported by the model.
- **Metrics (Q130–Q132):** auto-discovered from logs, CSV, headers, then verified (meaning, unit, extraction, definition version); inferred and confirmed are different; layered measurement model (value, unit, symmetric or asymmetric uncertainty, intervals, sample counts, method), richer data (distributions, covariance, masks) as linked artifacts; uncertainty kinds are not interchangeable; comparability is directly comparable / comparable after harmonisation (new derived metrics, approved) / unknown, and blocking invalid quantitative comparison never blocks side-by-side viewing.
- **Insights (Q133–Q135):** deterministic diagnostics work with no AI; four levels kept apart (measurements, statistical observations, hypotheses, validated conclusions); insight card shows observed relationship, possible interpretation, suggested next step; a dedicated Research Insights view, opt-in proactive monitors with budgets, never silent HPC jobs, transfers or inference cost; lifecycle new / examined / dismissed / promoted, independent of scientific validity; an ignored suggestion is not evidence it is false.
- **Outcomes (Q224):** execution (completed, interrupted, failed, cancelled), scientific validity (validated, provisional, invalidated, not assessed) and interpretation (supports, contradicts, inconclusive, not interpreted) are separate; negative results are results; reporting coverage is explicit (a board showing 12 of 30 registered evaluations says so).
- **Checkpoints (Q199):** pipelines declare application checkpoints, workflow-level continuation or scheduler restart; recovery proposes the cheapest scientifically valid path with authorisation (82 of 100 channels done, rerun 18) and reuses only what the algorithm permits.
- **Failure and degradation (Q168):** degradation is a designed property; never silently lower fidelity; reconcile real Slurm state before any retry (a failed status call is not a failed job); deadlines, limits, backpressure and circuit breakers; CI tests partial failures.
- **Durable operations (Q152, Q154):** persistent operation record (identity, parameters, owner, dependencies, progress, provenance) with executors local, server, HPC, external engines; ownership, idempotency, cancellation, recovery are explicit; after restart reattach to the existing Slurm job; distinguish resumed transfer, reattached job, restarted task, needs manual intervention. Artifact ingestion states Discovered → Transferring → Verifying → Available with staged storage and atomic publication; availability tracked per location; progressive integrity verification.

## 5. Data and catalog

- **Import (Q17, Q82):** open an existing experiment directory without changing the pipeline: auto-discover, preview uncertain associations, correct, save reusable import rules, index without copying large datasets; inferred relationships (`config_12.toml` ↔ `angle_map_12.fits`) are distinguishable from verified; recognise FITS, CSV, Parquet, JSON, TOML.
- **Live references (Q83, Q84):** change detection by metadata plus fingerprints; states available / modified / missing / unreachable; recorded runs keep configs, parameters, source revision and fingerprints; a fingerprint detects change but cannot restore bytes; published figures are pinned with update awareness (newer results detected, comparison offered).
- **Git (Q84–Q86):** extends Git, never replaces it; Git owns code history; each run records commit, branch, dirty state; metadata is hybrid: optional human-readable manifests in the repo, collaboration state in the database (board edits and comments never touch the working tree); Git-aware sync validates manifests, imports non-destructively, previews conflicts, never commits, pushes or rewrites without authorisation; a manifest is a description, never executable authority; Git-only collaborators need no account.
- **Datasets (Q136–Q138):** a dataset is a persistent logical identity plus immutable versions plus authorised storage locations (path, fingerprint, restrictions, availability each per location); experiments reference a dataset version, not a path; filename or header match is not proof of identity; derived (smoothed, downsampled) data gets its own identity. Indexing is progressive (discovery, scientific metadata from headers, previews, integrity); searchable before previews exist; runs on approved workers, not login nodes; the catalog shows how complete each stage is.
- **Cache and storage (Q139, Q145):** disposable cache (evicted within budget), pinned offline, preserved artifacts (never evicted); a cache never silently becomes the authoritative copy. "Review storage usage" with impact preview before deletion; recomputable is not disposable; external deletions are detected, not prevented.
- **Subsets and composites (Q141, Q142, Q208):** a saved subset is a virtual versioned dataset (source version, region, spectral interval) materialised on demand; existing scripts must run unmodified on resolved or materialised files; v1 is ordinary file compatibility plus reliable materialisation. Composites (collection, concatenation, mosaic) are manifests with explicit overlap policy; gaps are not zeros; v1 collections and simple concatenation.
- **Corrections (Q143, Q144):** original metadata preserved; versioned attributed corrections as a layer (sidecar import/export), optionally a new corrected file; descriptive notes differ from corrections that change numerical interpretation; impact analysis over lineage, verified versus uncertain dependencies, suggested revalidation, published results unchanged until a correction notice.
- **Transfers and sync (Q36–Q38):** small files like a file manager; large files get a preflight (size, space, conflicts, alternatives such as remote processing or slices) and a persistent resumable queue with verification; transfer, directory sync and on-demand remote access are different operations. Sync rules per directory (manual, one-way, bidirectional, excluded); the owner syncs Julia source and TOML often, cubes selectively per run; sync is not publication; conflicts are type-aware (diff and merge for source, preserve versions for FITS); destructive actions need confirmation and a local delete never deletes the HPC copy.
- **External archives (Q140, Q227):** discover, evaluate, reference without downloading, then retrieve subsets; the catalog can hold data it does not store; origin identifiers and terms are kept; connector API designed, discovery not in the first slice. Q227 (reproducible archive queries and selection manifests) was never answered.

## 6. Viewer and comparison

- **Built-in scientific viewer (Q24, Q25, Q91, Q92):** a dedicated tab, 2D and 3D FITS core, WCS navigation, value and metadata inspection, channel selection, spectrum extraction, synchronised map comparison, progressive remote loading; works on remote data without downloading the whole file; clearly marks downsampled preview versus full resolution; not a full CARTA/DS9 replacement (advanced overlays and specialised analysis go to extensions; owner now wants it all in-app, see section 15). Top priorities chosen: spectral cube navigation, scientific image comparison, performance on huge remote files. Spectra: pixel and region (rectangle, circle) averages with masks and units, bidirectional linking (region updates spectrum, spectral interval updates cube view), export; never assume axis order or spectral convention. Later: fitting, background subtraction, moments, PV diagrams, contours.
- **Regions (Q93):** temporary, then saved privately, then promoted to a shared project object with version history; pixel-space and celestial regions stay distinct; DS9 import and export where practical.
- **Exploration history (Q94–Q97):** exploration is lightweight (no permanent records); promotable results keep source version, region, spectral coordinates, method and recipe; private recoverable history stored as operations and references, not arrays, with exact-restore versus recompute distinguished and a warning when the source file changed; "Share exploration" gives a review snapshot (selected state, not whole history) that collaborators can inspect, comment on, "Continue from here" (a separate exploration, not a Git branch) or join live; live modes are Follow presenter, Explore independently, Share my view, with independent per-property sync (coordinates, zoom, channels, selections); joining a live session publishes nothing (Q98: v1 is lightweight live presentation).
- **Comparison (Q87–Q89):** adaptive workspace (synchronised viewers with shared zoom, coordinates, optional common scales and a compact parameter-difference summary for maps; table for parameter-heavy runs; plots for series); saved comparison keeps run versions, display settings, alignment, annotations; display differences are distinguished from data differences; quantitative ops respect axial angles. Alignment (Q88) is assisted with safeguards: WCS-aware sync is a display operation; reprojection, interpolation, convolution and resolution matching change data and need approval and a transformation record; matching grids does not mean matching resolution. Reproducibility is layered (Q89): save view (state), save analysis (recipe plus provenance for derived products), publish result (pinned); status shown, incomplete reproduction stated.
- **Large remote access (Q90, Q182):** previews first, then progressive tiles and subsets via approved caches and connectors; fidelity, permissions and availability always shown; a preview-only artifact must not pretend to support quantitative analysis. Planner chooses native reads, derived tiles, remote computation or local cache by permissions, layout, cost and fidelity; prefetch bounded; obsolete requests cancelled; exports use authoritative numbers.
- **Rendering and memory (Q183–Q185):** typed buffer descriptor (shape, dtype, byte order, strides, missing data, coordinates, units, source version); conversions intentional and traceable; renderer-independent visual model with backends WebGPU (primary target), WebGL2, CPU reference; equivalence means scientific interpretation, not identical pixels; preview may use reduced precision, measurement uses the precise path; a resource coordinator reuses buffers across panels, releases hidden viewers, cancels stale requests, evicts regenerable tiles first, recovers from device loss; the smallest backend set first, expand by measurement.

## 7. Scientific semantics (never violate)

Invariants repeat in `AGENTS.md`; the interview details they come from:

- **Untrusted files (Q200):** staged validation: header, resource preflight, selective bounded decoding, extended verification on demand; an impossible header fails before any allocation; distinct failure kinds; decoders fuzz-tested and checked against reference libraries; parsing success is not scientific validity.
- **Masks and quality (Q201, Q196):** distinct states (valid zero, missing, low-SNR, saturated, user-excluded); flags describe, a mask policy per operation decides (exclude, weight, propagate, flag, require review); compact bitfields, not dense arrays; QC is non-destructive and versioned (file integrity, scientific quality and fitness for a given analysis differ; no universal score; light checks at ingestion, heavy ones on authorised compute).
- **Calibration (Q202):** versioned registry as a first-class dependency (applicability, validity, procedure, uncertainty, review status); the latest is not automatically right; an update never rewrites history, it lists affected downstream results. v1: import references and record applied transformations.
- **Time (Q203):** typed temporal coordinates with scale, reference position, precision and uncertainty; conversions only via validated libraries; no millisecond-float reduction; simulation step 500 is not 500 s.
- **Coordinates (Q204):** four distinct operations (unit conversion, frame transformation, coordinate mapping, resampling); a km/s axis is not enough (frame, rest frequency, Doppler convention); reprojecting an orientation map differs from a scalar image; never infer missing physical context; v1 is accurate astronomical WCS and spectral axes.
- **Resolution (Q205):** pixel sampling, spatial resolution, spectral resolution, instrument response, effective resolution are separate; never silently smooth or deconvolve; no generic "Match Resolution"; VGT orientation maps need doubled-angle statistics, not Gaussian smoothing of the angle array; v1 reads beam metadata and flags mismatches. (The beam-matching convolution already built is an explicit derived resource.)
- **Field semantics (Q206):** scalar, directional angle (360°), axial orientation (180°), basis-dependent components (Stokes Q/U), vector and tensor; the 1° and 179° mean is 0° axial (90° arithmetic is wrong); the doubled-angle resultant can vanish, then the mean is undefined; colour scales for axial data are cyclic; unknown semantics are inspectable but block assumption-needing operations.
- **Topology (Q207):** regular grids and tables first; meshes, particles, AMR later through adapters; standardise meaning and capabilities, not data structures.
- **Units (Q209):** directly compatible, context-dependent (needs frequency, beam, Doppler) and incompatible; no implicit contextual conversion; conversions via Astropy or Julia libraries, planned at dataset level, no per-pixel unit strings.
- **Reference standards (Q210):** constants, rest frequencies, conventions, ephemerides are versioned dependencies; verified only when the adapter can establish what the library used; finished experiments never silently upgraded; the app does not curate constants itself.
- **Metadata (Q211):** native metadata preserved; semantic mappings are a separate versioned layer with status verified / declared / inferred / ambiguous; an AI suggestion never reaches verified; search results explain which mapping matched; v1 FITS only.
- **Uncertainty (Q197):** typed models (standard deviation, intervals, covariance, ensembles) with recorded interpretation and propagation method; automate only validated rules; unsupported is "unavailable", never a fabricated error bar; incompatible uncertainties are not combined.
- **Feature catalogs and associations (Q212, Q213, Q214):** a catalog is a versioned artifact with identities, geometry, measurements, lineage and review; matches are proposed correspondences (overlap, tracked continuation, proposed identity), never auto-equivalent; ambiguity is a valid result; non-detections keep context; selection and completeness models are versioned artifacts and corrections are explicit; unknown completeness is a valid state. v1: import existing catalogs, overlay, keep provenance.

## 8. Boards, figures, review, publication

- **Board model (Q10, Q11):** presentation-based, curated by the researcher; the explorer shows runs not on a board; new runs never auto-join a board. Flexible grid (rows and columns, resize, group, annotate). Creation (Q105): from an experiment, comparison, investigation or review package with suggested layout, or blank, or a template (experiment comparison, spectral analysis, investigation summary, weekly meeting). Adding results (Q12): drag from explorer, bulk select with automatic layout (channels as columns, methods as rows, histograms beneath), and an in-board picker; inserting stores a reference, never a copy. Modes (Q13): Presentation (clean) and Analysis (interactive viewers, synchronised zoom, regions) over the same board without rebuilding layout.
- **Personal versus shared state (Q14, Q15):** exploring never changes a shared presentation; a saved finding is a lightweight persistent annotation (author, time, artifact, coordinates, view context) that can later become an issue, a notebook entry or a linked experiment.
- **Presentation and export (Q106–Q108):** one board with an optional ordered presentation sequence (no duplicate slides), pinned artifact versions; v1 priorities: interactive browser sharing, PDF, scientific figure export (PowerPoint and standalone HTML later); exports keep units, axes, legends, provenance where the format allows and never bundle restricted data. "Prepare for offline" lists what works offline, partially, or needs the remote (v1: cached figures, selected spectra, navigation). Offline editing is queued and synced; conflicts keep both versions; permissions revalidated at sync (Q109).
- **Working board versus snapshot (Q110–Q113):** the working board is collaboratively editable; a published snapshot ("Weekly meeting #12") has pinned evidence and can still hold interactive viewers; later edits never alter it. Publishing is destination-aware (internal, restricted reviewers, public) with policy; a preflight per artifact offers exclude, substitute an authorised preview, request permission, change audience, keep private, and includes a "Preview as public visitor"; versions are citable, with correction, supersession and withdrawal notices; v1 has stable versioned URLs and citation metadata, no own DOI service. Repository deposit (Zenodo) is explicit and later (Q114).
- **Figures (Q186–Q188):** a figure is a versioned declarative specification (artifact versions, transformations, WCS, units, colormaps, annotations, layout, export settings) separate from viewer state and the exported file; interactive and publication renderers; export PDF, SVG, TIFF, PNG at physical size and resolution; layout editor with snapping, shared axes and colourbars, journal presets, lettering; scripted components edit through declared parameters, imported SVG/PDF/PNG at composition level, unknown code is preserved and re-executed, never rewritten. Boards are for storytelling; figures for precise publication.
- **Comments and review (Q99–Q104):** comment directly on a figure, region or spectrum (artifact version, coordinates, region, interval and display captured; anchored to scientific coordinates so they survive zoom and other resolutions); replies and resolution are lightweight, with optional evidence (commits, runs, comparisons); resolved is not "hypothesis confirmed". The supervisor sees contextual updates and a review queue (activity history, scientific change summaries, "Ready for review"); factual changes, researcher conclusions and suggestions are never mixed. A review package starts from suggestions, the researcher trims, adds a scientific question and optional board, picks reviewers; outcomes are separate (workflow status; methodological assessment; scientific assessment) and tied to exact versions, so v4 never inherits v3's approval.

## 9. Collaboration, access and policy

- **Three separate things (Q7, Q44):** cluster access, project membership and data-sharing permission. Individual SSH for development plus published or admin-approved shared data access for collaborators without HPC credentials; private keys never shared; project permission never silently reaches files the cluster account cannot read. Roles Viewer, Researcher, Maintainer, Owner with optional resource exceptions and a "view effective permissions" panel.
- **Sharing (Q45, Q46):** invitations, revocable guest links, published collections; private by default; commenting and editing need authentication; a link exposes only approved resources, never HPC paths, code or unrelated experiments. Visibility is private, public project or publication portal (a portal can exist while the project stays private); changing visibility never auto-exposes anything.
- **Delegated execution (Q29–Q31):** owner: other users should be able to submit jobs without credentials if the owner has them and approves. Hybrid approval: new jobs need explicit approval; trusted collaborators use preapproved templates and budgets; approval covers the exact executable, revision, parameters, inputs, limits and destination, not a free command; revocable; audit of who requested, who authorised, what ran. Lifecycle Requested → Authorised → Submitted → Running → Completed/Failed, so nobody guesses whether it waits on approval, SSH or Slurm; queued when only a personal connector exists, manual submission where automation is restricted. Whether Irgetas permits delegation is unverified.
- **Policy (Q117–Q119):** layered policy (researcher, project, institution, runtime capability), most restrictive wins, unknown is not permitted, the resource owner stays authoritative; a planner checks where an operation may run and which data may move, explains refusals; derived results inherit source restrictions until an authorised rule or decision, with downstream reassessment if a restriction changes. Cross-instance (Q115, Q116): guest invitations and stable cross-instance references first, one client listing local and several instances with origin shown, each instance keeping its own authority; federation later.
- **Authorisation and identity (Q71, Q159, Q161):** local projects need no account; accounts, invitations, OIDC and institutional SSO; platform auth never grants SSH or Slurm rights. Central policy decision, scoped short-lived delegated capabilities (a capability is not a credential); workers authenticate themselves and never borrow a researcher's SSH session; credential broker (agent, OS keyring, Vault) where workers get operations, not secrets, and agents request operations from the broker.
- **Isolation and supply chain (Q160, Q162, Q165):** risk-tiered execution (local Julia pipeline as a process, third-party plugin in a restricted worker, AI-generated code in a sandbox, Slurm under the researcher's account); real OS-level sandboxes where allowed; show what files, credentials and network a run can reach. Signed and hash-verified packages, capability review, no auto-upgrade of scientific dependencies, re-approval when a plugin asks for more. Multi-tenancy is a security property (shared infrastructure with strict tenant scoping first; no cross-tenant caches, indexes, jobs; quotas).

## 10. Architecture and performance contract

- **Backend (Q146, Q150, Q151):** modular core (projects and identity, scientific records, collaboration, API and MCP) plus separate scientific workers and compute connectors; no Kubernetes or broker for small installs; arbitrary scientific code never runs in the auth process. Go for core, SSH, transfers; TypeScript for the web; Python and Julia for algorithms; native or Rust only where measured. Control plane (versioned APIs, small results) separate from the data plane (binary arrays, tiles, artifact references; workers exchange references, not copies; avoiding copies never bypasses authorisation).
- **Persistence (Q153, Q155):** relational core (SQLite local, PostgreSQL shared); large data on files or object storage; append-only history only where needed (provenance, publication snapshots, reviews, audit, operation transitions), no event sourcing; indexes rebuildable; no search engine until measured. Versioning has four mechanisms, not one per entity: immutable evidence, mutable app state, ephemeral state, external references (turn 234).
- **Evolution and ops (Q156–Q158, Q163, Q166–Q167):** stable typed core with versioned extension schemas (unknown extensions never make a project unreadable; uninstalling never deletes history); capability negotiation with independent app, protocol, schema and plugin versions (a newer client never auto-migrates a shared project); sync by object semantics (documents CRDT, boards ordered operations, provenance append-only, permissions server-authoritative; convergence is not scientific correctness); layered local-first observability with correlation ids and a user-inspectable support bundle; consistency-aware backups with manifests, test-restore and post-restore reconciliation; staged expand-migrate-contract upgrades that never resubmit running jobs.
- **API (Q170, Q171, Q181):** contract-first, REST/OpenAPI first, event streaming, Python and Julia SDKs, MCP adapter exposing permission-limited operations; bulk data through the data plane; typed events with delivery by class (ephemeral progress, durable at-least-once with idempotent consumers and an outbox); canonical schemas generate wire types, with hand-optimised SDKs and cross-language compatibility tests that check units and frames.
- **Performance budgets (Q149, Q169, Q172, Q182):** measurable targets from the start on representative workloads (interaction latency, time to first preview, channel switching, bytes transferred, cache effectiveness, table filtering, indexing throughput, peak memory); a performance suite beside the first slice and regression checks in CI; never transfer a whole cube to show one channel. Workload classes interactive, presentation, background, batch with reserved interactive capacity, fair share, admission control, backpressure and visible queue reasons (50 ms channel switch idle must not become 3 s during indexing). Frontend partitioned by workload: large arrays outside reactive state, virtualised 100,000-row tables, coalesced job events, Web Workers, tab state kept with memory-aware eviction; framework chosen by measured prototypes.
- **Repository and process (Q177–Q180):** modular monorepo first (apps, core, workers, sdk, packages, tests, deploy) with automated architecture checks, third-party plugins in their own repos; living architecture docs with machine-readable contracts and executable enforcement; contract-first vertical slices with controlled agent parallelism and independently specified acceptance cases; progressive dev environments with a protocol-aware Slurm simulator (not fake success).
- **Platform verification (Q164):** reference datasets, differential tests against trusted libraries, property and fuzz tests, scientific end-to-end scenarios, performance regression; exact, numerical and interpretive levels; fast tests on every PR, large scientific suites scheduled.
